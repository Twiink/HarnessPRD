适用：简历或自我介绍中提到 HarnessPRD 项目。

## 1. 这个项目的核心业务链路是什么？
这是一个帮用户把「模糊想法」变成「能交给 AI 写代码的文档包」的工具。用户先录入需求，再和 AI 像产品经理一样聊几轮把不清楚的地方对齐，然后依次产出三样东西：产品需求文档、接口说明、以及给 Claude Code 这类工具用的提示词。每一档都能让人改、能让 AI 按一句话微调，也可以跳过某一步。所以它是一条完整的文档流水线，不是单次聊天。

**高频追问：** 如果只用一句话概括价值，你会怎么说？
**追问回答：** 把「不稳定的模型输出」收成「可交付的需求与开发文档流水线」，让后续 Vibe Coding / Claude Code 有稳定上下文，而不是每次从零描述产品。

## 2. 项目在发展过程中做过哪些流程迭代？为什么要做这个改变？
最初版本的流程比较直：用户填表、聊天澄清，然后把整段聊天记录交给模型写 PRD。问题有两个：第一，聊天记录是自由格式的，模型每次从里面理解结构的过程不稳定，容易漂；第二，模型会悄悄修改用户已经确认过的需求，而用户无从感知。

迭代后的方案引入了结构化摘要：表单数据和澄清结果被收成一份有骨架的 JSON 对象，聊天结束后把新确认的信息回填回去，有变化就展示 diff 让用户确认，PRD 以确认后的摘要为主输入，聊天记录只作补充。同时，生成接口文档前不再让用户手动确认检索结果，团队规范改为后台静默注入。核心改变是两点：输入先被收敛，不再从混沌文本里硬猜结构；输出中间有人工确认节点，不再让模型悄悄改需求。

**高频追问：** 这个改变付出了什么代价？
**追问回答：** 流程多了一步用户确认，开发复杂度增加；但生成的 PRD 格式更统一，需求跑偏的情况明显减少。对 AI Agent 系统来说，「可控」比「流程短」更重要。

## 3. 整体技术架构怎么分层？
可以想成四层：浏览器里的单页应用负责录入、聊天、文档审核和方案列表；后端 API 负责调模型、拼提示词、跑生成任务，并用 SQLite 存快照和任务状态；大模型和 Skill 知识层在最底下；最上面还有一层可观测，记录每次调模型用了多少 Token、走了哪些步骤。前后端用普通 HTTP，澄清和生成订阅都用 SSE 流式推送。后端按职责拆成「管对话」「管文档生成」「管 Job 执行」和「管快照读写」，提示词和团队规范集中管理。

**高频追问：** 有没有经历过架构升级？
**追问回答：** 早期进度只在浏览器本地，后来改成服务端存快照，才能做方案列表和续编；再后来文档生成从「绑在浏览器连接上」升级为后台 Job，刷新也能重连继续看进度。调模型的核心链路没变，仍是后端拼 prompt、前端订阅流式结果。

## 4. 工作台进度和对话历史存在哪？长对话怎么办？
两件事要分开。用户做到哪一步、表单和文档写到哪了，存成服务端 Session 快照，带方案列表和可续编的链接；只有开始澄清、生成文档这类实质动作才入库，避免空记录。正在跑的生成任务单独存 Job 表，草稿每几百毫秒节流写库，Phase 变更立即写库。调模型时，浏览器把当前聊天记录和文档正文一并发给后端，后端不单独跑一套聊天会话服务。长对话的痛点是单次请求体会变大，短期靠截断或摘要，定稿后以 PRD 为主少带闲聊；Token 预算模块会在调用前估算并告警。

**高频追问 1：** 对话已经很长，短期你会怎么处理？
**追问回答：** 截掉很早的闲聊，或对旧对话做摘要；PRD 定稿以后，后面生成接口文档、提示词时以 PRD 为主，少带无关对话。澄清阶段还会在 done 事件里返回 context_usage，让用户感知上下文占用。

**高频追问 2：** 若做成正式产品，架构上还会怎么演进？
**追问回答：** 长对话滚动摘要、按片段检索代替全量带历史；再加账号隔离和多设备同步。快照和 Job 已经解决了「进度别丢」，但还不是完整的多租户会话服务。

## 5. 为什么澄清用 SSE 直连，文档生成却做成 Job？
澄清是短交互，用户发一条、收一条，连接断了重发即可，不需要后台持久跑任务。文档生成往往几十秒甚至更长，用户刷新、关 tab、网络闪断都很常见。如果生成绑在同一条 SSE 连接上，一刷新后台任务也跟着停，半篇草稿还可能丢失。

Job 方案把「创建任务」和「订阅进度」拆开：点生成立刻拿到 jobId，Writer / Review / Rewrite 在服务端协程里顺序跑，和浏览器在不在线无关。刷新后用同一 jobId 重连，先发 snapshot 把已有全文立刻展示，再收后续 live chunk。澄清仍走 POST + fetch 读流，生成走 GET 订阅 Job 流，两条链路职责清晰。

**高频追问：** 为什么不用 Celery + Redis？
**追问回答：** 当前是单机部署、SQLite 落库，用 asyncio.create_task 在同进程后台跑就够了，运维成本低。Job 表和 API 形状已经预留好了，以后要多实例或排队，可以把执行层换成 Celery Worker，前端协议不用大改。

## 6. 为什么全链路用 SSE，而不是 WebSocket？
澄清和生成文档都是服务器往浏览器推字，用户不需要通过同一条长连接反向高频发小包。SSE 基于普通 HTTP，和现有网关、代理兼容好，实现也简单。WebSocket 更适合多人协同、实时双向场景，我们暂时没有这类需求。

**高频追问：** 浏览器不是有 EventSource 吗，为什么不用？
**追问回答：** 原生 EventSource 只支持 GET，而澄清要 POST 带上聊天记录、PRD 正文等，所以用 fetch 自己读流、按行解析服务端事件。Job 订阅虽然是 GET，但为了和澄清链路保持同一套解析逻辑，也统一用 fetch。

## 7. 流式协议在前端怎么解析？
后端按「一行一条事件」推送，每条里是 JSON，表示「又来了一段字」「进入审查阶段」「出错了」「整段结束」或「运行汇总」等状态。前端边读边更新界面；最终以「结束事件」里的完整结果为准，不能把手上的半篇草稿当成定稿。PRD 生成时还会用 phase 事件驱动进度条，比如「正在写」「正在审」「正在改」。

**高频追问：** 流式字都显示完了，但还没收到结束事件，算不算成功？
**追问回答：** 不算。没有结束事件就按失败处理，提示用户重试，避免复制半篇去下游工具。Job 重连时 snapshot 会把已有全文立刻展示，但 done 没到之前仍然不算终稿。

## 8. 刷新页面后，生成任务怎么恢复？
两步走。第一步，loadSession 拿到 activeJobId，调 GET /api/jobs/{id} 预加载 status、phase、draft_content，页面不空白。第二步，重连 GET /api/jobs/{id}/stream，首包是 snapshot 事件，把已有全文和当前阶段一次性推过来，后续才是 live chunk 打字机。

禁止假流式重播：snapshot 全文立刻展示，只对**新产生**的内容做打字机效果，避免用户以为又在从头生成。若 Job 已完成，直接展示终稿和审查结果；若失败，保留 draft_content 供用户手动抢救。

**高频追问：** reviewing 阶段刷新，用户会看到什么？
**追问回答：** 已有 PRD 初稿立刻展示，Stepper 停在「审查中」，等 review 事件或 done 事件回来。不会清空屏幕重新流式出字，也不会跳回澄清对话。

## 9. 前端怎么管理「现在在哪个步骤」？
用多阶段状态机管流水线：填表、聊天、生成/审核 PRD、接口文档、提示词。URL 对应新建、方案列表和继续编辑，从列表或链接能回到某次记录。正在生成时会锁住关键操作；刷新时若捞到 activeJobId 就触发 Job 重连，若没有 Job 但有草稿就停在文档审核；流式过程中的半篇不会当终稿写入快照。

**高频追问：** 用户刷新时 PRD 生成到一半，你会丢数据吗？
**追问回答：** Job 草稿每 500ms 节流写库，Phase 变更立即写库，所以大部分情况能恢复到最近进度。若服务重启，running 状态的 Job 会标记 failed，但 draft_content 仍保留，用户可以手动编辑或重新生成。

## 10. 前后端在澄清和文档阶段分别调哪些能力？
分三个阶段：需求录入阶段是纯前端表单，不调后端接口；对话澄清阶段调「开始对话」和「继续对话」两个流式接口，也可以跳过直接进文档阶段；文档生成阶段最复杂，顺序是：对话写回结构化摘要并让用户在 diff 预览里确认变更 → 创建 PRD Job（写 → 审 → 可选改）→ 用户确认 PRD 基线 → 创建接口文档 Job → 创建提示词 Job。每个文档生成后都进审核页，支持直接编辑或用一句话触发 AI 优化，不必整篇重来。

**高频追问：** 为什么生成接口文档前不再弹「检索确认页」了？
**追问回答：** 早期接口文档走关键词检索 + 用户确认，摩擦大，且规范库很小，检索能力有限。后来统一到 Skill 知识层，团队规范在后台静默注入，和 PRD 一样无感；注入了哪些规范文件会在 run_summary 里记录，排查风格变化时仍可追溯。

## 11. 为什么采用「结构化表单 + 对话」而不是纯聊天？
表单先把产品名、用户、核心功能等骨架定住，少漏项；对话专门解决「用户自己也说不清」和「字段之间有矛盾」的部分。纯聊天容易漏字段；纯表单又太死。这比较贴近真实产品经理：先有大纲，再访谈细化。

**高频追问：** 表单已经填了，澄清阶段 AI 还应不应该重复问？
**追问回答：** 不应该复读表单，而是围绕空白和歧义，每次只问一两个关键点。AI 回复里还会嵌入元信息（开放问题数、是否建议收口），前端据此展示就绪度提示。

## 12. 三份产出文档之间是什么关系？
PRD 是主文档。接口文档主要看 PRD，并参考澄清对话和团队规范。提示词套件主要看 PRD，有接口文档会更准，没有也能生成，但「怎么实现接口」那类提示会弱一些。三份都可以在审核页用自然语言做小改，不必整篇重来。接口文档一次生成一篇 Markdown，里面分核心接口和边缘接口。下游生成前还要用户显式「确认 PRD 基线」，防止 PRD 还在改就往下走。

**高频追问：** 用户跳过接口文档直接生成提示词，你怎么交代风险？
**追问回答：** 明确说联调、接口实现类提示会缺约束，建议补一版简版接口说明或事后再优化；产品上最好二次确认。基线确认是硬门槛，PRD 没确认基线时后端直接 400 拦截。

## 13. PRD 的「写 + 审 + 改」算不算 Multi-Agent？
算 Multi-Agent 多智能体编排。分工为一个 Agent 负责编写文档，另一个 Agent 对照校验清单核查内容完整性、信息真实性；审核不通过则触发第三个 Agent 按意见定向修订，**最多改一轮**，把控耗时与资源成本。该模式将文案撰写质量、交付合规性拆分校验，审核结果也可对外展示。

**高频追问 1：** 和一次 Prompt 写完比，最大收益是什么？
**追问回答：** 质量可解释、可展示；以后可以做回归测试；成本用「最多改一轮」卡住，不会无限循环。

**高频追问 2：** 审查仍不满意怎么办？
**追问回答：** 不无限自动循环，交给人在审核页改，或用「优化文档」按指令小改。revision_applied 字段会告诉用户「系统自动改过一次」。

## 14. 接口文档和提示词为什么只做「写 + 审」，没有自动改写？
PRD 是整条链路的源头，质量要求最高，值得多一轮 Rewriter。接口文档和提示词是派生文档，输入已经相对收敛（PRD 基线 + Skill 规范），Review 发现问题后交给人工在审核页改更划算，避免多一次 LLM 调用却引入新漂移。这是成本和收益的平衡，不是技术做不到。

**高频追问：** 以后会不会给派生文档也加 Rewriter？
**追问回答：** 可以，但要设同样的「最多一轮」上限，并且 UI 要明确区分初稿、审查意见和自动修订版。当前优先保证 PRD 质量，派生文档靠 quality_gate 结构校验 + 人工审核兜底。

## 15. 审查结果长什么样？界面怎么用？
审查会给出：是否通过、一段总结、以及问题列表（严重级别、对应章节、问题描述、修改建议）。生成过程中界面可以显示「正在审查」；结束后若自动改过，要明确告诉用户，避免误以为初稿就是终稿。Review 结果是结构化 JSON，后端有「提取 → 修复 → 重生成」容错链，PRD Review 是三级，派生文档 Review 是两级。

**高频追问：** 没通过也没自动改，界面怎么提示？
**追问回答：** 标明「未通过且未自动改写」，列出问题清单，引导手动编辑或点优化，不能显示成已通过质检。quality_gate 的结构校验报告单独展示，和 Review 的语义审查是两层不同的事。

## 16. 如何保证系统生成的 PRD 内容稳定、可信？用了哪些机制？
四个层次。第一是 Prompt 约束：Skill 里的写作规则和 PRD 模板从结构上限制模型的发挥空间，缺失信息要求标「待确认」而不是自由发挥。第二是 Review Agent：生成后有独立的 Reviewer 对照清单核查，不通过则自动改一次。第三是 quality_gate：生成结束后用确定性正则检查章节齐不齐、MVP 表格在不在，不调 LLM，成本低。第四是人工确认节点：摘要回填有 diff 预览，PRD 基线确认锁住下游，把「模型做了什么」摊给用户看。

**高频追问：** 哪一层最容易失效？
**追问回答：** Prompt 约束最脆，边缘需求容易绕过规则。Review Agent 相对稳，因为是独立模型用清单核查。quality_gate 只管结构不管语义。人工确认是最后兜底，这层不能省。

## 17. 「摘要回填」是做什么的？
用户聊完后点「生成 PRD」，系统会先把对话里新确认或修改过的信息，同步回那份结构化摘要，并和改之前做对比。有变化就全屏展示「哪些字段变了」，用户确认后再创建 PRD Job。目的是避免模型悄悄改需求用户却不知道。

**高频追问：** 用户不同意某条变更怎么办？
**追问回答：** 以用户确认后的摘要为准；可以取消回到聊天继续澄清，未确认的不进入写 PRD。若前后摘要完全一致，可以跳过 diff 面板直接生成。

## 18. 摘要同步时模型返回的不是合法 JSON 怎么办？
这是整个流程里最需要提前做校验兜底的地方，因为后面写 PRD 依赖这份结构化数据。后端会先从模型输出里抠出 JSON，失败再用「修复格式」的提示让模型重试，还不行就返回错误，前端提示用户再聊一轮或手改摘要，不会把脏数据传下去。

**高频追问：** 为什么不在浏览器里用正则解析？
**追问回答：** 字段多、嵌套深，边界难兜；统一在后端提取、修复、校验更稳。这和 Review JSON 容错是同一套思路。

## 19. 团队规范是怎么注入到生成流程里的？
早期接口文档走本地关键词检索，生成前要用户看命中片段并确认，三条产物三种做法，维护成本高。后来统一到 Skill 知识层：PRD、接口文档、提示词都从 `skills/` 目录读规范文件，经 skill_loader 和注册表 `config/skills.yaml` 静默拼进 prompt。用户点生成直接起 Job，无额外确认页；run_summary 里的 injected_skills 记录这次用了哪些规范，方便排查「为什么风格变了」。

**高频追问 1：** 为什么小规范库不用向量检索？
**追问回答：** 现在只有几份固定文档，关键词和整文件注入够用，部署零依赖。规范多了、需要语义找相似段落时，再上 embedding + 向量库；Skill 注册表的设计可以平滑演进，不必推翻重来。

**高频追问 2：** 新增一种文档规范要改哪些地方？
**追问回答：** 在 skills/ 下加目录和 skill.yaml，在 config/skills.yaml 里声明 artifact 绑定关系，尽量不改 document_service 主流程。产品同学主要改 markdown 规范文件，不用动 Python。

## 20. 提示词套件包含什么？
大约五类：项目总览、按 MVP 的功能开发、接口实现、前端开发、代码审查。输入主要是 PRD，有接口文档更好。生成规范同样从 Skill 目录加载，不再硬编码在 prompts.py 里。

**高频追问：** 没有接口文档时怎么防止胡编接口？
**追问回答：** 在 Skill 写作规则里要求：接口类内容标「待补充」或只写功能级描述，禁止虚构 URL、字段名。Review Agent 和 quality_gate 也会交叉检查。

## 21. 「优化文档」和「重新生成」有什么区别？
优化是在当前这一版上按用户一句话改相关段落，比如「部署改成 Docker」，要求结构不乱，走独立的 optimize Job，单轮流式。重新生成是整条流水线再走一遍，更贵，内容也容易飘。小改用优化，大改结构才重新生成。

**高频追问：** 优化把标题层级弄乱了怎么办？
**追问回答：** 提示里已要求保持结构；仍出现就引导用户重新生成或手改；quality_gate 会检查章节标题是否还在。PRD 优化后基线自动失效，下游会提示「上游已过期」。

## 22. 「技能包 / Skill」是干什么的？
把「怎么写 PRD、字段有哪些、示例长什么样」从代码里拆到仓库里一组配置文件，产品/提示词迭代时主要改这些文件，不用改 Python。包括字段定义、PRD 模板、写作规则、示例等，通过 skill.yaml 声明版本和绑定关系，方便版本管理和复用。

**高频追问：** Skill 和代码里的 Prompt 常量有什么分工？
**追问回答：** 给人看、常改的产品规则放 Skill；Agent 角色定义、工程拼接、强类型结构留代码里。Skill 是产品可以独立迭代的部分，不应该和路由代码耦合。

## 23. 怎么切换不同大模型厂商？
后端有一个工厂方法，按配置创建 Anthropic 或 OpenAI 的客户端，业务代码只调统一的流式接口，不关心底层差异。密钥只在服务器环境变量里，前端拿不到。models.yaml 维护各模型的物理窗口，运行时可在内存里切换 Provider，重启后仍以配置文件为准。

**高频追问：** 为什么某个依赖库要锁版本？
**追问回答：** 新版本会多发代理不支持的字段，导致 400，锁版本是对接兼容问题，不是功能偏好。

## 24. 提示词在项目里怎么管理和迭代？
按场景分开：澄清、写 PRD、写接口、写提示词、优化文档、摘要同步、JSON 修复等。工程拼接类的 Prompt 在代码里的常量文件；产品规则、写作约束、模板结构放在 Skill 配置文件里。改 Prompt 或改 Skill 即可迭代，不必动路由；大改时用几组固定需求做回放对比。

**高频追问：** 会不会把所有 Prompt 都放进 Skill？
**追问回答：** 不会。给人看、常改的产品规则放 Skill；工程拼接、强类型的留代码里。Reviewer 的清单和 JSON schema 也偏工程侧，和团队写作风格分开管理。

## 25. 澄清阶段的提示词要注意什么？
角色是资深产品经理：双向聊、每次只问一两个关键点、围绕已有表单或摘要补空白，不要一次抛十个问题，也不要在澄清阶段就开始写完整 PRD。Prompt 里会明确强调「只澄清、不写文档」，把阶段边界对模型说清楚。AI 还会在回复末尾嵌入元信息块，前端解析后展示开放问题数和收口建议。

**高频追问：** 用户一直闲聊怎么办？
**追问回答：** 提示词里礼貌拉回；前端有就绪度评估和生成前确认弹窗作软约束；产品上也可考虑轮次提示或允许跳过澄清。

## 26. 完整走一遍，大概几次调模型？成本在哪？
取决于聊几轮：每聊一轮算一次；写 PRD 至少「写 + 审」，不过审再加一次改；接口文档、提示词各「写 + 审」；摘要从对话同步回表单也算一次；用户点「优化文档」再加。成本大头在多轮澄清和 PRD 的写审改，不是单次接口文档。任务结束时会推送一份「运行汇总」，里面能看到总共用了多少 Token、调了几次模型。

**高频追问：** 成本要砍一半先砍什么？
**追问回答：** 限制澄清轮次或压缩历史；PRD 只在严重问题时才自动改写；接口文档和提示词不自动加改写轮。不会先砍审查环节，因为用户能直接感知质量下降。

## 27. 流式输出中途失败，前端怎么处理？
收到「出错」事件就提示用户，并把页面退回到安全步骤，比如生成 PRD 失败就回到聊天或审核页。屏幕上流式出来的半篇要清空或标记为草稿，不能当终稿；发消息失败则恢复发送前的聊天记录。若是「Token 超限」这类专门错误码，会给出对应提示。

**高频追问：** 字都出来了但没有结束事件？
**追问回答：** 按失败处理，提示未完成，请重试。后台任务场景下，草稿可能已写入数据库，用户可以手动编辑抢救，但不能自动流转到下一步。

## 28. 如何降低模型编造需求里没有的内容？
靠多层约束叠起来：澄清阶段只基于已有信息提问；写文档时缺的信息标「待确认」；摘要回填严格跟对话原文走；审查 Agent 对照清单核查；生成结束后再跑一遍结构规则检查（不调模型，看章节齐不齐、几份文档之间是否对得上）。规范和 PRD 冲突时，以 PRD 为准。没法彻底杜绝，所以每档文档都留人工审核。

**高频追问：** 举一个你担心的编造例子？
**追问回答：** 比如用户没提登录，接口文档里冒出 OAuth——靠 PRD 标待确认、审查问题列表、Skill 写作规则约束；仍出现就靠人删。结构检查还会看接口路径是否统一前缀这类硬规则。

## 29. API Key 和模型配置存在哪？
密钥只在服务器环境变量，前端永远接触不到。有一个配置接口可以查当前用的哪家模型、是否已配置 Key，改配置只在内存生效，重启恢复文件，生产必须鉴权或关掉。

**高频追问：** 为什么接口只返回「有没有 Key」而不是 Key 本身？
**追问回答：** 防止泄露到浏览器和网络日志；前端只需要知道能不能用。

## 30. Token 预算是怎么设计的？为什么叫「双层」？
两层取更严的那个。**硬件层**看模型本身能吃多长：总窗口减去留给输出的空间，写在模型配置文件里。**策略层**是产品自己定的「合理用量」：澄清对话允许带更长历史，单次写文档则更保守，写在环境变量里按步骤类型区分。估算优先用 tiktoken 数 Token，不行就用字符数粗算。用到预算 95% 以上可以只告警继续，也可以直接拒绝并提示「上下文太长」。

**高频追问 1：** 为什么需要策略层，模型窗口不是已经很大了吗？
**追问回答：** 窗口大不代表应该塞满。单次写 PRD 输入过长，会挤占输出空间，生成质量反而下降。策略层管的是「怎么用才合理」，和模型物理上限是两件不同的事。

**高频追问 2：** 预算结果怎么让用户看到？
**追问回答：** 澄清结束时，在「完成」事件里附带上下文占用情况，聊天页可以实时提示。文档生成结束后，在「运行汇总」里事后统计，展示在汇总面板。

## 31. 你怎么观测一次生成的成本和步骤？
每次调模型都会自动记下：这一步叫什么、用的哪个模型、花了多少 Token、耗时多久、成功还是失败。整次任务结束推一条「运行汇总」给前端，不用人工加日志。采集器用线程上下文变量挂到当前任务上，避免函数层层传参。每次 HTTP 请求还有唯一请求 ID，方便在日志里串起来查。就算任务失败，汇总信息也会在最后推送，方便排查。

**高频追问：** 流式输出怎么统计 Token？
**追问回答：** 流式场景下，用量信息在最后一个数据块里才完整返回，所以要等流结束才记录。这是所用框架的流式特性，不是设计疏忽。

## 32. 生成前和生成后分别有哪些「门禁」？
分三个时机。**生成前**检查「有没有资格开始」：写 PRD 必须有结构化摘要；写接口文档和提示词必须先确认 PRD 基线且 PRD 不为空——不满足直接报错，任务都不创建。**生成中**由审查 Agent 看语义质量。**生成后**用正则做结构校验（不调模型）：章节标题在不在、表格有没有、几份文档功能数是否对得上，结果跟着版本存下来。三者各管一摊，不能互相替代。

**高频追问：** 「确认 PRD 基线」为什么比「PRD 不为空」更强？
**追问回答：** 有内容不代表用户认可。基线是用户显式点的「我确认这份 PRD 可以当下游依据」。PRD 被改过后内容指纹对不上，基线自动失效，新的下游生成会被拦住并提示「上游已过期」。

## 33. 结构校验和审查 Agent 有什么区别？
审查 Agent 要调模型，看语义：信息全不全、有没有瞎编、各段是否自洽。结构校验不调模型，用固定规则看格式：六大章节标题在不在、MVP 表格有没有、接口文档是否分了核心/边缘区、提示词里的功能数和 PRD 是否大致匹配。可能出现「语义审查过了但结构扣分」，或反过来，两层互补。

**高频追问：** 结构校验为什么不也交给大模型？
**追问回答：** 结构规则稳定、结果要可预期，用正则检查零成本、零随机性，适合自动化回归。语义质量才需要模型的判断力。结构交给规则，语义交给 Agent，职责清楚。

## 34. 文档版本是怎么管理的？
每种文档有一个「当前槽位」存最新版，另有一条「版本历史链」存历次变更。无论是 AI 生成、用户优化、编辑自动保存还是手动恢复，都会新建一个版本号，并带上来源类型和附加信息（审查结论、结构校验报告、当时依赖的上游 PRD 是第几版）。恢复历史不是把指针拨回去，而是基于旧内容新建一版，审计链不断。前端版本面板可以对比和恢复。

**高频追问：** 「自动保存」和「AI 生成」的版本有什么区别？
**追问回答：** AI 生成或整篇重写的版本，带着审查和结构校验结果；编辑过程中的自动保存只是防抖落盘，附加信息很轻。展示上 AI 生成版优先级更高，自动保存不会盖掉审查结论。

## 35. 下游文档怎么知道上游 PRD「过期了」？
生成接口文档或提示词时，会在版本信息里记下「当时依据的 PRD 是第几版」。前端拿当前 PRD 版本号和这个记录比，不一致就展示「上游已更新，建议重新生成」横幅。不用 diff 全文，只看版本号，简单也够用。

**高频追问：** 用户无视横幅继续用旧接口文档会怎样？
**追问回答：** 产品上不硬拦，但导出交付包时，清单文件会带过期警告，让接手的人自己判断。若重新生成，依赖记录会更新到新版本。

## 36. 同一个方案能同时跑两个生成任务吗？
不能。同一个方案里，同一类任务（比如「生成 PRD」和「优化 PRD」）同时只能有一个在跑，第二个请求会被拒绝。不同产物（PRD 和接口文档）也建议串行，避免两个任务同时写同一份进度快照造成混乱。任务进行中前端会锁住生成按钮。

**高频追问：** 用户连点两次生成怎么办？
**追问回答：** 第一次成功后，当前进行中的任务 ID 会写入方案快照；第二次请求被拒绝，前端提示「已有任务进行中」。刷新后重连已有任务，不会重复创建。

## 37. 服务重启时，正在跑的任务怎么处理？
启动时会扫一遍任务表，把「进行中」的任务标记为失败，并说明是服务重启中断。但已流式出来的草稿和改写前的备份仍会保留，用户可以手动编辑或重新生成。这是单机部署的务实选择，不是 Bug。

**高频追问：** 未来怎么避免重启丢任务？
**追问回答：** 上独立任务队列（如 Celery + Redis）或容器编排里的 Job，工作进程和 API 进程分开，重启 API 不影响后台跑模型。当前任务表已经预留了状态和阶段字段，换执行层比从零设计容易。

## 38. 任务事件广播是什么？浏览器关了任务会停吗？
后台有一个内存里的事件广播器：任务执行过程中，把「又来一段字」「阶段切换」「审查结果」「任务结束」推给当前正在看的浏览器。连接断开只是取消订阅，**不会取消**后台协程，任务继续跑完并写库。如果当时没有人在看，实时事件会丢，但草稿仍定期落库，重连时用「快照」事件能恢复已有内容。

**高频追问：** 多台服务器部署时还能用吗？
**追问回答：** 不能，内存广播跨不了进程。多实例时需要 Redis 发布订阅或类似方案，这也是未来上独立任务队列的原因之一。当前单进程部署没有这个问题。

## 39. 澄清对话的「就绪度」是怎么评估的？
两层软约束。AI 在回复里附带元信息：还有多少开放问题、是否建议可以开始生成；前端再结合聊了几轮、表单填得怎么样，给出「还缺关键信息」或「建议再聊聊」的提示。用户点生成时若就绪度不够，弹确认框「建议再澄清几个问题」，但不硬拦——用户坚持可以跳过。

**高频追问：** 这和生成前的硬拦截有什么区别？
**追问回答：** 硬拦截在后端：缺摘要就不让创建 PRD 任务，这是门槛。就绪度是前端软提示，帮用户做更好决策，不替代后端校验。软引导体验，硬拦截兜底。

## 40. 交付包导出包含什么？
打成一个 ZIP：三份 Markdown（PRD、接口文档、提示词），再加一份「清单文件」。清单里记各文档版本号、结构校验结果、谁依赖谁、有没有过期警告、什么时候生成的。方便整包交给开发团队，不是只导出一个裸文件。

**高频追问：** 为什么要单独做清单文件？
**追问回答：** 三份文档可能不同步（PRD 改了但接口文档没重生），清单让接手的人一眼看到依赖关系和过期状态，不用人工对版本。

## 41. 项目支持哪些入口模式？
除了标准的「填表 → 澄清 → 生成」全流程，还支持：已有 PRD 直接生成接口文档和提示词；已有提示词导入后做优化。不同入口跳过不同阶段，但下游的「后台任务 + 审查 + 结构校验」流程一致。还有行业模板加速填表。

**高频追问：** 导入 PRD 模式还需要澄清吗？
**追问回答：** 不需要，用户已有 PRD 就直接进审核页确认基线，然后生成下游文档。结构化摘要能从 PRD 反推就填，推不出就留空，看导入内容完整度。

## 42. 你怎么评估生成质量？
现在主要靠审查 Agent 的结构化结论 + 结构校验报告 + 人工过一遍，没有线上自动打分。运行汇总和版本附加信息会把每次审查结论和门禁分数存下来，刷新后仍能看到。若要补自动化，用几组固定需求定期回放，看章节齐不齐、JSON 能不能解析、审查通过率有没有掉。

**高频追问：** 最小可用的自动化回归怎么做？
**追问回答：** 三到五组固定表单和对话脚本，在 CI 里 mock 模型或用最便宜模型，断言章节标题、JSON 可解析、结构校验通过率趋势。后端已有结构校验、Skill 加载等单元测试打底。

## 43. 你认为最大的技术债是什么？
长对话仍要整包带聊天记录，请求体还是会胀，虽然有 Token 预算告警但还没有滚动摘要；任务草稿和方案快照两处存内容有冗余；缺少端到端集成测试；单机异步任务不能跨进程恢复。若只有一周，优先做对话滚动摘要压缩上下文，或把任务失败后的用户引导做得更明确。

**高频追问：** 只修一项选什么？
**追问回答：** 对话滚动摘要，从根上治上下文膨胀；快照怎么存、任务怎么跑是另一条线，可以并行排期。

## 44. 若做成对外 SaaS，最少还要补什么？
账号与租户隔离、文档版本与审计、用量计费、密钥托管、内容安全、长任务独立队列、每次调模型的链路追踪、多实例任务调度。现在有单机快照和任务续编，但还没有登录隔离和横向扩展，不能直接当多租户产品卖。

**高频追问：** 先做鉴权还是先做异步任务？
**追问回答：** 先鉴权和隔离，否则数据和算力会混用；异步队列第二批，但在鉴权之后。任务表结构已经像异步任务了，换执行层比从零设计容易。

## 45. 如果让你画架构图，你会画哪几层？
用户层：录入、聊天、文档审核、方案列表、生成进度条。应用层：前端 + 后端 API + 流式推送 + 任务调度 + 快照读写。Agent 层：写 PRD 的三角（写 / 审 / 改）和派生文档的两步（写 / 审）。知识与模型层：大模型、提示词、Skill 规范库。可观测层：Token 预算、分步追踪、运行汇总。数据流上：澄清走流式直连，生成走「创建任务 + 订阅进度」；实质动作触发快照落库。

**高频追问：** 最关键的一条数据流？
**追问回答：** 录入 → 澄清 → 摘要差异确认 → PRD 任务 → 基线确认 → 接口文档任务 → 提示词任务 → 交付包导出。每段生成都是：创建任务 → 后台跑 → 订阅流式进度 → 结束并汇总 → 版本入库。

## 46. 为什么把「对话」和「文档生成」拆成不同模块？
职责清楚：一块只管多轮聊天和消息格式；一块管 PRD、接口、提示词、规范注入、摘要同步；任务模块管生命周期和持久化。路由层只转发，业务不堆在路由文件里。以后若在聊天中途预览 PRD 大纲，加在文档服务里，而不是写在路由里。

**高频追问：** 澄清中途预览 PRD 大纲改哪？
**追问回答：** 文档服务加轻量预览接口，或对话服务调短提示；前端仍走流式，体验一致。当前没做，因为摘要差异确认已经覆盖了「生成前再看一眼」的需求。

## 47. 三种文档发给模型时，上下文怎么拼？
PRD 最复杂：系统角色说明 + 澄清对话 + 确认后的摘要和团队规范，分多条消息。接口文档把对话、PRD 正文、规范合成一条大用户消息。提示词套件相对简单：系统说明 + 一条大用户消息。三者共用同一套规范加载器，但拼法因输入来源不同而有差异。

**高频追问：** 能不能抽成完全统一的拼 prompt 函数？
**追问回答：** 公共部分可以抽（规范加载、格式约束、预算检查），但三种文档的输入源和上下文长度策略不同，硬拧成一条函数反而难维护。当前在文档服务里分函数写，共享加载器和预算检查。

## 48. 审查结果的 JSON 容错是怎么分级的？
PRD 审查三级：先从模型输出里抠 JSON → 失败则让模型专门修格式 → 再失败则让审查 Agent 重新出结果。接口文档和提示词审查两级：抠 JSON → 修格式，仍失败就返回一份「解析失败」的占位审查，不阻断交付。摘要同步也是三级，因为后面写 PRD 依赖这份 JSON。

**高频追问：** 为什么 PRD 审查比派生文档多一级「重生成」？
**追问回答：** PRD 审查结果决定是否触发改写 Agent，是整个流水线质量分叉点，容错要求最高。派生文档审查主要做展示和存档，解析失败时宁可给空问题列表也不挡交付。

## 49. 你最有说服力的一个技术决策是什么？
在「可控」和「能落地」之间，我坚持用结构化摘要 + 人工差异确认管住需求漂移，用写审分离的 Agent 管住文档质量，用后台生成任务把长任务和浏览器连接解耦，再用轻量快照和版本链把整条流水线的进度存住。部署仍然是一条命令跑后端，但用户刷新、列表续编、任务重连都不会丢进度。

**高频追问：** 你只是调 API？
**追问回答：** 难点在编排：多阶段状态机、任务状态机、结构化输出修复、规范注入与审查闭环、Token 预算、人机确认差异、版本过期检测——这是系统工程，不是单次问答。

## 50. 如果面试官问「这个项目和你没关系，只是调 API」，你怎么回应？
我会带一条完整链路讲清楚：用户刷新时任务怎么重连、摘要差异确认为什么要有、语义审查和结构校验为什么是两层、Token 预算为什么分对话类和生成类。这些都不是调一次聊天接口就完事的，而是围绕「模型输出不可控」，逐层加约束和工程化手段。最后补一句：项目迭代过好几轮，每一轮都是踩坑后的收敛，不是一开始就设计得这么完整。

**高频追问：** 用 30 秒介绍这个项目？
**追问回答：** AI 驱动的需求文档流水线：帮用户从模糊想法产出 PRD、接口文档和开发提示词。我负责前后端架构和核心链路，包括多 Agent 写审改、后台任务刷新可续、Skill 规范注入、Token 预算和版本追溯，目标是把不稳定的大模型输出收成可交付、可续编、可审计的文档包。

## 51. 澄清和文档生成的流式协议一样吗？
大框架一样：都是「一行一条 JSON 事件」，最后发结束标记。但事件类型有差异：澄清主要是「增量文字」和「完成（附带上下文占用）」；任务流还多「阶段切换」「审查结果」「全量快照（重连用）」「运行汇总」「出错（含 Token 超限）」。前端有两处解析逻辑，底层都是 fetch 读流、按行解析。

**高频追问：** 为什么任务重连首包是「快照」而不是从头重播每个字？
**追问回答：** 重播会让用户以为又在重新生成，体验差且耗时。快照立刻展示已有全文，只对**新产生**的内容做打字机，这才是「续看」而不是「重播」。

## 52. 前端进度条怎么知道任务当前在哪一步？
订阅任务流，收到「阶段切换」事件就更新进度条：PRD 是「起草 → 审查 → 改写 → 完成」，派生文档是「生成 → 审查 → 完成」。重连时「快照」里带当前阶段，进度条直接跳到对应步骤，不用等下一个实时事件。

**高频追问：** 「阶段」和「任务状态」有什么区别？
**追问回答：** 任务状态管整件事：等待中、进行中、已完成、失败、已取消。阶段是「进行中」内部的细进度。一个进行中的 PRD 任务可能依次经历起草、审查、改写三个阶段。

## 53. 为什么 PRD 优化后基线会自动失效？
确认基线时记录了 PRD 内容的指纹（hash）。用户手改或 AI 优化后内容变了，指纹对不上，说明「之前认可的那份 PRD」已经变了。此时仍可以查看旧接口文档，但会拦住新的下游生成，并提示「上游已过期」，防止基于过时 PRD 继续产出。

**高频追问：** 能不能优化 PRD 但不失效基线？
**追问回答：** 产品上不推荐，因为基线的意思就是「我确认这份 PRD 可以作准」。若允许静默失效，下游和 PRD 的矛盾用户感知不到。若只是改错别字，重新点一次确认基线即可，成本很低。

## 54. 数据库为什么选 SQLite 而不是 Postgres？
单机部署、个人或小团队使用，SQLite 零运维，一个文件随项目走，一条命令启动。方案快照、生成任务、文档版本都在同一个库里，备份就是复制数据库文件。以后要多实例或高并发，可以迁 Postgres，数据访问层已经做了大部分抽象。

**高频追问：** SQLite 写任务草稿会锁表吗？
**追问回答：** 草稿每 500 毫秒才写一次，已经降了频率；SQLite 开 WAL 模式后读写并发尚可。当前规模没问题，瓶颈会先出现在调模型而不是写库。

## 55. 如果规范库规模变大，Skill 方案怎么演进？
现在 Skill 适合规范少、整份注入的场景。规范多了可以分步走：一，Skill 内按章节拆文件，注册表声明优先级；二，在加载器里加语义检索，只挑和当前 PRD 最相关的段落注入，Skill 框架不变；三，独立检索中台，本项目通过 API 拉规范片段。关键是「注入点」和「运行汇总里记录用了哪些规范」不变，换的是「怎么选哪些规范塞进去」。

**高频追问：** 关键词检索和向量检索在这个项目里怎么选？
**追问回答：** 规范就几份、内容固定时，Skill 整份注入最简单；规范上百份、需要「找和这段 PRD 最像的 API 示例」时用向量检索。早期走关键词是因为库小，不是不知道向量检索更好。

# 观测链路实现提示词

点击此处可复制本篇提示词

观测链路的核心，是把分散在各 service 里的 LLM 调用收拢到**统一包装层**，在每次调用前后自动记录 `request_id`、当前 `step`、耗时与 Token 用量。实现上先定义 `request_id`、`step`、`run_summary` 的数据结构，再逐层替换 `get_llm()` 调用点，最后在 SSE 路由里汇总输出。**业务 prompt 和生成逻辑不动。**

## 使用场景

这份提示词用于在 harnessprd 项目 `backend/` 目录增加统一 LLM 观测（不改 `frontend/`，不建日志表，日志以 stdout 单行 JSON 输出，不接 Langfuse）。

**现状问题：** LLM 调用分散在 `conversation_service`、`prd_writer_agent`、`prd_review_agent`、`document_service` 等处，直接 `get_llm().ainvoke / astream`，出了错 mostly 只有 `logger.exception`。因此无法回答这些常见问题：

- 一次 PRD 生成到底调了几次模型？
- 哪一步 input 最大、哪一步最慢？
- 如何用同一个 ID 把分散的日志串起来查？

**改造后的调用链：**

```
HTTP Request
  → middleware 注入 request_id
  → API 路由
  → 业务 service
  → tracked_llm（绑定 step + 计时 + 记录 tokens）
  → RunMetrics 累计
  → SSE 末尾 emit run_summary
  → 结构化 JSON 日志（方便 grep / jq）
```

本篇只做后端观测，不改前端，不做 Token 预算拦截（见 02 篇）。

### 一、功能目标

在 harnessprd `backend/` 一步完成观测链路：

- 新增 `core/request_context.py`、`middleware/request_id.py`、`services/llm_metrics.py`
- 改造 `services/llm_factory.py`：提供 `get_tracked_llm(step)`，在 `ainvoke` / `astream` 外包一层观测
- 所有 LLM 调用点改用 tracked 版本；`step` 必须使用固定枚举，禁止随手写字符串
- `api/conversation.py`（及 Job 流 `api/jobs.py`）在 SSE `[DONE]` 前 emit `run_summary`
- 结构化 JSON 日志：逐步打 `event=llm_step`，整趟结束打 `event=run_summary`
- 更新 `.env.example`

### 三、step 枚举

`step` 表示「这一步在干什么」，全文统一用枚举，**禁止**各写各的字符串：

```python
class LlmStep(str, Enum):
    CHAT_START = "chat_start"              # 澄清：第一轮
    CHAT_CONTINUE = "chat_continue"        # 澄清：继续聊
    SUMMARY_SYNC = "summary_sync"          # 摘要：对话同步回 JSON
    JSON_REPAIR = "json_repair"            # 辅助：修 JSON 格式
    JSON_REGENERATE = "json_regenerate"    # 辅助：重生成 JSON
    PRD_WRITER = "prd_writer"              # PRD：起草
    PRD_REVIEW = "prd_review"              # PRD：审查
    PRD_REWRITE = "prd_rewrite"            # PRD：按意见改稿
    API_DOCS_GENERATE = "api_docs_generate"
    PROMPTS_GENERATE = "prompts_generate"
    DOCUMENT_OPTIMIZE = "document_optimize"
```

**为什么要单独记 `json_repair` / `json_regenerate`：** 不要并进 `prd_review`，否则排查「JSON 容错链」时看不清到底哪一步在修格式。

### 四、数据结构

#### StepMetrics（单次 LLM 调用）

| 字段 | 类型 | 说明 |
|------|------|------|
| step | string | 步骤名，见第三节枚举 |
| model | string | 实际使用的模型名 |
| input_tokens | int | 输入 Token 数；流式无 usage 时为 0 |
| output_tokens | int | 输出 Token 数；流式无 usage 时为 0 |
| duration_ms | int |  wall time，本次调用耗时（毫秒） |
| status | string | `ok` 成功 / `error` 失败 |
| error | string | 失败时简短信息；成功为空 |

#### RunMetrics（一次 API 流程汇总）

| 字段 | 类型 | 说明 |
|------|------|------|
| request_id | string | 请求唯一标识，来自 middleware |
| run_type | string | 流程类型标签，见第九节对照表 |
| total_input_tokens | int | 各 step 的 input 之和 |
| total_output_tokens | int | 各 step 的 output 之和 |
| total_duration_ms | int | 从 run 开始到结束的总耗时 |
| llm_call_count | int | 一共调了几次模型 |
| steps | StepMetrics[] | 各 step 明细，按时间顺序 |
| revision_applied | bool | PRD 是否触发了自动改写（可选） |

PRD 流程的 `revision_applied`：优先读业务 `done` 事件里的字段；也可根据 steps 中是否出现 `prd_rewrite` 推断。

#### SSE run_summary 事件

```json
{
  "type": "run_summary",
  "request_id": "req_xxx",
  "run_type": "generate_prd_from_summary",
  "total_duration_ms": 47000,
  "total_input_tokens": 28400,
  "total_output_tokens": 6200,
  "llm_call_count": 3,
  "revision_applied": true,
  "steps": [
    {"step": "prd_writer", "input_tokens": 6200, "output_tokens": 3800, "duration_ms": 18000},
    {"step": "prd_review", "input_tokens": 15200, "output_tokens": 420, "duration_ms": 9000},
    {"step": "prd_rewrite", "input_tokens": 7000, "output_tokens": 1980, "duration_ms": 20000}
  ]
}
```

`steps` 在 run_summary 里可只带摘要字段；完整细节走 logger 单行 JSON。

### 五、request_id 中间件

作用：为每次 HTTP 请求分配唯一 `request_id`，便于日志串联与排查。

在 `main.py` 注册 middleware：

- **入站：** 若请求头没有 `X-Request-ID`，生成 `req_{uuid4().hex[:12]}`
- **写入上下文：** 存到 `request_context.request_id`，后续 LLM 日志都能带上
- **出站：** 响应头 `X-Request-ID` 原样回传，前端失败时可复制给用户排查

可选：前端 session 请求带 `X-Session-ID`，middleware 一并写入 context，日志里打出。

### 六、LLM 包装层

在 factory 里新建 `TrackedChatModel`（或返回 proxy），**对业务透明**：业务仍调 `ainvoke` / `astream`，包装层自动记录 metrics。

```python
async def ainvoke(self, messages, *, step: str, **kwargs):
    started = time.perf_counter()
    try:
        response = await self._llm.ainvoke(messages, **kwargs)
        duration_ms = int((time.perf_counter() - started) * 1000)
        usage = getattr(response, "usage_metadata", None) or {}
        record = build_step_metrics(step, usage, duration_ms, "ok")
        RunMetricsCollector.current().add_step(record)
        log_llm_step({**record, "request_id": get_request_id()})
        return response
    except Exception as e:
        ...
```

**流式 `astream`：** 等同理，在**流结束后**再取 usage。DeepSeek 等流式场景常没有 `usage_metadata`，此时 `duration_ms` 仍必填，tokens 记 0 并打 debug 日志，**不视为失败**。

**没有 active run 时**（忘记调用 `RunMetricsCollector.start`）：仍打 `llm_step` 日志，但 skip `add_step`，避免 crash。

**与 02 Token 预算的关系：** 包装层已持有 `model` 名（来自 `settings.default_llm_model`），02 会在真正调模型前做 budget 检查。本篇不改 budget 逻辑。

Token 用量从 response 的 `usage_metadata` 读取（LangChain 标准字段）。原 `get_llm()` 可内部转调 `get_tracked_llm()`，减少 diff。

### 七、RunMetrics 生命周期

一次「用户触发的流程」（如生成 PRD）对应一次 RunMetrics：开始时 `start`，结束时 `finish` 并推送汇总。

现有 `conversation.py` 里，多数流式路由走 `_make_sse_generator`，`start-stream` / `continue-stream` 为手写 generator。**两类都要**包 RunMetrics：优先改造 `_make_sse_generator`，在 `[DONE]` 前统一 emit `run_summary`；不要只改部分路由。

每个 SSE 路由在进入 generator 时 `RunMetricsCollector.start(run_type=...)`，在 `finally` 里 `finish()` 并 yield run_summary：

```python
run = RunMetricsCollector.start(run_type="generate_prd_from_summary")
try:
    async for event in document_service.generate_prd_from_summary_stream(...):
        yield sse(event)
finally:
    summary = run.finish()
    yield sse({"type": "run_summary", **summary.to_dict()})
    log_run_summary(summary)
```

- **非 SSE 接口**（如 `sync-summary-from-conversation`）：handler 里同样 start/finish，响应 body 可选增加 `run_summary`
- **出错时：** SSE error 必须带 `request_id`，例如：`{"type":"error","message":"...","request_id":"req_xxx"}`

### 八、结构化日志

每条 LLM 调用打**一行 JSON**，便于运维 grep：

```json
{
  "event": "llm_step",
  "request_id": "req_abc",
  "session_id": "uuid-or-null",
  "step": "prd_review",
  "model": "deepseek-chat",
  "input_tokens": 15200,
  "output_tokens": 420,
  "duration_ms": 9100,
  "status": "ok"
}
```

整趟 run 结束再打一行 `event: run_summary`。排查示例：

```bash
grep '"event":"llm_step"' app.log | jq 'select(.request_id=="req_abc")'
```

### 九、接入位置

#### LLM 调用替换（各 service 内）

| 文件 | 使用的 step |
|------|-------------|
| `conversation_service.py` | `chat_start` / `chat_continue` |
| `prd_writer_agent.py` | `prd_writer` / `prd_rewrite` |
| `prd_review_agent.py` | `prd_review`；repair / regenerate 分别用 `json_repair` / `json_regenerate` |
| `document_service.py` | `summary_sync`、`api_docs_generate`、`prompts_generate`、`document_optimize` |

必须全部替换，漏一处观测就不完整。

#### SSE / JSON 路由（`api/conversation.py`）

在每个流式路由的 generator 外包装 RunMetrics；`run_type` 是「这趟流程叫什么」，与路由对应：

| API | run_type |
|-----|----------|
| POST `/api/conversation/start-stream` | `chat_start` |
| POST `/api/conversation/continue-stream` | `chat_continue` |
| POST `/api/conversation/sync-summary-from-conversation` | `summary_sync` |
| POST `/api/conversation/generate-prd-stream` | `generate_prd` |
| POST `/api/conversation/generate-prd-from-summary-stream` | `generate_prd_from_summary` |
| POST `/api/conversation/generate-api-docs-stream` | `generate_api_docs` |
| POST `/api/conversation/generate-prompts-stream` | `generate_prompts` |
| POST `/api/conversation/optimize-document-stream` | `optimize_document` |

业务 service 的 `generate_*_stream` **只负责** yield 业务事件（phase、text_delta 等），**不要**重复 emit run_summary；汇总在 API 层（或 Job 层）统一完成。

### 十、配置项

`.env.example` 补充：

```env
LOG_LLM_METRICS=true
LOG_LEVEL=INFO
```

`LOG_LLM_METRICS=false` 时：**仍** emit SSE `run_summary`（前端还能看到汇总），只是不打逐步 `llm_step` 日志。

### 十一、验收标准

- 任意一次 PRD 生成，日志中同一 `request_id` 下有多条 `llm_step`，含 `prd_writer`、`prd_review`；若自动改写则含 `prd_rewrite`
- SSE 在 `[DONE]` 前有 `type: run_summary`，字段含 `request_id`、`steps`、`total_duration_ms`
- 响应头含 `X-Request-ID`
- `prd_review` 的 `input_tokens`、`duration_ms` 可在日志或 run_summary.steps 中读出
- 业务 prompt 与生成结果与改前一致（**观测不改变 LLM 行为**）
- LLM 失败时 step 记录 `status: error`，SSE 仍发 error 事件且带 `request_id`
- `json_repair` 触发时单独出现在 steps 中，不并入 `prd_review`
- 经 `_make_sse_generator` 的流式路由与手写 generator **均** emit `run_summary`

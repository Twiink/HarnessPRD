# 输入合并：结构化表单与澄清对话

用户向 harnessprd 描述一个产品需求，可能走两条路。一条是直接填表：产品名称、目标用户、MVP 功能、平台类型……所有信息以结构化字段的形式交出来。另一条是自由对话：跟 AI 产品经理聊，边聊边明确，细节在来回对话里逐渐清晰。

实际使用时，用户往往两条路都走：先填表交代大致轮廓，再通过澄清对话补充细节。PRD 生成时，这两份输入都要合并进来，不能丢掉任何一侧的信息。

## 两路输入，一条流水线

结构化表单是以 JSON 形式存储的 `requirements_summary`，字段明确，机器可读，可以直接拿来做就绪度检查。每个字段的语义是固定的，比如 `product_name` 一定是产品名称，`mvp_features` 一定是一个数组。

澄清对话是一串 `messages`，每条消息有 `role` 和 `content`。它的信息密度不均匀：同一条消息可能既确认了某个功能，又提出了新的约束，还顺带推翻了表单里的某个字段。自然语言的灵活性正是它的价值，也是它难以直接用的地方。

两者不是替代关系，而是互补。结构化表单确保关键字段不缺失，澄清对话把字段里无法容纳的细节补进来。

| 输入来源 | 格式 | 主要价值 |
|------|------|------|
| 结构化表单 | JSON (`requirements_summary`) | 字段明确、可校验、硬性阻断不合格请求 |
| 澄清对话 | 消息列表 (`messages`) | 补充细节、修正字段、处理歧义 |

## 生成 PRD 之前

用户点击「生成 PRD」时，系统按顺序处理三件事：先判断能不能生成，再把对话里的变更写回 JSON 摘要，最后把更新后的摘要和对话原文一起组装进 Writer 的 prompt。

### 生成前门禁：表单校验与澄清收口感知

表单校验是硬约束。前端字段校验和后端 delivery guards 会在生成请求发出前拦截关键字段缺失的情况，用户得到的是「这里必须填」的阻断提示。

澄清收口感知是软约束，负责在信息足够或可能不足时给用户信号，但控制权始终在用户手里。澄清对话没有内置的终止条件——用户可以随时停下来触发生成，也可以聊二十条消息再开始。系统不会在某个时刻叫停，但它有两种方式给出「差不多了」的信号。

**第一种：提示词指令。** 两个对话场景的 System Prompt 里都有一条让模型主动感知收口时机的指令：

```python
# harnessprd/backend/services/prompts.py

SYSTEM_PROMPT = """...
# 自由对话阶段：信息足够时主动建议进入生成
6. 当信息足够完整时，主动提议生成 PRD
...
"""

CLARIFICATION_SYSTEM_PROMPT = """...
# 结构化澄清阶段：提示用户可以结束而不是继续追问
4. 在信息已经足够时，只需明确提示用户"如果没有更多补充，可以结束澄清"
...
"""
```

模型会在回复里说出「需求看起来已经比较完整了，如果没有补充可以开始生成了」。用户可以接受这个建议，也可以说「再聊一个问题」继续往下聊。

**第二种：前端生成前提醒。** 当用户点击「生成 PRD」时，前端会检查是否还有尚未补充完整的澄清问题。如果有，会弹出一个提醒，询问是否确认在当前状态下生成。用户选择确认，生成照常触发；选择取消，回到对话继续补充。

这同样是软约束——系统不阻断，只提醒。区别在于它发生在生成的入口，而不是对话过程中，给用户一个最后的检查机会。

| | 澄清收口感知 | 表单校验 |
|---|---|---|
| 作用时机 | 对话中 + 生成入口 | 生成请求发出前 |
| 约束性质 | 软约束，建议或提醒，用户自决 | 硬约束，不满足条件直接阻断 |
| 实现方式 | System Prompt 指令 + 前端提醒弹窗 | 前端字段校验 + 后端 delivery guards |
| 用户体验 | 得到一个「是否继续」的推进信号 | 得到一个「这里必须填」的阻断提示 |

两者各司其职。表单校验负责拦截没有意义的生成请求，澄清收口感知负责推进或提醒，但不替用户做决定。

### 摘要回填：对话写进 requirements_summary

通过门禁之后，生成前先调 `syncSummaryFromConversation`，让模型把对话里明确的补充、修正写回 `requirements_summary`，再把这个 JSON 作为 Job payload 里的主输入。

```python
# harnessprd/backend/services/document_service.py

async def sync_summary_from_conversation(
    self,
    requirements_summary: Dict[str, Any],
    conversation_messages: List[Dict[str, str]],
) -> Dict[str, Any]:
    # temperature=0，让摘要更新结果尽量确定，不受随机性影响
    llm = get_tracked_llm(LlmStep.SUMMARY_SYNC.value, temperature=0)
    lc_messages = [
        SystemMessage(
            content=(
                "你是一位严谨的需求分析师。"
                "你的任务是根据澄清对话更新结构化需求摘要，并只返回 JSON。"
            )
        ),
        # 把当前摘要和对话历史一起传入，由 prompt 函数组装成完整指令
        HumanMessage(content=_build_summary_sync_prompt(requirements_summary, conversation_messages)),
    ]
    # 调用模型更新摘要，同样有三级容错链（extract → repair → regenerate）
    response = await llm.ainvoke(lc_messages)
    updated_summary = _extract_json_object(str(response.content).strip())
    return {"requirements_summary": updated_summary, "status": "completed"}
```

回填 prompt 里明确要求「只在对话中出现了明确补充、修正或澄清时才更新字段」，不要编造，不确定的内容保留原值。这避免了模型过度推断，用对话里的只言片语去改掉表单里已经明确的字段。

### 对话注入：原文附进 prompt

摘要对齐之后，再把澄清对话转成可读文本，附在 prompt 里，让模型在生成 PRD 时同时参考更新后的摘要和对话原文。

```python
# harnessprd/backend/services/document_service.py

def _format_conversation_context(conversation_messages: List[Dict[str, str]]) -> str:
    lines: List[str] = []
    for msg in conversation_messages:
        role = msg.get("role", "")
        # 跳过 system 消息，只保留用户和 AI 的对话内容
        if role == "system":
            continue
        speaker = "AI" if role in ("assistant", "ai") else "用户"
        content = str(msg.get("content", "")).strip()
        if content:
            lines.append(f"{speaker}: {content}")
    return "\n".join(lines)
```

过滤掉 system 消息，把用户和 AI 的对话整理成对话体文本，拼进 prompt 里作为补充上下文。

回填和注入通常连着走：先用对话更新结构化字段，再把完整对话原文注入 prompt，保留对话里的语气和细节。两者叠加，模型拿到的上下文比单独用表单或单独用对话都更完整。

## Writer 里两份输入怎么排

PRD Writer 收到的是一组 LangChain 消息，按下面顺序组装。

**第一步，SystemMessage。** 定义角色，并说明存在补充对话时要优先采用对话里已澄清的内容。

**第二步，HumanMessage #1（有澄清对话时）。** 把完整澄清对话整理成可读文本，单独作为一条消息注入。模型先读到用户和 AI 来回确认过的内容。

**第三步，HumanMessage #2。** 生成任务的主体，把代码里的任务要求、结构化摘要、Skill 规范拼成一条 prompt：

```python
# harnessprd/backend/services/document_service.py

lc_messages = [
    SystemMessage(
        content=(
            "你是一位资深产品经理和技术写作者。"
            "请把结构化需求摘要整理成简洁、结构化、工程可执行的 PRD。"
            "如果存在补充对话，请优先采用对话中已澄清的内容。"
        )
    )
]

if clarification_context:
    lc_messages.append(
        HumanMessage(
            content=(
                "以下是围绕该需求的澄清对话，请将其中明确的信息视为对结构化需求摘要的补充或修正：\n\n"
                f"{clarification_context}"
            )
        )
    )

lc_messages.append(HumanMessage(content=_build_prd_from_summary_prompt(requirements_summary)))
```

这条 HumanMessage 的内部顺序是：

1. 硬编码任务要求（中文 Markdown、MVP 表格、不编造等）
2. 结构化需求摘要 JSON
3. Skill 写作规则（`reference`）
4. Skill 生成说明（`instructions`）
5. Skill 输出模板（`template`）

```python
# harnessprd/backend/services/document_service.py

def _build_prd_from_summary_prompt(requirements_summary: Dict[str, Any]) -> str:
    sections = compose_prompt_sections(load_skill_bundle("prd"))
    writing_rules = sections.get("reference", "")
    summary_json = json.dumps(requirements_summary, ensure_ascii=False, indent=2)
    prompt_parts = [
        "请基于以下结构化需求摘要生成一份专业、简洁、工程可执行的 PRD。",
        # ... 任务要求 ...
        "结构化需求摘要：",
        summary_json,
    ]
    if writing_rules:
        prompt_parts.extend(["", "补充写作规则：", writing_rules])
    # instructions、template 等 Skill 内容在后续追加
    return "\n".join(prompt_parts)
```

![PRD 生成前的输入合并顺序](https://pic.niumianoffer.com/images/fs/03-01-input-merge-order.png)

**优先级怎么理解。** 上面是阅读顺序，不是「谁更重要」的简单对应。事实层面：对话与摘要冲突时，以对话为准——System 和 HumanMessage #1 都写了这条规则，且生成前摘要已经 sync 过，多数字段已对齐，注入对话原文是为了保留细节并在遗漏时兜底。写作层面：PRD 的章节结构和落笔依据来自 HumanMessage #2 里的摘要 JSON 和 Skill 模板，任务指令也是「基于以下结构化需求摘要生成 PRD」。可以记成：先读对话建立上下文，再按摘要 + Skill 写文档；写的过程中，对话里已明确的信息覆盖摘要里的旧值。

合并之后，模型拿到的是一份既有结构、又有上下文的完整输入，比单纯对话或单纯表单都更适合生成工程可执行的 PRD。

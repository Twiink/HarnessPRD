# 版本追溯：文档依赖与过期检测

harnessprd 生成的三份文档之间有明确的依赖关系：接口文档依赖 PRD，提示词套件依赖 PRD 和接口文档。这意味着 PRD 改了之后，旧版接口文档就可能过期了。如果没有版本追踪，就没有办法知道这件事。

这篇文章讲的是 harnessprd 如何设计版本链，以及如何通过元数据实现跨文档的依赖追踪。

## 数据模型：槽位与版本链

存储层分两张表。`documents` 表是文档槽位，每个 session 下每种文档类型只有一条记录，指向当前版本：

```
documents
├── session_id
├── doc_type        ("prd" | "api-docs" | "prompts")
└── current_version_id  ← 指向 document_versions 的外键
```

`document_versions` 表存所有历史版本，每个版本有指向父版本的链接：

```
document_versions
├── id
├── document_id
├── version_no          (1, 2, 3, ...)
├── content             (完整文档内容)
├── source_kind         (生成来源：见下文)
├── parent_version_id   ← 指向上一个版本
└── metadata_json       (review 结果、run_summary、derived_from 等)
```

`source_kind` 记录这个版本是怎么来的：

```python
# harnessprd/backend/services/document_version_service.py

class VersionSourceKind(str, Enum):
    GENERATE    = "generate"    # 完整生成 Job 完成
    OPTIMIZE    = "optimize"    # 优化 Job 完成
    AUTO_SAVE   = "auto_save"   # 前端 debounce 自动保存
    CHECKPOINT  = "checkpoint"  # 用户手动保存快照
    RESTORE     = "restore"     # 从历史版本恢复
    IMPORT      = "import"      # 跨文档引用时导入
```

这个字段让你在看版本历史时，能看出每一个版本是怎么产生的：哪些是模型生成的，哪些是手动保存的，哪些是恢复的。

## derived_from：记录生成时的上游版本

接口文档和提示词套件生成完成后，Job 层会把当时的上游版本号写进生成来源字段（`derived_from`）：

```python
# harnessprd/backend/services/job_runner.py

def _build_derived_from(
    session_id: str,
    artifact: str,
    payload: Dict[str, Any],
) -> Dict[str, Any]:
    derived: Dict[str, Any] = {}
    # 记录当时的 PRD 版本号，用于后续过期检测
    prd_current = get_current_version(session_id, "prd")
    if prd_current:
        derived["prd_version_id"] = prd_current["id"]
        derived["prd_version_no"] = prd_current["version_no"]
    if artifact == "prompts":
        api_docs_content = (payload.get("api_docs_content") or "").strip()
        if not api_docs_content:
            # payload 没带接口文档，跳过版本记录
            derived["api_docs_skipped"] = True
        else:
            api_current = get_current_version(session_id, "api-docs")
            if api_current:
                derived["api_docs_version_id"] = api_current["id"]
                derived["api_docs_version_no"] = api_current["version_no"]
    return derived
```

这份元数据随版本一起写进 `metadata_json`，大致如下：

```json
{
  "derived_from": {
    "prd_version_id": "uuid-of-prd-v2",
    "prd_version_no": 2
  },
  "review": { "passed": true, "summary": "...", "issues": [] },
  "run_summary": { "total_input_tokens": 9400, ... }
}
```

有了生成来源字段（`derived_from`），就能回答"这份接口文档是基于哪个版本的 PRD 生成的"。如果 PRD 当前版本号是 3，而接口文档记录的 PRD 版本号（`derived_from.prd_version_no`）是 2，说明接口文档基于旧版 PRD，可能存在过期风险。

## 版本升降的逻辑

生成 Job 完成时，版本更新有两条路，取决于这是首次生成还是再次生成：

```python
# harnessprd/backend/services/document_version_service.py

def sync_from_job(session_id, artifact, content, ...) -> None:
    current = get_current_version(session_id, doc_type)
    if current is None:
        # 第一次生成：创建 v1
        create_initial_version(...)
    elif source_kind == VersionSourceKind.GENERATE:
        if _document_has_generate_version(session_id, doc_type):
            # 已有过 generate 版本：升新版，旧版进历史
            append_generated_version(...)
        else:
            # 只有 auto_save 版本：覆盖 current，不升版本号
            update_current_content(...)
```

这个判断解决了一个实际问题：流式生成过程中，前端会 debounce 把草稿定期写成 `auto_save` 版本。如果 Job 最终完成时总是 append 出一个新版本，就会产生很多"生成中" vs "生成完成"的重复版本。现在的逻辑是：如果 current 只是 auto_save 状态，Job 完成直接覆盖它；只有当已经存在过一次完整的 `generate` 版本，下次再生成才升新版本号。

## 恢复操作：新版本而不是回滚

用户把历史版本恢复为 current，不是直接修改 `current_version_id` 指针，而是**创建一个新版本**，内容来自历史，`source_kind` 为 `restore`：

```python
# harnessprd/backend/services/document_version_service.py

def restore_version(session_id, doc_type, version_id) -> Dict[str, Any]:
    # 查找目标版本，验证它属于当前文档
    source_content = (source_row["content"] or "").strip()
    meta = {
        "restored_from_version_id": source_row["id"],
        "restored_from_version_no": source_row["version_no"],
    }
    # 插入新版本，内容=历史版本，parent=当前版本
    conn.execute("""
        INSERT INTO document_versions (...)
        VALUES (?, ?, ?, ?, ?, NULL, ?, ?, ?)
    """, (new_version_id, doc["id"], next_no, source_content, VersionSourceKind.RESTORE.value, current_id, ...))
    conn.execute("UPDATE documents SET current_version_id = ? ...", (new_version_id, ...))
```

这样做的好处是历史链完整，"恢复到 v2" 这个操作本身成为了版本历史的一部分（记为 v4，source_kind=restore，内容=v2 的内容）。如果恢复之后发现不对，还可以再恢复到 v3，因为 v3 没有被删掉，只是不再是 current 了。

## content_preview：版本列表的可读性

版本列表页不需要展示全文，只需要让用户能大致判断"这个版本写的是什么"。`content_preview` 取内容前 200 个字符，去掉多余空白：

```python
# harnessprd/backend/services/document_version_service.py

CONTENT_PREVIEW_LEN = 200

def _build_preview(content: str) -> str:
    # 合并多余空白，确保预览是单行连续文本
    text = re.sub(r"\s+", " ", content or "").strip()
    if len(text) <= CONTENT_PREVIEW_LEN:
        return text
    return text[:CONTENT_PREVIEW_LEN] + "..."
```

版本列表 API 返回时带上 `content_preview`，不带完整内容。用户点进去某个版本才加载全文，避免一次性把所有历史版本的全文返回给前端。

## 版本追踪的完整图景

一次完整的生成流程在版本层面的样子：

```
PRD v1 (generate)
  └─ 用户手动保存
PRD v2 (checkpoint)  ← 用户把这个版本确认为基线
  │
  ├─ 接口文档 v1 (generate)
  │    derived_from: { prd_version_no: 2 }
  │
  └─ 提示词 v1 (generate)
       derived_from: { prd_version_no: 2, api_docs_version_no: 1 }

（后来 PRD 又生成了一次）
PRD v3 (generate)
  ← 此时接口文档 v1 的 derived_from.prd_version_no=2 < 当前 PRD version_no=3
  ← 可以推断接口文档已过期，提示用户重新生成
```

从 `derived_from.prd_version_no` 和当前 PRD 的 `version_no` 之间的差，就能判断下游文档是否过期。这个判断不需要读文档内容，只需要比较两个版本号，开销极小。

## 过期检测的前端实现

过期判断的实际逻辑在前端的 `staleArtifact.ts` 里：

```typescript
// harnessprd/frontend/src/utils/staleArtifact.ts

export function buildStaleWarnings(params: {
  docType: 'api-docs' | 'prompts';
  derivedFrom?: DerivedFrom | null;
  prdCurrentVersionNo: number | null;
  apiDocsCurrentVersionNo?: number | null;
  onRegenerate?: () => void;
}): StaleWarning[] {
  const { derivedFrom, prdCurrentVersionNo, apiDocsCurrentVersionNo, docType, onRegenerate } = params;
  if (!derivedFrom) return [];

  const warnings: StaleWarning[] = [];

  // 主检查：接口文档或提示词依赖的 PRD 版本号 < 当前 PRD 版本号
  if (
    prdCurrentVersionNo != null &&
    derivedFrom.prd_version_no != null &&
    derivedFrom.prd_version_no < prdCurrentVersionNo
  ) {
    const label = docType === 'api-docs' ? '接口文档' : '提示词';
    warnings.push({
      message: `PRD 已更新至 v${prdCurrentVersionNo}，当前${label}基于 v${derivedFrom.prd_version_no}。建议重新生成或手动核对。`,
      actionLabel: docType === 'api-docs' ? '重新生成接口文档' : '重新生成提示词',
      onAction: onRegenerate,
    });
  }

  // 提示词的额外检查：接口文档版本是否也过期
  if (
    docType === 'prompts' &&
    !derivedFrom.api_docs_skipped &&
    apiDocsCurrentVersionNo != null &&
    derivedFrom.api_docs_version_no != null &&
    derivedFrom.api_docs_version_no < apiDocsCurrentVersionNo
  ) {
    warnings.push({
      message: `接口文档已更新至 v${apiDocsCurrentVersionNo}，当前提示词基于 v${derivedFrom.api_docs_version_no}。建议重新生成或手动核对。`,
      actionLabel: '重新生成提示词',
      onAction: onRegenerate,
    });
  }

  return warnings;
}
```

函数只做简单的版本号比较，返回 `StaleWarning[]` 数组，每条警告包含提示文本、操作按钮文案和触发回调。

PRD 不参与过期检测——它是上游，没有比它更上游的文档能让它过期。接口文档只检查 PRD 版本；提示词同时检查 PRD 和接口文档版本，接口文档缺席标志（`api_docs_skipped`）为 `true` 时跳过接口文档版本比较（说明当时生成提示词时没有接口文档）。

## 过期提示的 UI 呈现

文档版本审阅组件（`DocumentReviewWithVersions`）在渲染文档时，会先异步拉取上游文档的当前版本号，再调 `buildStaleWarnings()` 得出警告列表：

```typescript
// harnessprd/frontend/src/components/DocumentReviewWithVersions.tsx

// 拉取当前 PRD 版本号，供过期比较使用
useEffect(() => {
  if (!sessionId || docType === 'prd') return;
  void fetchVersionList(sessionId, 'prd').then((result) => {
    setPrdCurrentVersionNo(resolveCurrentVersionNo(result));
  });
}, [sessionId, docType, versions.currentVersionNo]);

// 计算过期警告，输入变化时重新计算
const staleWarnings = useMemo(() => {
  if (docType === 'prd') return [];
  return buildStaleWarnings({
    docType,
    // 从当前版本的元数据里读取 derived_from
    derivedFrom: versions.activeDetail?.metadata?.derived_from,
    prdCurrentVersionNo,
    apiDocsCurrentVersionNo,
    onRegenerate: onRegenerateStale,
  });
}, [docType, versions.activeDetail?.metadata?.derived_from, prdCurrentVersionNo, ...]);
```

警告由过期提示横幅组件（`StaleArtifactBanner`）渲染，显示在文档内容的顶部：

```tsx
// harnessprd/frontend/src/components/StaleArtifactBanner.tsx

export default function StaleArtifactBanner({ warnings }: StaleArtifactBannerProps) {
  if (!warnings.length) return null;
  return (
    <div className="mb-4 space-y-2">
      {warnings.map((warning, index) => (
        // 琥珀色警告条，带操作按钮
        <div key={...} className="border border-amber-300 bg-amber-50 px-4 py-3 text-sm ...">
          <p>⚠ {warning.message}</p>
          {warning.actionLabel && warning.onAction && (
            // 点击直接触发重新生成
            <button onClick={warning.onAction}>{warning.actionLabel}</button>
          )}
        </div>
      ))}
    </div>
  );
}
```

效果是：用户打开接口文档页面，如果 PRD 在接口文档生成之后又更新了，文档顶部会出现一条琥珀色警告条，提示"PRD 已更新至 v3，当前接口文档基于 v2，建议重新生成或手动核对"，同时提供"重新生成接口文档"按钮。

## 基线确认与 optimize 的版本边界

版本追踪还有一个关键状态：**PRD 基线确认**（`prdBaselineConfirmed`）。接口文档和提示词的生成不能在 PRD 刚生成时就触发，必须等用户明确点击"确认基线"——确认这份 PRD 是后续生成的依据：

```typescript
// harnessprd/frontend/src/AppV2.tsx

const handleConfirmBaseline = useCallback(async () => {
  // 记录确认时刻的版本号和内容哈希
  const list = await fetchVersionList(sessionId, 'prd');
  const hash = await shortContentHash(prdContent);
  setPrdBaselineConfirmed(true);
  setPrdBaselineVersionId(list.current_version_id);
  setPrdBaselineVersionNo(resolveCurrentVersionNo(list));
  setPrdBaselineContentHash(hash);
}, [sessionId, prdContent]);
```

基线确认后，如果 PRD 内容被修改（内容哈希变化），系统会自动将基线置为无效，接口文档和提示词的生成入口随即被锁住，直到用户再次确认基线。

对已有文档做优化修订（optimize 操作）同样会让基线失效——optimize PRD 完成时，会把基线确认状态清掉。这保证了一个不变式：**接口文档和提示词，始终只能基于用户显式确认的 PRD 版本生成**，不会静默地基于一个中间状态的草稿。

optimize 生成的版本 `source_kind` 为 `"optimize"`，和 `"generate"` 版本一样进入版本历史，在列表里用"优化"标签区别显示。过期检测只比较版本号，不区分来源——PRD 被 optimize 了一次，版本号从 2 升到 3，接口文档同样会被标记为过期。

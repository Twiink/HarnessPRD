# 双层门禁：前置条件与结构校验

文档生成涉及三个不同的时机和三种不同的检查。**生成之前**：这个请求有没有触发的资格？**生成期间**：内容是否达到语义质量要求？**生成之后**：产出是否满足基本的结构规范？三者解决的是不同的问题，实现方式截然不同。

这篇文章重点讲两层门禁：生成前的业务前置检查（交付守卫），以及生成后的结构性校验（质量门禁）。生成期间的语义审查由 Review Agent 负责，它会给出结构化的审查结果（`review` 字段）并写入版本元数据——这在"多 Agent 流水线"里已有详述，这里只说它与质量门禁的分工关系。

## 第一层：交付守卫

交付守卫在 Job 创建时触发，失败就直接返回 400 错误，连 Job 都不会创建。逻辑在 `delivery_guards.py` 的 `assert_can_create_job()` 里：

```python
# harnessprd/backend/services/delivery_guards.py

def assert_can_create_job(session_data, artifact, payload=None) -> None:
    payload = payload or {}

    if artifact == "prd":
        # PRD 生成必须有结构化需求摘要
        summary = payload.get("requirements_summary") or _summary_from_session(session_data)
        if not summary:
            raise HTTPException(status_code=400, detail="缺少结构化需求摘要")
        return

    if artifact in ("api-docs", "prompts"):
        # 接口文档和提示词套件必须先完成 PRD 基线确认
        if not session_data.get("prdBaselineConfirmed"):
            raise HTTPException(status_code=400, detail="请先确认需求基线")
        prd = (session_data.get("prdContent") or "").strip()
        if not prd:
            raise HTTPException(status_code=400, detail="PRD 内容为空")
        return

    if artifact.startswith("optimize-"):
        return  # 优化类操作无前置依赖
```

这里检查的是**业务前置条件**。PRD 生成需要结构化摘要，而不是让用户把空表单提交上来浪费一次 LLM 调用；接口文档和提示词套件依赖已确认的 PRD，没有 PRD 就没有上游输入，生成出来的东西没有意义。

基线确认标志（`prdBaselineConfirmed`）是一个显式的用户操作，用户在确认 PRD 内容后手动点击"确认基线"，这个字段才会变为 true。它比"PRD 内容不为空"更强：内容存在，但用户还没明确说这份 PRD 可以作为后续生成的依据，不应该放行。

## 第二层：质量门禁

质量门禁在 Job 结束后（finally 块）触发，调 `run_quality_gate()` 对生成内容做结构性校验。这一层用的是确定性正则规则，完全不调 LLM，成本低，结果稳定：

```python
# harnessprd/backend/services/quality_gate.py

def run_quality_gate(doc_type, content, context=None) -> Dict[str, Any]:
    # 清理空白，得到干净的文本内容
    text = (content or "").strip()
    if doc_type == "prd":
        checks = _run_prd_checks(text)
    elif doc_type == "api-docs":
        checks = _run_api_docs_checks(text)
    elif doc_type == "prompts":
        checks = _run_prompts_checks(text, context)
    score, passed = _compute_score_and_passed(checks)
    return {"passed": passed, "score": score, "checks": checks, ...}
```

每种文档类型的检查项是不同的，但评分逻辑共用：高严重度检查项权重为 2，中低严重度权重为 1，`passed` 要求所有 `high` 严重度项都通过。

### PRD 的检查项

PRD 检查的是章节完整性和核心内容：

```python
# harnessprd/backend/services/quality_gate.py

def _run_prd_checks(content) -> List[Dict]:
    return [
        _check("prd.section.overview",  "产品概述章节",  _section_present(content, r"##\s*1\.\s*产品概述")),
        _check("prd.section.features",  "功能需求章节",  _section_present(content, r"##\s*2\.\s*功能需求")),
        _check("prd.section.pages",     "页面设计章节",  _section_present(content, r"##\s*3\.\s*页面设计")),
        _check("prd.section.tech",      "技术规格章节",  _section_present(content, r"##\s*4\.\s*技术规格")),
        _check("prd.section.nfr",       "非功能需求章节", _section_present(content, r"##\s*5\.\s*非功能需求")),
        _check("prd.section.scope",     "项目范围章节",  _section_present(content, r"##\s*6\.\s*项目范围")),
        _check("prd.mvp.table",         "MVP 功能表格",  bool(re.search(r"\|\s*功能名称\s*\|", content, re.IGNORECASE))),
        _check("prd.scope.in",          "在范围内",      _scope_has_content(content, "在范围内")),
        _check("prd.scope.out",         "不在范围内",    _scope_has_content(content, "不在范围内")),
        # 待确认项超过 5 处降为 medium 警告
        _check("prd.pending.count", "待确认项数量", pending_count <= 5, severity="medium", detail=...),
    ]
```

六个章节标题都要存在，MVP 表格要有"功能名称"表头，"在范围内"和"不在范围内"章节要有实际内容。"待确认"出现太多次是 medium 级别的警告，不阻断 passed 判断，但会在结果里记录。

### 接口文档的检查项

接口文档检查核心/边缘分区、统一响应结构和路径规范：

```python
# harnessprd/backend/services/quality_gate.py

def _run_api_docs_checks(content):
    endpoint_count = _count_api_endpoint_definitions(content)
    return [
        _check("api.section.core",     "核心接口分区",   bool(re.search(r"核心接口", content))),
        _check("api.section.edge",     "边缘/辅助接口分区", bool(re.search(r"边缘接口|辅助接口", content))),
        _check("api.response.wrapper", "统一响应结构",   bool(re.search(r'"code"', content) and re.search(r'"data"', content))),
        _check("api.path.prefix",      "API 路径前缀",   bool(re.search(r"/api/v1", content))),
        _check("api.endpoint.count",   "接口条目",       endpoint_count >= 1),
    ]
```

接口条目的识别支持三种写法：标题行内嵌 HTTP 方法、`路径:` 字段格式、以及直接的 `POST /api/v1/...` 行。取三种识别方式的最大值，避免因写法差异漏判。

### 提示词套件的检查项

提示词套件会用 PRD 里的 MVP 功能数量来校验功能提示词的数量是否匹配：

```python
# harnessprd/backend/services/quality_gate.py

def _run_prompts_checks(content, context=None):
    checks = [
        _check("prompts.section.context",  "项目总览章节", ...),
        _check("prompts.section.features", "功能开发章节", ...),
        _check("prompts.section.frontend", "前端开发章节", ...),
        _check("prompts.section.review",   "代码审查章节", ...),
    ]
    prd_content = (context.get("prd_content") or "").strip()
    if prd_content:
        expected = _count_mvp_table_rows(prd_content)  # 数 PRD MVP 表格的行数
        feature_headings = _count_prompt_feature_headings(content)  # 数功能开发提示词数
        diff = abs(feature_headings - expected)
        checks.append(_check(
            "prompts.feature.count", "功能提示词数量",
            diff <= 1,  # 允许相差 1 个
            severity="high",
        ))
    return checks
```

这是个跨文档的一致性检查：PRD 有 4 个 MVP 功能，提示词套件里的"功能开发"章节理应也有约 4 个子提示词。相差超过 1 个就是不通过，说明模型可能遗漏了某个功能模块。

## 门禁结果写入版本元数据

质量门禁的结果不只是给当下看，它会被写进版本元数据里：

```python
# harnessprd/backend/services/job_runner.py

quality_gate = run_quality_gate(doc_type, content, gate_context)
# 把质量检查结果写进当前版本的元数据
metadata["quality_gate"] = quality_gate
patch_current_metadata(job["session_id"], doc_type, metadata)
```

这意味着每个版本都带着当时的质量检查结果，后续查版本历史时能看到"这个版本生成时，哪些检查通过了，哪些没有"。版本 2 比版本 1 质量分高，说明修订起了作用——这是一条可追溯的质量时间线，不只是当下的快照。

## Job 完成时机与失败边界

文档最终化处理在 `finally` 块里被调用，无论 Job 成功还是失败都会执行：

```python
# harnessprd/backend/services/job_runner.py

try:
    async for event in document_service.generate_prd_from_summary_stream(...):
        # ...
except Exception as exc:
    # Job 失败时，把草稿和 job_status=failed 写进版本元数据
    _sync_document_before_session(session_id, "prd", draft, failed=True, job_id=job_id)
finally:
    # finally 块始终执行：run_summary + quality_gate 写入元数据
    await _finish_run_summary(job_id, run, revision_applied, artifact="prd")
    # _finish_run_summary 内部调 _finalize_document_for_job
    # _finalize_document_for_job 里根据 job status 判断 failed 并运行 quality_gate
```

文档最终化时会检查 Job 状态决定是否写失败标记，但质量门禁照样运行。失败的 Job 如果有草稿内容，同样会对草稿做结构检查，结果写进元数据。这让排查时能区分"生成失败"（`job_status=failed`）和"生成完成但结构不达标"（`quality_gate.passed=false`）两种情况。

## Review 与 quality_gate 的分工

两者都在生成之后运行，但检查的东西完全不同：

| | Review Agent | quality_gate |
|---|---|---|
| 检查对象 | 内容语义质量 | 文档结构完整性 |
| 实现方式 | LLM 调用，有推理过程 | 确定性正则，无 LLM |
| 可能触发 Rewriter | 是（PRD 不通过时） | 否，只记录，不干预流程 |
| 结果字段 | `metadata.review` | `metadata.quality_gate` |
| 运行时机 | Job 执行期间 | Job 结束后（finally 块） |

Review Agent 的结果影响流程——PRD 的 Review 不通过会触发 Rewriter 重写；quality_gate 的结果只写进元数据，不影响 Job 是否完成。两者互补：Review 保障内容质量，quality_gate 保障结构合规，都写进版本元数据，都可以在版本历史里看到。

## 两层门禁的分工

| | 交付守卫 | 质量门禁 |
|---|---|---|
| 触发时机 | Job 创建前 | Job 结束后（finally 块） |
| 检查内容 | 业务前置条件（摘要存在？PRD 已确认基线？） | 文档结构完整性（章节标题、表格、前缀） |
| 失败后果 | 拒绝创建 Job，返回 400 | 记录到版本元数据，不阻断流程 |
| 实现方式 | 显式业务规则 | 确定性正则，无 LLM |

两层各司其职。交付守卫在入口拦截没有意义的请求，质量门禁在出口记录内容是否结构完整。Review Agent 在生成期间独立运行，补充的是语义层面的质量检查。三者都把结果持久化到版本元数据，查历史版本时能看到当时每一层的检查情况。

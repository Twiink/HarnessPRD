# 项目架构全景

harnessprd 是一个 AI 驱动的产品文档生成平台。用户描述需求，系统通过多轮澄清对话提炼信息，再调度多 Agent 流水线，依次生成 PRD、接口文档和 AI 提示词套件。

整个系统按职责分四层：

```
┌──────────────────────────────────────────────────────┐
│  需求采集层（结构化表单 · 澄清对话 · requirements_summary）│
├──────────────────────────────────────────────────────┤
│  任务执行层（Generation Job · asyncio · job_bus）      │
├──────────────────────────────────────────────────────┤
│  Agent 生成层（Writer · Reviewer · Rewriter）          │
├──────────────────────────────────────────────────────┤
│  可观测层（LLM Step 指标 · Token 预算 · run_summary）  │
└──────────────────────────────────────────────────────┘
```

四层从上往下各司其职。需求采集层把用户意图转化为结构化摘要，任务执行层把生成过程从浏览器连接里解耦出来，Agent 生成层负责文档质量，可观测层让整个过程可度量、可诊断。

## 需求采集层

用户进入平台，首先看到的是结构化表单。表单涵盖项目背景、目标用户、核心功能等字段。填完后，系统进入澄清对话阶段。LLM 逐轮提问，引导用户补全细节。

对话全程走 SSE 推送。每条消息实时打字机出现，用户逐轮回答。Session 每隔约 1 秒写一次数据库。网络短暂闪断，历史不会丢失。

澄清结束后，系统把表单数据和对话内容合并成一份结构化摘要。这份摘要是后续所有生成步骤的共同输入，字段包括需求概述、功能列表、约束条件等。

## 任务执行层

用户点击生成按钮，后端立刻创建一个 Generation Job 并返回 `job_id`。

Generation Job 是整个 v2 架构最关键的设计决策。生成过程不再绑在 HTTP 连接上，而是以 `asyncio.create_task` 在 FastAPI 进程内后台运行。前端通过 `GET /api/jobs/{id}/stream` 订阅事件流。浏览器关掉，协程继续跑；下次打开，用同一个 `job_id` 重连即可。

任务状态存在 SQLite 的 `generation_jobs` 表里。状态路径是：

```
pending  →  running  →  completed
                     →  failed
                     →  cancelled
```

生成过程中，每 500 毫秒把最新草稿内容节流写一次数据库。每当 Phase 切换（比如从起草转入审查），则立刻写库。这两个写入频率的差异是刻意设计的，草稿内容允许短暂落后于内存中的最新状态，Phase 变更则必须即时持久化。

## Agent 生成层

PRD 生成是最复杂的一段，由三个 Agent 串联完成。

**Writer Agent** 接收需求摘要和 Skill（团队规范与参考模板），生成第一版 PRD 正文。输出是流式的，chunk 实时推送给前端，Stepper 上显示「起草中」。

**Reviewer Agent** 收到完整 PRD 后，按结构化标准对每个章节逐一评审，生成一份包含通过 / 未通过明细的 JSON 报告。这个阶段不输出新字。Stepper 显示「正在审查」，前端把已有正文静态展示，不触发打字机。

**Rewriter Agent** 拿到 Review 报告和第一版 PRD，针对不合格项修订，生成最终版本。修订前把 v1 草稿另存到历史字段 `previous_draft`，v2 写入当前草稿字段 `draft_content`，前端渐进替换显示。

接口文档和提示词走 Generate → Review 两步：流式生成后同样会调 Reviewer 产出 JSON 审查报告，但不设 Rewriter，审查意见只记录、不自动改稿。三类文档共用同一套 Job 基础设施，runner 按产物类型挂不同的 generator。

## 可观测层

可观测层做两件事：记录每次 LLM 调用的过程指标，以及在调用前检查 token 预算。

**过程指标**方面，每次 LLM 调用，系统记录一条步骤指标 `StepMetrics`，内容包括步骤名称、模型名称、输入输出 token 数、耗时毫秒。多条步骤指标汇总成一次运行的汇总指标 `RunMetrics`，流程结束后以汇总事件 `run_summary` 推给前端展示，同时在服务端打一行 JSON 日志。日志里带有请求唯一标识 `request_id` 和会话标识 `session_id`，出问题时可以用请求标识把同一次生成的所有调用记录串起来。

**token 预算**方面，每次 LLM 调用前，系统对比两套上限：一是从模型注册表 `models.yaml` 读取的物理上限，二是环境配置 `.env` 里按场景设定的业务上限。取两者最小值作为有效预算。比如澄清对话的业务上限是 6 万 token，远小于模型支持的 1M 上限。对话过长时，系统提前给出中文提示，而不是等到模型报错。

四层加在一起，构成了一个从需求录入到文档落库的完整闭环。后续四章分别深入其中的核心难点：长任务工程化、多 Agent 流水线、Prompt 上下文注入，以及可靠性工程。

# 项目竞争力：四大核心亮点

大多数 AI 文档生成工具停留在把 prompt 塞给模型、把结果展示给用户这个层面。harnessprd 的目标不是这个。它要解决的是真实使用场景里持续出现的问题：生成中刷新页面会怎样、PRD 质量靠什么保证、上下文越来越长时怎么控制成本、历史版本怎么追溯。

下面四个亮点，是 v2 在工程设计上值得认真讲的地方。

## 亮点一：长任务工程化

生成一份 PRD 往往要几十秒，完整走完起草、审查、修订三段流水线有时超过两分钟。如果生成过程绑在浏览器连接上，用户一刷新，后台生成就停了，已经流出来的草稿也可能只剩一半。

v2 用 Generation Job 解决这个问题。创建 Job 和订阅事件流是两个独立请求，生成协程在服务端独立运行，与前端连接无关。刷新后用同一个任务标识重连，已有内容立刻全量展示，后续新字继续打字机效果。

这套设计刻意没有引入 Celery 和 Redis，任务用 `asyncio.create_task` 在现有 FastAPI 进程里运行，架构足够轻。以后若要支持多实例或任务排队，只需把执行层换成 Celery，Job 表和 API 形状可以不动。

## 亮点二：多 Agent 流水线

让 LLM 一次生成一份完整 PRD，往往得到的是结构尚可但细节潦草、边界模糊的结果。v2 把这个单步生成拆成三个职责明确的 Agent，让它们串联配合。

**Writer Agent** 专注起草。它拿到需求摘要和团队规范 Skill，生成第一版正文。它不负责校对自己写的是否完整，只管把初稿写出来。

**Reviewer Agent** 专注审查。它接收完整 PRD，对照结构化标准逐项评估，输出一份 JSON 格式的审查报告，明确标记哪些章节通过、哪些有问题以及原因。它不改文档，只给结论。

**Rewriter Agent** 专注修订。它拿着 Review 报告和初稿，针对不合格项逐一改写，生成最终版本。它不重新起草，只在初稿基础上精准修订。

三个 Agent 各做各的事，互不侵权。这种分工带来一个额外好处：每个 Agent 的 system prompt 可以针对自己的任务深度优化，而不是用一个大而全的 prompt 同时覆盖三种目标。

## 亮点三：Prompt 上下文注入

生成质量的上限不只由模型决定，还由 prompt 里放了什么决定。v2 在 prompt 构造阶段做了两层注入：输入合并和规范注入。

**输入合并**把两类信息组合成统一的需求摘要：一是结构化表单收集的功能列表、目标用户、约束条件等字段，二是澄清对话里用户补充的细节。表单给出骨架，对话补充细节，两者合并后的摘要比任何单一来源都更完整。

**规范注入**通过 Skill 系统完成。Skill 是挂载在项目上的一组配置文件，包含团队的写作规范、输出模板和参考示例。项目里目前有三套 Skill 目录，分别对应三类文档：

```
skills/
  prd-generator/          ← PRD 生成规范
  api-docs-generator/     ← 接口文档规范
  prompts-generator/      ← 提示词套件规范
```

每套目录下放写作指引、字段规范、输出模板等文件。生成时，系统把与当前文档类型匹配的 Skill 段落拼入 system prompt，让模型感知这个团队的风格要求和禁止写法。Skill 与代码分离，修改规范不需要改代码，重新生成就能反映新规范。

两层注入的结合，让同一个模型在不同团队、不同项目下能生成风格一致、符合规范的输出。

## 亮点四：可靠性工程

一个 AI 系统长期运行，最常见的问题不是功能缺失，而是难以诊断。为什么这次生成慢？上下文快满了吗？哪一步 token 消耗最高？v2 在可靠性上投入了四个方向：观测链路、Token 预算、生成前门禁和版本追溯。

**观测链路**给每次 HTTP 请求分配唯一的请求标识 `request_id`，给每次 LLM 调用打步骤标签，比如代表 PRD 起草的 `prd_writer`、代表 PRD 审查的 `prd_review`。所有调用记录输入输出 token 数和耗时，流程结束时以汇总事件 `run_summary` 推给前端，同时在服务端打 JSON 日志。用请求标识可以把一次生成的全部调用记录串起来，不再猜测是哪步出了问题。

**Token 预算**在每次 LLM 调用前检查。系统维护两套上限：一是从模型注册表 `models.yaml` 读取的物理上限，二是环境配置 `.env` 里按场景设定的业务上限。发送前取两者最小值，超过阈值的请求提前拦截并返回中文说明，而不是等 API 报错后让用户面对难以理解的错误信息。

**生成前门禁**，也叫质量门控，在用户点击生成之前，检查当前 Session 的状态是否满足条件。比如生成接口文档前，必须已有 PRD 内容；同一方案同类型 Job 同时只能有一个在运行。门禁不通过时返回明确错误，不让用户误触触发重复生成。

**版本追溯**让每份文档从单一字符串升级成带版本链的对象。每次生成完成自动创建新版本，用户也可以手动保存里程碑。生成时的 Review 结果和运行汇总 `run_summary` 挂在版本元数据里，刷新后不丢。历史版本可以预览，也可以恢复成新的当前版。

这四个方向加在一起，让系统从「能生成」变成「出了问题能诊断、跑久了能维护」。

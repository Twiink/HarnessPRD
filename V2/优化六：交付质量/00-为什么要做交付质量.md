# 00 - 为什么要做交付质量

v2 已经能稳定跑完一条链路：结构化表单 → 澄清 → PRD（Writer / Review / Rewrite）→ 接口文档 → 提示词套件。生成改成了 Job，刷新可以重连；文档有版本链，Skill 规范统一静默注入。

但从「能生成」到「敢交付」，中间还缺一层：**用户说不清这版需求够不够好、三份文档齐不齐、能不能直接交给研发或 AI 编码工具。**

常见无力感包括：

- 澄清聊得挺多，一点「生成 PRD」才发现 MVP 描述太薄、范围边界没写
- PRD 刚出来就点「生成接口文档」，其实还没看清正文
- PRD 手改了几段，接口文档和提示词仍是旧内容，系统不提醒
- 只有 PRD 有 Review Agent，接口文档和提示词生成完就结束，出了问题只能肉眼扫
- 三份 md 分散在页面里，没有「这是一套交付物」的打包感

根因可以概括成：**有流水线，但没有「合格标准」和「门禁」**——该拦的地方没拦，该签字的地方没签字，该对齐的地方没对齐。

## 当前缺口：生成成功 ≠ 交付合格

| 环节 | 今天有什么 | 缺什么 |
|------|-----------|--------|
| 生成 PRD 前 | 表单校验、Summary Diff | 澄清是否收口、**未澄清时警告确认** |
| PRD 生成中 | Writer + Review + 可选 Rewrite | Rewrite 后无**确定性**结构校验 |
| PRD 生成后 | Review 结果展示、版本历史 | 用户**确认需求基线**才能进下游 |
| 接口文档 / 提示词 | 单次生成 + Skill 注入 | 无 Review；无与 PRD 的**版本追溯** |
| 交付 | 单文件下载 | 无质量报告汇总、无**交付包** |

PRD 的 Review Agent 解决的是「草稿有没有明显语义问题」；它**不能替代**：

- 生成前的澄清状态判断（输入侧，对话感知）
- 生成后的格式校验（规则侧）
- 人对「就这版 PRD 开工」的确认（基线侧）
- 下游产物与 PRD 版本的对齐（追溯侧）

## 目标：把「交付合格」做成可感知、可检查、可打包

交付质量改造要在 **不显著拉长主路径** 的前提下，补齐四层能力：

```
生成前  → 澄清状态 + 警告确认（对话收口感知，不重复表单校验）
生成后  → 结构校验 quality_gate（规则，三件套各有检查项）
进下游前 → 需求基线确认（人工 sign-off）
迭代中  → 上下游过期提示 + 下游 Review（语义，各 1 次，不自动 Rewrite）
终点    → 质量报告 + 交付包导出
```

用生活类比：

> 现在像工厂能出货，但没有质检单、没有放行章、外箱标签也不写批次。  
> 改完后：进产线前先看料够不够；出厂前过检；放行要签字；箱子上写清楚「这批货对应哪版图纸」。

## PRD 流程：保持现有节奏，不叠 Review

PRD 仍维持 **Writer → Review（1 次）→ 最多 Rewrite（1 次）**，不在 Rewrite 后再跑第二轮完整 LLM Review（避免 Review 阶段无输出、用户以为卡死，且 worst case 多等半分钟）。

Rewrite 之后用 **结构校验 quality_gate** 兜底章节、表格、范围等硬指标；Review 仍不通过时，**照常交付并展示已知 issues**，由用户手改或「优化文档」。

接口文档、提示词：**Review only，不自动 Rewrite**——它们是 PRD 的派生物，自动改稿容易偏离已确认基线；问题应通过「重新生成」或用户带指令的「优化文档」解决。

## 大概怎么做

分三篇实施说明（同目录 `01`～`03`）：

**澄清状态与生成前警告**

- 澄清页顶栏状态；未澄清完可生成，但按钮警告 + 点击 confirm
- `canPerformAction` / `delivery_guards`：统一极端兜底与基线等 artifact 规则

**文档结构校验与质量报告**

- `quality_gate` 服务：PRD、接口文档、提示词各有规则
- Job 完成后写入 `document_versions.metadata.quality_gate`
- review 页展示质量报告

**基线追溯、下游 Review 与交付包**

- 需求基线确认；`derived_from` 记录上下游版本关系；过期 banner
- `ApiDocsReviewAgent`、`PromptsReviewAgent`（各 1 次 Review）
- ZIP 交付包 + `manifest.json`

```
用户完成澄清（或带警告确认后生成 PRD）
  → 生成 PRD Job → Review → [Rewrite] → quality_gate
  → review-prd：用户「确认需求基线」
  → 生成 api-docs Job → Review → quality_gate（metadata 记 derived_from）
  → 生成 prompts Job → Review → quality_gate
  → 导出交付包（含 manifest、质量摘要）
```

![三件套交付包与质量报告](https://pic.niumianoffer.com/images/fs/opt6-00-delivery-package.png)

## 本阶段明确不做

- LangGraph / LCEL 等编排框架替换现有 `job_runner` + `document_service`
- MCP、Function Call、联网检索
- 并行多 Specialist Agent（安全 / 合规 / UX 各一个）
- 接口文档 / 提示词自动 Rewrite
- PRD 第二次 LLM Review 或多轮 Rewrite 循环
- 方案探索（2～3 技术架构卡片）、提示词 writing-plans 化
- REQ-ID 贯穿、PRD 版本 diff、Golden Eval CI、`team.yaml`
- 改造 v1 `App.tsx`

## 做了之后有什么优势

**对用户**

- 生成 PRD 前顶栏可见澄清是否收口；强行生成须确认，避免浑然不觉
- PRD 确认基线后再开下游，三件套不会对不上还浑然不觉
- 每份文档有质量报告，导出是一包而不是三个散文件

**对工程**

- 澄清状态、gate、基线规则集中在 `clarificationState` / `delivery_guards` / `quality_gate`，不散落 `AppV2`
- 不引入新中间件；仍用 SQLite、现有 Job 与版本 metadata
- Review Agent 增量复用 `prd_review_agent` 模式，Agent 数量可控

**对产品边界**

- 仍是单机需求工作台，不是团队协作 ALM
- 质量层与 Skill、观测、Job 正交：只加检查点，不重写主链路

交付质量解决的是「敢不敢拿出去用」。和 Skill、版本、Job 合在一起，v2 才从 **能生成**，变成 **可检查、可确认、可打包的专业需求工作台**。

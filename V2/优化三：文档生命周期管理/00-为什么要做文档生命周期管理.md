# 00 - 为什么要做文档生命周期管理

v2 已经能稳定走完一条链路：澄清对话 → 生成 PRD → 接口文档 → 提示词。生成和优化都改成了 Job，刷新可以重连，过程不容易丢。

但生成结果本身，仍然像写在草稿纸上的字——改一次，覆盖一次；关掉页面，只剩最后那一版字符串。

用户优化 PRD 三四次，只想找回「第二版挺不错」的那段表述，做不到。接口文档是上周基于某版 PRD 写的，PRD 后来又改了，系统也不会提醒上下游可能对不上。生成时 Review 出了什么问题、花了多少 token，刷新后 run_summary 常常只剩当前会话里的临时状态。

这些问题的根因一样：**文档没有被当成有历史、有身份的对象来管理，只是 Session 里的三个字符串字段。**

## 当前存法：三个字符串，覆盖即丢失

今天 `session_data` 里大致是这样：

```
prdContent        ← 每次生成、优化、手改，直接覆盖
apiDocsContent    ← 同上
promptsContent    ← 同上
```

手改是实时的：编辑器每打一个字会更新前端 state，约 1 秒 debounce 后写入 Session。但这只是覆盖同一个字段，不是版本管理。

| 用户动作 | 现在的结果 |
|----------|------------|
| 生成 PRD | `prdContent` 被新正文覆盖 |
| 优化 PRD 三次 | 只保留最后一次，前两版消失 |
| 手改几段话 | 覆盖同一字段，无里程碑 |
| 刷新页面 | 能看到最后保存的正文，但无版本列表 |
| 查看这版怎么来的 | 只能靠猜，或去翻 Job 表，前端没有入口 |

Job 表里有 `draft_content`、`review_json` 等过程数据，但那是任务记录，不是用户能理解的「PRD 第 2 版」。

## 目标：文档要有版本，而不是一次性字符串

文档生命周期管理要做的，是把 PRD、接口文档、提示词从三个字符串升级成有版本链的文档对象：

- **有 current**：用户编辑、优化，默认改的是当前这一稿
- **有历史**：用户主动「保存为新版本」时，才多一条可回看的里程碑
- **有关联数据**：某次生成或优化对应哪个 Job、`run_summary`、Review 结果，挂在版本元数据上，刷新不丢

用生活类比：

> 现在像 Word 没开修订记录，只保留最后一次 Ctrl+S。  
> 改完后要有「当前稿自动保存 + 偶尔另存一个里程碑」，而不是每次优化都多一个 v2、v3、v4。

![文档从三个字符串升级为三条版本链](https://pic.niumianoffer.com/images/fs/opt3-00-document-version-chains.png)

## 版本规则

### 三种文档，三条独立的版本链

PRD、接口文档、提示词各自从 v1 开始编号，互不对齐：

```
PRD:        v1 → v2 → v3
接口文档:   v1 → v2
提示词:     v1
```

进入每个 review 页，默认展示该文档自己的 current 版本，也就是最新工作稿。三份文档不共用一个版本号。

### 什么时候升版本、什么时候只改 current

| 动作 | 版本行为 |
|------|----------|
| 第一次生成完成 | 自动创建 v1，设为 current |
| 再次点击生成 PRD / 接口文档 / 提示词 | 版本号加一，新版变 current，旧版进历史 |
| 优化完成 | 更新 current 正文，不升版本号 |
| 手改 debounce 自动保存 | 更新 current，不升版本号 |
| 用户点「保存为新版本」 | 版本号加一，新版变 current，旧版进历史，只读 |
| 预览历史版本后点「恢复此版本」 | 以该历史版正文新建下一版（如 v3），设为 current；v1、v2 不变 |
| 浏览历史某一版 | 只读预览，不改变 current（除非用户点恢复） |
| 生成或优化进行中 | 只写 Job 草稿，Job 完成后再落 current |

不做「定稿」按钮，也不做单独的「保存」按钮。手改继续沿用现在的 debounce 自动保存，落库目标从覆盖字符串改成更新 current 版本。

历史版本默认不参与生成 prompt，模型仍主要读 current 正文，避免 token 膨胀和跨版本混用。版本历史是给人回看、留档用的。

## 大概怎么做

在现有 SQLite 上增加文档表，Job 完成和 Session 保存时写入版本层；前端 review 页增加版本侧栏和一个按钮。

```
用户编辑 / 优化
  → debounce 更新 current 版本，经 Session save 同步
  → 用户点「保存为新版本」
  → POST checkpoint，版本号加一

生成 / 优化 Job 完成
  → job_runner 内部写 current 版本与 metadata
  → 同步 session_data 三字段，作为兼容镜像

打开版本侧栏
  → GET 版本列表、某一版详情，只读预览
  → 预览历史版时可「恢复此版本」，升一新 current，历史快照不删不改
```

新增 HTTP 接口 6 个（含恢复、版本备注），改造已有 `POST /api/session/save`，在保存时顺带同步 current 版本。Job 写版本、老数据迁移走服务内部，不单独暴露 API。

**本阶段明确不做：**

- 定稿与审核工作流
- 两版 diff 对比
- PRD 变更后提示接口文档过期
- 向量检索与 RAG 入库
- 改造 v1 `App.tsx`

## 做了之后有什么优势

**对用户**

- 优化多次不会把中间稿全冲掉，需要时能另存一个版本留档
- 刷新后仍能看到当前稿；生成统计、Review 结果跟版本走，不丢
- **审查意见**：每次生成 PRD 写入该版 `metadata.review`；优化/手改不刷新；侧栏标注「基于生成时审查，修改后仅供参考」

**对工程**

- 文档有稳定 ID 和版本链，以后接案例库、导出、diff 都有挂点
- Session 三个字符串可继续当镜像，前端渐进迁移
- 与 Job 模型正交：Job 管过程，Document 管结果

**对产品边界**

- 不碰澄清对话流式链路
- 不引入新中间件，仍是 SQLite 与现有 FastAPI

文档生命周期解决的是「结果留得住、里程碑分得清」。和观测、Job 合在一起，v2 才从能生成，变成能反复打磨、有据可查。

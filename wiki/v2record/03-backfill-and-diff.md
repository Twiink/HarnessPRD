# 回填与 Diff 机制的形成过程

> 这是整个 `/v2` 链路里技术含量和产品思考都很集中的一环。简单说：AI 在对话里补充了信息，这些信息需要"写回"结构化数据，但写回之前用户应该先看到改了什么——这就是回填 + diff 的来由。

---

## 1. 问题是怎么暴露出来的

第一版 `/v2` 走通之后，很快就遇到了一个核心问题：

> 用户在对话里补充的那些细节，到底去哪了？

用户通过澄清对话说了很多：这个功能的优先级、某个页面的特殊逻辑、某些字段的约束……但如果这些信息只存在于聊天记录里，没有"写进"结构化摘要，那么：

- PRD 生成时，AI 仍然主要依靠摘要里的信息，对话里补充的细节可能被漏掉
- 用户也不知道"系统到底记住了我说的哪些东西"

所以必须有一套机制，把对话中的澄清结果**回写到结构化摘要**中。

---

## 2. 为什么不能直接回填，还要加 diff？

最直觉的方案是：

```text
澄清结束 -> 自动修改 summary -> 继续生成 PRD
```

但这会带来一个问题：**用户完全不知道 AI 改了什么。**

这是高风险的，因为 AI 在回填时可能：
- 补充了太多超出用户意图的内容
- 改错了字段（把某个功能的描述写进了另一个功能）
- 把模糊的表述写得过于确定，改变了原意

如果这些修改直接生效，用户后来发现 PRD 有问题，根本不知道是哪一步出了问题。

**类比**：这就像你请助理帮你修改一份文件，但助理改完之后没给你看修改记录，直接把新版本给了甲方。即使助理改得大体没问题，你也会觉得不安心——因为你不知道到底改了什么。

---

## 3. 增加 diff 预览

回填之后不直接应用，而是先展示"修改前 vs 修改后"的对比。

**白话说**：就像 Word 的"修订模式"，或者 GitHub 的 diff 视图——哪里加了内容，哪里改了措辞，一眼就能看清楚，你决定要不要接受。

这一步让用户能明确看见：
- 哪些字段发生了变化
- 具体变成了什么内容
- 这个改动是否符合自己的意图

---

## 4. Diff 机制的三轮演进

### 第一版：简单前后对比

最初的 diff 只是把"回填前"和"回填后"的摘要对象做比较，展示完整内容。

**问题**：用户会看到大量"没有变化"的字段，干扰很多，真正改了什么反而不容易找。

### 第二版：只展示变化的字段

很快就发现，用户真正关心的是"到底改了什么"，不是"所有字段的全貌"。

于是改成：
- 只展示有变化的字段
- 支持展示嵌套路径（比如 `功能列表[2].描述` 这样的路径）

### 第三版：区分变化类型 + 颜色高亮

进一步增加了变化类型的区分：
- **新增**：这个字段之前没有，现在加了
- **修改**：这个字段的内容变了
- **删除**：这个字段被移除了

并通过颜色高亮区分，让一眼扫过去就能判断变化的性质。

---

## 5. 为什么最后变成"确认后直接生成 PRD"

早期设计里，用户确认 diff 之后，下一步是"应用到表单"——也就是把回填结果写回前端表单，再由用户手动点"生成 PRD"。

但实际用下来发现：这一步虽然技术上合理，**心理上不顺**。

用户真正想做的是：

> 确认这些补充没有问题，然后继续走流程。

而不是：

> 先把数据"应用"回表单，然后再手动继续。

"应用到表单"这个动作对用户来说是一个不必要的中断——它需要用户理解"为什么要应用回表单"这个技术逻辑，而大多数用户并不关心这个细节。

所以最终把流程简化成：

```text
结束澄清
  -> 回填 summary
  -> diff 预览（只看变化的字段）
  -> 用户确认
  -> 直接生成 PRD
```

---

## 6. 这套机制的重要性

这一轮迭代意义非常大，因为它把"对话"和"结构化数据"之间的桥搭起来了。

如果没有这座桥：
- 前端的结构化录入只是个样子——好看但对生成结果没有实质影响
- 对话中补充的信息永远是"一次性"的，不会沉淀进系统
- AI 生成最终还是"自由发挥"，结构化数据成了摆设

有了回填 + diff + 确认这套机制：
- 对话成为结构化数据的"输入渠道"
- 用户对整个链路的控制感大幅提升
- 系统真正形成了一个闭环

**用一句话总结**：回填机制让"结构化数据"从"用户填写的起点"，变成了"贯穿整个工作流的中心对象"。

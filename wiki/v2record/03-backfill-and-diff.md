# 回填与 Diff 机制的形成过程

## 1. 问题是怎么暴露出来的

第一版 `/v2` 走通后，很快就遇到一个核心问题：

> 结构化录入之后，AI 通过对话补充的信息到底去哪了？

如果这些补充只存在于聊天历史里，那么：

- PRD 生成仍然会依赖自然语言推断
- 用户也不知道系统真正记住了哪些信息

所以必须把对话中的澄清结果回写到结构化摘要中。

## 2. 为什么不是直接回填

一开始很自然会想到：

```text
澄清结束 -> 自动修改 summary -> 生成 PRD
```

但这会带来一个新问题：

> 用户并不知道 AI 改了哪些字段。

这是高风险的，因为模型可能：

- 补得太多
- 改错字段
- 把模糊表述写得过于确定

## 3. 所以增加了 diff 预览

回填之后不直接应用，而是先展示：

- 回填前
- 回填后

这一步让用户能明确看见：

- 哪些字段变了
- 变成了什么
- 值不值得接受

## 4. Diff 机制的演进

### 4.1 最初版本

最开始的 diff 只是简单比对对象，能展示前后内容，但不够好用。

### 4.2 第二版

很快发现：

- 不应该展示“前后一样”的字段
- 用户更关心“到底改了什么”

于是 diff 改成：

- 只展示有变化的字段
- 支持嵌套路径

### 4.3 第三版

后来又增加了变化类型：

- 新增
- 修改
- 删除

并通过颜色高亮区分。

## 5. 为什么最后变成“确认后直接生成 PRD”

早期一个中间动作叫“应用到表单”，但很快发现这一步虽然技术上合理，心理上却不够顺。

用户真正想做的是：

> 确认这些补充没有问题，然后继续走流程。

而不是：

> 先回填表单，再手动继续。

所以最后调整成：

```text
结束澄清
-> 回填
-> diff 预览
-> 确认并生成 PRD
```

## 6. 这套机制的重要性

这一轮迭代的意义非常大，因为它把“对话”和“结构化数据”之间的桥搭起来了。

如果没有这座桥，skill-first 方案就仍然会退回：

- 前端结构化只是壳
- 最终生成还是靠模型自由发挥

有了这座桥，系统才真正形成一个闭环。

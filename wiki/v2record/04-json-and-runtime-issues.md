# JSON 与运行时问题实录

## 1. 为什么这一类问题最折磨人

在 `/v2` 开发过程中，最棘手的问题并不是页面 UI，而是：

- 模型回填 JSON 失败
- 服务代码更新了但进程还在跑旧逻辑
- 看似是模型问题，实际上是运行时未刷新

这类问题的共同点是：

> 前端只看到“失败”，但真实原因可能完全不同。

## 2. 第一个典型问题：服务没重启

有一次错误日志显示：

- 代码还在执行 `json.loads(content)`
- 行号也对应旧代码

但工作区里的文件已经变成了 `_extract_json_object(content)`。

这说明不是代码没改，而是：

> 后端服务进程没加载到最新代码。

这个问题的经验教训很直接：

- 看 traceback 时要同时核对行号和当前文件内容
- 不要默认“运行中的代码”就是“磁盘上的代码”

## 3. 第二个典型问题：模型输出看起来像 JSON，其实不是

后续又出现了更典型的错误：

```text
json.decoder.JSONDecodeError: Expecting ',' delimiter
```

这说明模型返回的内容：

- 外形像 JSON
- 但中间少逗号、引号没转义，或者拼接异常

这比“完全不是 JSON”更麻烦，因为第一眼会误判成解析器太严格。

## 4. 为了解这个问题，做了几层兜底

### 4.1 第一层：直接解析

直接 `json.loads`

### 4.2 第二层：提取对象

尝试去掉：

- ```json 围栏
- 多余前缀
- 前后解释文本

再从首个 `{` 到最后一个 `}` 截对象。

### 4.3 第三层：JSON 修复调用

如果还是不行，再让模型做一轮：

> 把这段内容修复成合法 JSON 对象，只输出 JSON。

## 5. 错误返回策略也被改了

最开始失败会直接 500，这对排查帮助很小。

后面改成：

- 不再只抛裸异常
- 失败时返回更可读的信息
- 附原始输出片段和修复后输出片段

这样前端或日志里就能看到：

- 模型到底说了什么
- 修复轮又吐了什么

## 6. 第三个典型问题：流程逻辑和模型行为冲突

还有一个看起来像“生成逻辑错了”的问题，其实本质是 Prompt 没隔离：

- `/v2` 的澄清对话居然会提前产出 PRD

原因是它最初还在用旧版通用系统 Prompt，而旧 Prompt 明确鼓励“信息足够就生成 PRD”。

这提醒了一个关键事实：

> 工作流控制不能只靠前端按钮，还必须靠 Prompt 边界。

## 7. 这轮问题留下的经验

### 7.1 任何回填型系统都必须当 JSON 会失败

不能把模型当语法完美机器。

### 7.2 运行时可观测性比“猜测模型意图”更重要

能看到原始输出，排查效率会高很多。

### 7.3 多阶段工作流必须有专用 Prompt

“澄清阶段只澄清”不能靠用户理解，必须靠系统约束。

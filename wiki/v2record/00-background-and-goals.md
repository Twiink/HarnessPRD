# `/v2` 的背景与目标

## 1. 为什么会有 `/v2`

旧版页面的工作流是线性的：

```text
表单 -> 对话 -> PRD -> 接口文档 -> 提示词
```

这条链路对“从零开始梳理需求”的场景很顺，但它有几个明显限制：

- 输入阶段仍偏自然语言，稳定性有限
- 对话虽然能补信息，但无法可靠回到结构化数据
- 很难从中间环节开始
- 很难把 `PRD 生成` 单独抽成一个可迁移的能力包

这也是 `/v2` 出现的根本原因。

## 2. `/v2` 不是简单重写页面

`/v2` 的目标不是“再做一个界面”，而是验证一整套新范式：

1. skill-first
2. schema-first
3. 澄清对话先于文档生成
4. 中间态可见
5. 可以从任意环节开始

所以它本质上是一个实验性工作台，而不是旧版页面的样式升级。

## 3. `/v2` 要解决什么问题

### 3.1 输入稳定性

让前端先把需求录成稳定结构，而不是全靠模型猜。

### 3.2 中间态可见

让用户知道：

- 当前摘要是什么
- 对话补了什么
- 回填改了什么

### 3.3 过程可控

让用户能够：

- 返回上一步
- 中途结束
- 从中间开始
- 刷新后恢复

### 3.4 能力可迁移

把 PRD 生成逻辑逐步从页面逻辑中抽离出来，靠 skill 包与 schema 驱动。

## 4. `/v2` 的基本设计方向

最初定义的主链路是：

```text
结构化录入
-> 澄清对话
-> 结构化回填
-> diff 预览
-> 用户确认
-> PRD
```

后续又继续扩成：

```text
PRD
-> 接口文档
-> 提示词
```

并且支持：

- 从 PRD 开始
- 从提示词开始

## 5. 设计时的一个关键取舍

用户明确提出：

> 稳定可靠比所谓体验更重要。

这句话对 `/v2` 的方向影响非常大。

它直接导致：

- 前端表单更贴近 schema
- 输入格式更严格
- 不刻意追求“自然填写”
- 更强调显式校验、显式回填、显式确认

## 6. 这条线的价值

从结果上看，`/v2` 实际上承担了两个任务：

1. 作为新工作流的产品验证
2. 作为 skill 运行时的第一版前端壳

这也是为什么后面会出现那么多与：

- schema
- 回填
- JSON
- 多阶段跳转
- 会话恢复

有关的细节问题。

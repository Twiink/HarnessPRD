# `/v2` 的背景与目标

> 这篇文章回答一个最基本的问题：我们为什么要做 `/v2`？旧版有什么不够用的地方？新版想解决什么？

---

## 1. 先说旧版哪里不够用

旧版页面的工作流是这样的：

```text
表单 -> 对话 -> PRD -> 接口文档 -> 提示词
```

用户在表单里用自然语言描述需求，然后 AI 通过对话补充细节，最终生成一份 PRD（产品需求文档）。

这条路对"从零开始梳理需求"的场景走得通，但它有几个让人越用越难受的地方：

- **输入太自由，不够稳定**：用户用自然语言填写，每个人写法不一样，AI 理解的结果也不一样
- **对话补充的信息没有落地**：对话里补充了很多细节，但这些细节只存在于聊天历史中，没有"写进"结构化数据
- **只能从头走**：如果你已经有了一份 PRD，想直接生成接口文档，做不到
- **PRD 生成逻辑是"页面私有的"**：没法把这套生成能力单独拿出来、复用到别处

---

## 2. `/v2` 不是简单重写页面

听到"做个 v2"，很容易以为就是把旧页面换个皮肤、做得更好看。但 `/v2` 从一开始就不是这个目标。

它实际上是在验证一套新的工作方式，核心理念有五条：

1. **skill-first（能力先行）**：生成逻辑不写死在页面里，而是封装成独立的 skill 包，可复用、可迁移
2. **schema-first（结构先行）**：前端先把需求录成标准化的结构，不是让模型去猜自然语言
3. **澄清对话先于文档生成**：先问清楚，再生成，而不是靠模型猜完直接出文档
4. **中间态可见**：每一步的中间结果都让用户看得到，不是黑盒
5. **可以从任意环节开始**：不必从头走，有 PRD 可以直接从 PRD 开始

所以 `/v2` 本质上是一个**实验性工作台**，而不是旧版页面的迭代升级。

---

## 3. `/v2` 要解决的四个具体问题

### 3.1 输入稳定性

**白话说**：旧版用户自由填写，每次输入结果差异很大，AI 也经常理解跑偏。`/v2` 想让输入先变成一个"有固定格式的表单"，减少模糊性。

让前端先把需求录成稳定的结构化数据，而不是全靠模型从自然语言里猜。

### 3.2 中间态可见

**白话说**：你和 AI 聊了很多，它"理解"了什么？当前摘要长什么样？改了哪里？用户应该能看到，而不是只看到最终输出。

让用户知道：
- 当前的结构化摘要是什么
- 对话过程中补充了什么信息
- 回填之后改了哪些字段

### 3.3 过程可控

**白话说**：流程不该是一条不能回头的单行道。用户应该能随时暂停、返回、跳步。

让用户能够：
- 返回上一步
- 中途结束
- 从中间某个环节开始
- 刷新后恢复进度

### 3.4 能力可迁移

**白话说**：PRD 生成这件事，不该只能在这个页面里用。把它封装好，以后任何地方都能调用。

把 PRD 生成逻辑从页面代码中抽离出来，靠 skill 包和 schema 驱动，而不是页面私有逻辑。

---

## 4. 最初定义的主链路

```text
结构化录入
  -> 澄清对话
  -> 结构化回填
  -> diff 预览
  -> 用户确认
  -> 生成 PRD
```

后续又往后延伸：

```text
PRD -> 接口文档 -> 提示词
```

并且支持从任意一步直接进入。

---

## 5. 一个关键的设计取舍

在设计过程中，用户明确说了一句话：

> 稳定可靠比所谓体验更重要。

这句话的影响远比听起来大。它直接决定了 `/v2` 的很多设计风格：

- 前端表单更严格，字段格式更贴近 schema（宁可麻烦点填，也要保证可靠）
- 不追求"自然填写"，而强调"显式校验、显式回填、显式确认"
- 凡是会影响结果的中间状态，都必须让用户看见并确认

**换句话说**：这套系统宁可多一个确认步骤，也不愿意让用户事后发现"AI 悄悄改了什么但我不知道"。

---

## 6. `/v2` 承担了两个任务

从结果来看，`/v2` 实际上干了两件事：

1. **作为新工作流的产品验证**：证明"结构化输入 + skill 驱动生成"这条路走得通
2. **作为 skill 运行时的第一版前端壳**：第一次让 skill 包有了一个真实可用的前端界面

这也解释了为什么后面会出现那么多关于 schema、回填、JSON 解析、多阶段跳转、会话恢复的具体技术问题——不是过度设计，而是这条路本身带来的工程挑战。

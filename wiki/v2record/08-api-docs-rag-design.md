# 接口文档生成前的 RAG 设计记录

> 这篇记录了给接口文档生成加"参考资料检索"（RAG）的整个设计过程。如果你不熟悉 RAG 是什么，可以把它理解成：AI 在生成接口文档之前，先去查了一遍团队的接口规范和历史示例，然后再动笔——而不是全靠自己"凭感觉"写。

---

## 1. 为什么接口文档生成需要参考资料？

PRD 生成和接口文档生成，看起来都是"让 AI 写文档"，但约束来源其实完全不同。

**PRD 生成**主要依赖当前需求本身——用户填的表单、澄清对话里说的内容，这些就是主要依据。

**接口文档生成**则强依赖**团队习惯**：
- 接口路径怎么命名（`/api/v1/` 还是 `/api/`？）
- 请求字段用什么风格（驼峰还是下划线？）
- 响应结构怎么包裹（有没有 `data` 层？）
- 错误码怎么写
- 分页、排序、鉴权怎么表达
- 历史上类似功能的接口是怎么设计的

如果 AI 全靠自己"知道"这些，生成结果就很容易漂移，每次都不一样。比如同一个"重新生成文案"的接口，AI 可能写成：

```text
POST /api/regenerate
POST /api/copywriting/regenerate
POST /api/v1/copywritings:regenerate
```

三种写法都能看懂，但团队一致性完全不同。

**这次 RAG 的目标**不是做一个"万能知识库问答"，而是在生成接口文档之前，把少量高质量的团队规范和历史示例取出来，给 AI 一个明确的参照系。

---

## 2. 什么是 RAG？（给非技术读者）

RAG（Retrieval-Augmented Generation，检索增强生成）这个词听起来很学术，但核心思路很朴素：

**类比**：就像你要写一篇技术报告，你不会纯靠记忆来写，而是先去查相关资料，然后参考这些资料来写。RAG 就是让 AI 也做这件事——在生成之前先检索相关知识，然后基于这些知识来生成内容。

具体到接口文档生成：

```text
用户想生成接口文档
  -> 系统自动检索：哪些团队规范和历史接口文档和这次需求最相关？
  -> 把检索到的参考资料给 AI 看
  -> AI 基于这些参考资料生成接口文档
```

这样 AI 生成的结果就不是"全靠自己发挥"，而是"参考了团队规范之后输出"。

---

## 3. 为什么没有一开始就用 Milvus 和 Embedding？

Milvus 是一种向量数据库，embedding 是一种把文本转成"语义向量"的技术——两者组合可以实现语义级别的相似度检索。这是目前 RAG 系统最主流的技术栈。

**但这次没有先上这套，原因很实际**：

当前知识库只有几类文档：
- 团队接口规范
- 历史接口文档示例
- 将来可能再加的错误码规范、鉴权规范等

这类文档有两个特点：

**第一，数量不会很大。** 接口规范知识库需要的是"小而精"，不是把公司所有文档都塞进去。

**第二，结构非常清晰。** Markdown 的标题本身就是天然的切片边界，比如：

```markdown
## 路径命名
## 请求规范
## 响应规范
## 错误响应
```

在这种情况下，先用本地 Markdown + 简单关键词打分来检索，能更快验证一个核心问题：

> 生成接口文档前显式参考团队规范，是否真的能提升输出稳定性？

如果这个问题还没有验证，就先引入 Milvus、embedding 模型、索引构建、数据同步等一套复杂基础设施，系统复杂度会过早膨胀。

**当前方案是一个最小可用 RAG**：

```text
本地知识文档
  -> 按 Markdown 标题切片
  -> 关键词 / 中文双字匹配打分
  -> 取评分最高的几个片段（topK）
  -> 前端让用户确认
  -> 把参考资料注入接口文档生成的 Prompt
```

它不是终点，但非常适合当前阶段。

---

## 4. 知识库文档放在哪里

当前示例知识库放在：

```text
backend/knowledge/api_docs/
  ├── team-api-guidelines.md     # 团队接口规范（硬约束）
  ├── history-copywriting-api.md # 文案类产品历史接口示例
  └── history-task-api.md        # 任务管理类产品历史接口示例
```

**三个文件各有分工：**

- `team-api-guidelines.md`：**硬约束**，规定接口路径命名、请求结构、响应结构、错误码格式、安全要求。所有接口设计必须遵守。

- `history-copywriting-api.md`：**相似业务示例**，适合"朋友圈文案助手"这类 AI 生成类产品，覆盖生成、重新生成、复制、历史记录等常见接口。

- `history-task-api.md`：**另一类典型示例**，主要覆盖任务管理、列表查询、状态流转这类 CRUD 接口。

**重要原则**：这三个文件不是越多越好，而是要足够典型。RAG 在这里的价值不是"给 AI 喂更多文字"，而是"给 AI 喂更可靠的边界"。

---

## 5. Chunk 是怎么切的？

"Chunk"（片段）是 RAG 系统里的基本检索单元——把大文档切成小片，每次检索命中的是最相关的那几个小片，而不是整篇文档。

**当前切片逻辑**（在 `backend/services/rag_service.py` 的 `_split_markdown()` 函数中）：

按 Markdown 标题来切。只要遇到标题行（`#`、`##`、`###`），就开始一个新的片段。

每个片段包含三个字段：

```python
@dataclass(frozen=True)
class RagChunk:
    source: str   # 来自哪个文件
    title: str    # 这个片段的标题
    content: str  # 片段的正文内容
```

比如 `team-api-guidelines.md` 会被切成：

```text
team-api-guidelines.md / 适用范围
team-api-guidelines.md / 路径命名
team-api-guidelines.md / 请求规范
team-api-guidelines.md / 响应规范
team-api-guidelines.md / 错误响应
team-api-guidelines.md / 安全要求
team-api-guidelines.md / 接口文档输出要求
```

**为什么这样切？**

接口文档生成时，AI 不需要整篇历史文档，它只需要知道"路径命名怎么约定""响应结构怎么写"这类具体的规范片段。按标题切片，命中的就是有明确语义边界的小单元，而不是一大段文字。

---

## 6. 检索 Query 怎么生成的？

用户在生成接口文档时，不需要手动输入搜索词。系统会自动把当前 PRD 和对话上下文组合成检索 query：

```python
query = f"{prd_content}\n\n{_format_conversation_context(conversation_messages)}"
```

**为什么同时用 PRD 和对话上下文？**

因为有些接口细节不一定写进了 PRD 主体，但可能在澄清对话里被明确提到，比如：

- "这个功能不需要登录"
- "只做本地缓存，不存数据库"
- "换一批使用相同的搜索条件重新生成"

这些细节会影响接口设计，所以 RAG 检索不能只看 PRD，也要看对话上下文。

---

## 7. Token 是怎么处理的？

**白话说**：中文没法像英文那样按空格分词，所以用了一个简单的处理方法——把中文文本切成"相邻两个字的组合"（bigram），用这个来做关键词匹配。

```python
def _tokenize(text: str) -> set[str]:
    normalized = _normalize_text(text)
    ascii_tokens = set(re.findall(r"[a-zA-Z0-9_:/.-]{2,}", normalized))
    cjk_chars = re.findall(r"[\u4e00-\u9fff]", normalized)
    cjk_bigrams = {cjk_chars[i] + cjk_chars[i + 1] for i in range(len(cjk_chars) - 1)}
    return ascii_tokens | cjk_bigrams
```

它会提取两类 token：

**第一类：英文/数字/路径/字段名**

```text
api, v1, copywritings, generate, /api/v1/tasks, scenario_type
```

**第二类：中文双字 bigram**

"朋友圈文案助手"会被拆成：

```text
朋友、友圈、圈文、文案、案助、助手
```

这不是完美中文分词，但对接口规范文档已经够用。因为接口文档里高频词非常集中，例如"接口""文案""生成""错误码""分页""鉴权"。

## 8. 打分排序具体怎么算

每个 chunk 独立打分，分数越高越可能被选中。打分分三步：

### 8.1 基础重叠分：query 和 chunk 共享了多少词？

```python
overlap = len(query_tokens & chunk_tokens)
score = overlap / max(len(query_tokens), 1)
```

**白话说**：如果 PRD 里有"生成文案、换一批、复制"，某个历史文案接口的片段里也有"生成文案、重新生成"，那它们的重叠词越多，这个片段的分数就越高。

### 8.2 团队规范加权：规范文档永远优先

```python
if "guidelines" in chunk.source or "规范" in chunk.title:
    score += 0.18
```

**为什么要专门加权？**

团队规范不是普通参考资料，而是硬约束。即使某个规范片段和这次 PRD 的业务词不完全重合，它也应该更容易被选中——因为它规定的是所有接口都必须遵守的格式。

这条加权保证了 `team-api-guidelines.md` 里的片段有更高机会进入 topK，防止它被历史示例挤掉。

### 8.3 重要业务词加权：业务匹配加分

```python
important_phrases = ["接口", "api", "鉴权", "错误码", "分页",
                     "生成", "文案", "任务", "复制", "历史",
                     "收藏", "登录", "数据库"]

if phrase in query_text and phrase in chunk_text:
    score += 0.03
```

**白话说**：如果某个词同时出现在 query 和 chunk 里，说明"业务高度相关"，加一点点分。比如"朋友圈文案助手"的 PRD 会让"生成""文案""复制""登录""数据库"等词发挥作用，让文案类历史接口片段更容易排到前面。

这个加权很小（每个词只加 0.03），不会完全改变排序，但能让"明显业务相关"的片段往前移一点。

## 9. TopK：最终选几个片段？

```python
selected = [chunk for score, chunk in ranked if score > 0][:top_k]
```

默认选 `top_k = 6` 个评分大于 0 的片段。

**如果所有片段分数都是 0 怎么办？**

兜底取前几个：

```python
if not selected:
    selected = [chunk for _, chunk in ranked[:min(top_k, len(ranked))]]
```

这个兜底是为了防止接口文档生成完全没有规范上下文。因为即使业务词完全对不上，团队规范文档通常仍然有价值（路径命名规则、错误码格式等是跨业务通用的）。

## 10. 命中后返回什么

**最初设计**：RAG 命中后直接返回拼好的 Markdown 上下文字符串，传给 AI 用。

**后来的改进**：拆成两层接口：

```python
retrieve_api_docs_hits(query) -> List[RagHit]    # 结构化命中结果
format_api_docs_rag_context(hits) -> str          # 格式化成 Prompt 上下文
```

结构化命中结果包含：

```python
@dataclass(frozen=True)
class RagHit:
    source: str           # 来源文件
    title: str            # 片段标题
    score: float          # 评分
    content: str          # 完整内容
    content_preview: str  # 预览摘要
```

**为什么要拆两层？**

这样后端既可以把 `RagHit` 返回给前端展示（让用户看到"参考了哪些资料"），也可以把同一批 hits 格式化成 Prompt 上下文传给 AI。

否则 RAG 始终是黑盒：用户只能看到最终的接口文档，完全不知道系统参考了什么规范。

## 11. `/v2` 页面为什么要做确认步骤

现在的接口文档生成流程是：

```text
点击"生成接口文档"
  -> 显示"正在检索接口规范与历史示例..."
  -> 展示命中的参考资料（用户可以看到来源和内容预览）
  -> 用户确认
  -> 正式生成接口文档
```

**这不是为了让用户多点一下按钮。**

这是 `/v2` 一贯设计原则的体现：

> 中间态必须可见，关键变更必须可确认。

在 PRD 链路里，我们已经做了"对话 → 回填 → diff 预览 → 确认 → 生成 PRD"。接口文档生成也应该遵循同样的精神：RAG 命中的资料会影响最终接口设计，用户应该知道系统参考了哪些规范和历史案例。

这一步之后，页面上不再只是"生成了接口文档"，而是明确告诉用户：

> 这份接口文档生成前，参考了哪些团队规范和历史示例。

---

## 12. RAG 是如何注入到生成 Prompt 的？

正式生成接口文档时，后端再次检索 RAG，把格式化后的上下文拼进 Prompt：

```python
rag_context = retrieve_api_docs_context(
    f"{prd_content}\n\n{_format_conversation_context(conversation_messages)}"
)
```

如果命中内容存在，会拼成：

```text
接口文档生成前检索到的 RAG 参考资料：

[RAG-1] 来源：team-api-guidelines.md / 路径命名
（路径命名规范的具体内容）

[RAG-2] 来源：history-copywriting-api.md / 生成文案
（历史接口示例的具体内容）
```

然后附加使用说明：

```text
1. 优先遵循 RAG 中的团队接口规范。
2. 参考历史接口文档示例的路径命名、参数表、响应结构和错误码写法。
3. 如果引用了 RAG 中的规范，请把它内化为接口设计结果，不要在正文中机械堆砌原文。
```

**最后一条"内化"很关键**：接口文档最终应该像一份自然生成的团队文档，而不是 RAG 片段的拼贴。AI 要把规范"消化进"自己的输出，而不是把参考资料原文抄一遍。

## 13. 当前方案的优点

**简单**：不需要部署 Milvus，不需要 embedding 模型，不需要异步索引任务，本地 Markdown 文件就能跑。

**可解释**：命中结果能直接展示给用户，source、title、score、preview 都清楚可见。

**适合小而精知识库**：接口规范这类知识不需要无限堆量，反而要控制质量。

**容易迁移**：接口文档生成服务只依赖一个检索入口，后面要换 Milvus，不需要重写业务逻辑。

---

## 14. 当前方案的局限

**不是语义检索**：用户写"换一组"，文档写 `regenerate`，如果没有共享关键词，召回可能不稳定。

**没有 token 级 chunk 控制**：按标题切片，如果某个章节很长，仍然可能把过多内容塞进 Prompt。

**没有真正的阈值策略**：当前只要分数大于 0 就可能进入 topK，未来应该区分"必须注入的规范"和"可选注入的示例"。

**没有知识库管理后台**：现在文档是本地 Markdown，适合开发阶段，不适合多人维护大型知识库。

---

## 15. 什么时候该升级到 Milvus？

如果出现以下情况，就该认真考虑引入向量数据库：

- 历史接口文档超过几十份，且类型越来越多
- 用户的表达习惯和历史文档的写法经常不一致（关键词匹配不够用）
- 需要跨业务线检索相似接口设计
- 需要支持团队上传文档并自动入库
- 需要记录命中日志、召回质量和用户反馈
- 需要做关键词 + 向量的混合检索

到那时，完整流程会演进成：

```text
query
  -> embedding 转向量
  -> Milvus topK 向量检索
  -> rerank（重排序）
  -> RagHit[]
  -> 前端用户确认
  -> Prompt 注入
```

**重要的是**：未来变的是检索的实现方式，不是产品流程。用户看到的"参考了哪些资料 → 确认 → 生成"这条交互链路不需要变。

---

## 16. 这次设计最重要的结论

这次 RAG 不是为了"显得用了高级技术"，而是为了把接口文档生成从"AI 自由发挥"拉回到"团队规范约束内"。

真正重要的不是用了 Milvus 还是关键词检索，而是这条链路的成立：

```text
规范知识
  -> 可检索（能找到相关的）
  -> 可展示（用户看得见参考了什么）
  -> 可确认（用户决定要不要用）
  -> 可约束生成（AI 基于规范生成，而不是自由发挥）
```

这条链路一旦成立，底层是本地 Markdown、BM25、embedding 还是 Milvus，都只是检索层的实现细节。

对 `/v2` 来说，这和之前的"结构化回填 + diff 确认"是一脉相承的：

> 凡是会影响最终文档质量的中间信息，都应该尽量**可见、可解释、可确认**。

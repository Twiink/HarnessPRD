# 从 v1 到 v2：这个项目是怎么被 Vibe Coding 出来的

这篇不是普通的开发日志。

普通开发日志通常记录“做了哪些功能、改了哪些文件、修了哪些 bug”。但这个项目更有意思的地方在于：它本身就是一个“帮助用户生成 PRD、接口文档和开发提示词”的工具，而它自己的演进过程，也正是一次非常典型的 Vibe Coding。

也就是说，我们不是先写完一份完整需求文档，再按部就班开发。

更真实的过程是：

```text
先有一个粗糙想法
-> 快速做出 v1
-> 使用中发现问题
-> 通过自然语言持续指出不满意的地方
-> 每一轮把问题转成产品设计和代码改动
-> 最后沉淀出 v2 工作台、skills、RAG、文档体系
```

这个过程本身，反而比任何一份静态 PRD 都更能说明“Vibe Coding 到底怎么发生”。

## 1. 最早的产品直觉

项目最开始的直觉其实很朴素：

> 很多人想做一个软件，但说不清需求。能不能做一个工具，帮他们把模糊想法整理成 Claude Code 能看懂的 PRD？

这个想法背后有两个判断。

第一，普通用户不会天然知道怎么写需求。他们可能只会说：

```text
我想做一个小程序
我想做一个 AI 工具
我想做一个类似 XXX 的网站
```

这些话对人类来说能听懂，但对开发系统来说还不够。

第二，AI 编程工具最怕的不是“不会写代码”，而是“输入上下文不清楚”。如果 PRD 不清楚，后面代码生成、接口设计、页面实现都会一路漂。

所以 v1 的目标不是做一个大而全的项目管理系统，而是先跑通一条最短链路：

```text
表单收集基础信息
-> AI 对话继续澄清
-> 生成 PRD
-> 继续生成接口文档和提示词
```

这就是 v1。

## 2. v1 是怎么一步一步出来的

v1 的形态很像一个“对话式需求收集器”。

用户先填一些基础问题，例如：

- 产品名称
- 解决什么问题
- 目标用户
- MVP 功能
- v2 功能
- 页面数量
- 页面风格
- 平台类型
- 是否需要登录
- 是否需要数据库

然后系统把这些信息交给 AI，让 AI 像产品经理一样继续追问、讨论、补齐。

最后用户可以生成：

```text
PRD
-> 接口文档
-> Claude Code 提示词套件
```

从代码形态上看，v1 的核心入口是：

```text
frontend/src/App.tsx
backend/services/conversation_service.py
backend/services/document_service.py
backend/services/prompts.py
```

它的设计非常直接：

```text
前端表单
-> formData
-> 后端格式化成自然语言上下文
-> LLM 对话
-> 对话历史生成 PRD
-> PRD 生成接口文档
-> PRD + 接口文档生成提示词
```

这个阶段最重要的不是“架构多漂亮”，而是先证明一件事：

> 一个普通用户确实可以通过表单 + 对话，把产品想法推进到可交付给 AI 编程工具的文档。

v1 证明了这个方向是成立的。

## 3. v1 的典型提示词

v1 里最核心的是“产品经理式对话提示词”。

它大概是这样的：

```text
你是一位资深产品经理，专门帮助用户清晰描述软件产品需求。

你的工作方式：
1. 通过双向对话深入了解产品需求，不是单向追问，而是真正的讨论
2. 仔细分析用户提供的信息，识别不清晰、有歧义或缺失的关键点
3. 像产品伙伴一样提出建议，帮助用户想清楚他们可能没考虑到的问题
4. 每次回复聚焦 1-2 个最重要的点，不要一次问太多
5. 适时总结已确认的内容，推动对话向前
6. 当信息足够完整时，主动提议生成 PRD
```

这类提示词的重点不是让模型“输出一个答案”，而是让模型扮演一个持续协作的角色。

它解决的是 v1 的核心问题：

> 用户不知道怎么把需求说完整，所以 AI 要帮他问出来。

PRD 生成提示词则更像一个模板约束：

```text
基于我们完整的对话内容，生成一份专业的 PRD。

要求：
1. 使用 Markdown
2. 结构清晰，Claude Code 可直接用于 AI 辅助开发
3. 简洁易懂，便于人类审核
4. 信息完整，覆盖所有已讨论内容

输出章节：
1. 产品概述
2. 功能需求
3. 页面设计
4. 技术规格
5. 非功能需求
6. 项目范围
```

接口文档提示词继续基于 PRD：

```text
基于以下产品需求文档和前期需求对话，设计完整的 API 接口文档。

要求：
1. 使用 Markdown
2. 接口按核心接口和边缘接口组织
3. 每个接口包含 Method + Path、功能说明、请求参数、响应结构
4. 路径命名遵循 RESTful 规范
```

提示词套件生成则面向 Claude Code：

```text
基于 PRD 和接口文档，生成一套完整的 AI 辅助开发提示词套件。

包含：
1. 项目总览提示词
2. 功能开发提示词
3. 接口实现提示词
4. 前端开发提示词
5. 代码审查提示词
```

这就是 v1 的提示词体系：  
先用对话提示词把需求问清楚，再用文档提示词把对话结果转成 PRD、接口文档和开发提示词。

## 4. v1 暴露出来的问题

v1 能跑通，但跑通之后问题也很明显。

最大的问题是：**所有信息都混在对话里。**

表单是表单，对话是对话，最后生成 PRD 时，模型需要从一大段历史里自己判断哪些信息重要、哪些信息已经被修正、哪些信息只是临时讨论。

这带来几个问题：

- 上下文越长，生成越容易漂
- 用户在对话里补充的信息没有回到结构化字段
- AI 说“可以生成 PRD”时，前端不一定知道状态是否真的准备好了
- 缺失字段没有统一表达
- 生成 PRD 的输入不是稳定 schema，而是一段聊天历史

这些问题一开始不一定致命，但只要你想让这个工具变得更稳定，就绕不过去。

所以 v2 的核心不是“把页面做得更好看”，而是换一种底层思路：

> 从会话驱动，升级到结构化 schema 驱动。

## 5. v2 的第一个关键转向：结构化优先

v2 最开始来自一个很明确的判断：

> 用户都是有经验的，宁愿前端改动表单，能基本对应上 schema，稳定可靠比所谓体验更重要。

这句话其实决定了 v2 的方向。

v1 更像：

```text
用户随便填
-> AI 自己理解
-> 生成文档
```

v2 则变成：

```text
用户按 schema 填
-> 前端转换成 requirements_summary
-> AI 只补齐不清楚的地方
-> 回填结构化摘要
-> 用户确认
-> 生成 PRD
```

这一步让项目进入了一个更工程化的阶段。

前端不再只是把文本交给模型，而是承担了“结构化输入层”的职责。比如 MVP 功能不再是一段自由文本，而要求按格式填写：

```text
功能名称｜功能描述｜用户价值
```

页面结构也要求按格式填写：

```text
页面名｜模块1,模块2｜备注
```

这样做看起来牺牲了一点自由度，但换来了更稳定的生成基础。

这就是 v2 的第一条重要经验：

> 如果目标是稳定产出工程文档，就不要把所有结构化责任都推给模型。

## 6. v2 的第二个关键转向：Skill 化

在讨论 PRD 生成时，有一个很关键的问题被提出来：

> 能不能把“PRD 生成”封成一个 skill：输入需求摘要，输出固定结构的 PRD？

一开始这听起来像“整理一下 Prompt”，但继续往下讨论后，方向变得更清楚：

> 不是做 Codex 或 Claude Code 专用 skill，而是做成 OpenClaw 那种平台无关、可迁移的通用 skill。

于是 `prd-generator` 被拆成了一个独立能力包：

```text
skills/prd-generator/
├── skill.yaml
├── instructions.md
└── references/
    ├── field-schema.json
    ├── prd-template.md
    ├── writing-rules.md
    └── examples/
```

这里的设计思想是：

```text
skill.yaml      定义能力契约
instructions.md 定义执行说明
field-schema    定义输入结构
template         定义输出结构
rules/examples   定义风格和质量边界
```

这一步非常重要，因为它把“PRD 生成”从代码里的 prompt，升级成了一个可独立维护、可复用、可迁移的能力包。

这也是后面 `wiki/skills/` 那组文档的来源。

## 7. v2 的第三个关键转向：澄清不是生成

v2 刚开始也踩过一个典型坑：澄清阶段的 AI 仍然会沿用 v1 的通用产品经理 Prompt，而 v1 的 Prompt 里有一句：

```text
当信息足够完整时，主动提议生成 PRD
```

在 v1 里这句话是合理的，因为 v1 是会话式流程。

但在 v2 里，它会破坏流程边界。因为 v2 希望：

```text
澄清
-> 回填
-> diff 确认
-> 生成 PRD
```

如果 AI 在澄清阶段直接输出 PRD，整个中间链路就被跳过了。

所以 v2 增加了澄清专用提示词：

```text
你是一位资深产品经理，正在帮助用户补齐一份已经结构化过的产品需求摘要。

你的任务边界：
1. 只做需求澄清、补充确认和纠偏
2. 每次只聚焦 1-3 个最需要确认的问题
3. 优先识别会影响 PRD 结构化输出的缺失项或歧义项
4. 可以总结当前已确认内容，但总结必须简短

严格限制：
1. 不要生成 PRD
2. 不要输出完整文档、完整模板、接口文档或大段结构化产物
3. 不要说“我来为你生成 PRD”或直接进入文档撰写
4. 在信息已经足够时，只需明确提示用户“如果没有更多补充，可以结束澄清”
```

这条提示词背后真正的设计原则是：

> 每个阶段都要有清晰边界，不能让模型自己决定跨阶段。

v2 的稳定性，很大一部分来自这个原则。

## 8. v2 的第四个关键转向：回填和 diff

用户在澄清对话里补充的信息，如果只留在聊天记录里，结构化 schema 就失去了意义。

所以 v2 加了一个关键动作：

```text
结束澄清
-> AI 根据对话更新 requirements_summary
-> 生成回填前后 diff
-> 用户确认
-> 应用到表单
-> 生成 PRD
```

这个阶段的提示词非常典型：

```text
请根据以下结构化需求摘要和后续澄清对话，输出一份更新后的结构化需求摘要 JSON。

要求：
1. 只输出合法 JSON，不要输出 Markdown 代码块，不要输出解释
2. 保持原有字段结构，尽量不要新增字段
3. 仅在对话中出现了明确补充、修正或澄清时才更新字段
4. 不要编造信息；不确定的内容保留原值
5. 如果对话中补充了更明确的内容，应覆盖原先的“待确认”或较模糊值
6. mvp_features、ui_pages、interaction_notes、in_scope、out_of_scope 等字段保持结构化
```

这个 Prompt 的目的不是生成文档，而是生成“结构化状态变更”。

这也是 v2 和 v1 一个很大的区别：

```text
v1 主要让 AI 生成内容
v2 开始让 AI 参与状态维护
```

但这里也踩了一个真实问题：模型并不总能返回合法 JSON。

于是后端又加了一层 JSON 修复：

```text
第一次解析失败
-> 把模型原始输出交给 JSON 修复提示词
-> 要求只修复成合法 JSON
-> 再解析
-> 仍失败则返回可诊断错误
```

这件事后来被单独记录在 `04-json-and-runtime-issues.md` 里。

## 9. v2 的第五个关键转向：工作台，而不是向导

一开始 `/v2` 只是结构化表单到 PRD 的新流程。

后来又出现了新的需求：

> v2 也需要包含 v1 之前的能力，有 PRD 之后能继续选择生成接口文档，以及后面的提示词。

再往后，又出现了更高级的需求：

> 每一步既可以串联，也可以从中间某步开始。

这一下 `/v2` 就不再是一个线性向导，而变成了工作台。

于是它支持三种入口：

```text
结构化需求开始
从 PRD 开始
从提示词开始
```

也支持完整串联：

```text
结构化需求
-> 澄清
-> PRD
-> 接口文档
-> 提示词
```

同时支持：

- 返回上一步
- 结束当前任务
- 刷新恢复
- 阶段导航
- 从某个中间文档继续

这一步背后的提示词不是某一段系统 Prompt，而是一个产品指令范式：

```text
这个页面既要支持完整串联，也要支持从中间开始。
每一步都应该既能承接上一步，也能作为独立入口。
用户中途想结束或返回上一步时，必须支持。
```

这类提示词很适合 Vibe Coding，因为它没有规定具体代码怎么写，而是清楚表达了产品行为边界。

## 10. v2 的第六个关键转向：接口文档生成前加 RAG

PRD 生成稳定后，下一个问题出现在接口文档。

接口文档不像 PRD，只依赖当前产品需求。它还依赖团队规范和历史接口风格。

于是新的需求出现：

> 生成接口文档之前，会使用 RAG 技术，相关文档有团队接口规范，历史接口文档示例。

第一版 RAG 没有直接上 Milvus，而是采用本地 Markdown 知识库：

```text
backend/knowledge/api_docs/
├── team-api-guidelines.md
├── history-copywriting-api.md
└── history-task-api.md
```

检索逻辑是：

```text
PRD + 对话内容
-> Markdown 标题切 chunk
-> 关键词 / 中文 bigram 打分
-> topK 命中
-> 注入接口文档生成 prompt
```

后来又进一步要求页面能看出来用了 RAG，于是流程变成：

```text
点击“生成接口文档”
-> 先显示“正在检索接口规范与历史示例...”
-> 展示命中结果
-> 用户确认使用这些参考资料
-> 再生成接口文档
```

这一步和前面的 diff 确认是一脉相承的：

> 凡是会影响最终文档的中间信息，都应该可见、可解释、可确认。

RAG 设计已经单独记录在 `08-api-docs-rag-design.md`。

## 11. 这个项目里的“提示词”其实分成三类

复盘下来，这个项目里的提示词不是一种东西，而是三类。

### 11.1 角色型提示词

用来规定 AI 扮演谁、怎么交流。

典型例子是 v1 的产品经理提示词：

```text
你是一位资深产品经理，专门帮助用户清晰描述软件产品需求。
通过双向对话深入了解产品需求，像产品伙伴一样提出建议。
```

它适合开放式对话。

### 11.2 生成型提示词

用来把已有上下文生成某种文档。

比如：

```text
基于完整对话生成 PRD。
基于 PRD 生成接口文档。
基于 PRD 和接口文档生成 Claude Code 提示词套件。
```

它适合内容产出阶段。

### 11.3 状态型提示词

这是 v2 才真正出现的。

它不是让 AI 写文章，而是让 AI 修改结构化状态：

```text
请根据澄清对话更新 requirements_summary JSON。
只在明确补充或修正时更新字段。
不要编造。
只输出合法 JSON。
```

这类提示词更接近“AI 参与工作流状态机”，也是 v2 比 v1 更高级的地方。

## 12. 这个项目的 Vibe Coding 方法论

如果把整个过程抽象出来，它不是“用户一句话，AI 写完全部代码”。

真正有效的方式更像这样：

```text
1. 先说目标，不要急着说实现
2. 做出最小可运行版本
3. 真实使用，发现不顺的地方
4. 用自然语言指出具体问题
5. 每一轮只推进一个明确能力
6. 能跑通后再抽象成架构和文档
7. 关键中间态都要可见、可确认
```

这个项目里反复出现的高质量用户指令，大多有一个共同点：不是泛泛地说“优化一下”，而是指出具体行为。

比如：

```text
用户都是有经验的，这里宁愿前端改动表单，能基本对应上 schema，稳定可靠比所谓体验更重要。
```

这句话直接决定了 v2 走结构化表单。

再比如：

```text
回填应该是对话问题问完之后，就自动回填，出现对比界面。
回填对比里面，只用展示 diff。
应用到表单感觉可以直接输出 PRD。
```

这句话直接塑造了回填 diff 流程。

再比如：

```text
每一步既可以串联，也可以从中间某步开始。
```

这句话让 `/v2` 从流程页升级成工作台。

再比如：

```text
点击“生成接口文档”
-> 先显示：正在检索接口规范与历史示例...
-> 显示命中结果
-> 用户确认
-> 再生成接口文档
```

这句话让 RAG 从隐藏后端能力变成了可见产品流程。

这些指令之所以有效，是因为它们描述的是“期望行为”，不是纠结具体代码实现。

## 13. 你是怎么用提示词“制造”出这个产品的

回头看，这个项目并不是靠一条超级提示词一次性生成出来的。

更准确地说，它是被一组连续提示词“塑形”出来的。每一轮提示词都在做一件不同的事情：有的定义目标，有的规定取舍，有的纠正流程，有的要求沉淀文档，有的把隐藏能力变成可见产品体验。

这和很多人理解的 Vibe Coding 不太一样。

很多人以为 Vibe Coding 是：

```text
我说一个需求
AI 直接做完整产品
```

但这个项目真正发生的是：

```text
你不断给出产品判断
-> 我把判断翻译成架构和代码
-> 你使用后继续指出不对劲的地方
-> 我再把问题修成新的产品机制
```

这里面最核心的不是“AI 会写代码”，而是你一直在用提示词控制产品方向。

### 13.1 第一类：目标提示词，让项目先有形

最早的提示词，本质上是在定义产品原型：

```text
我想做一个项目，帮助生成 PRD 文档和接口文档。
```

这类提示词不需要很长，但必须说清楚“产品最终帮用户完成什么”。

它制造出来的是 v1 的主干：

```text
需求收集
-> 对话澄清
-> PRD 生成
-> 接口文档生成
-> 提示词生成
```

这一步不是在追求完美，而是在让产品先有一个能跑通的闭环。

如果没有这类目标提示词，后面的所有优化都没有落点。

### 13.2 第二类：判断提示词，让 AI 不只是执行，而是参与取舍

在讨论 RAG 和 skill 时，你并没有直接说“马上写代码”，而是先问：

```text
我这个项目有必要引入 RAG 技术吗？
我这个项目有必要用 skill 技术吗？
```

这类提示词的价值在于，它不是命令式的，而是决策式的。

它让 AI 先帮你判断：

- 当前阶段是否真的需要
- 复杂度值不值得
- 哪些技术应该先轻量做
- 哪些技术应该以后再升级

这直接影响了后来的设计取舍。

比如 RAG 没有一开始就上 Milvus，而是先做本地 Markdown RAG。skill 也没有一开始绑定 Codex 或 Claude Code，而是做成平台无关的能力包。

这类提示词制造出来的不是某个按钮，而是项目的技术路线。

### 13.3 第三类：边界提示词，把模糊功能变成可实现系统

v2 最关键的提示词之一是：

```text
用户都是有经验的，这里宁愿前端改动表单，能基本对应上 schema，稳定可靠比所谓体验更重要。
```

这句话非常关键，因为它不是在说“帮我加个字段”，而是在声明一个产品原则：

> 稳定可靠优先于低门槛体验。

这个原则直接制造出了 v2 的结构化表单。

于是系统从：

```text
用户随便填，模型自己猜
```

变成：

```text
用户按 schema 填，模型负责补齐和润色
```

类似的边界提示词还有：

```text
可以搞成独立的页面，不影响原来页面可能好一些，这个页面路径有个 v2 就行。
```

这句话决定了新旧版本隔离，避免了在旧流程上硬改。

它制造出来的是：

```text
/      保留 v1
/v2    承载新工作台实验
```

这类提示词的特点是：它不一定直接描述功能，但会改变工程边界。

### 13.4 第四类：流程提示词，把“能用”变成“顺”

很多能力第一版能跑，但流程不一定对。

比如回填刚做出来时，你指出：

```text
回填应该是对话问题问完之后，就自动回填，出现对比界面，而现在错误地直接输出 PRD 了。
回填对比里面，有回填前、回填后一样的数据，这种就没必要展示，只用展示 diff。
应用到表单感觉可以直接输出 PRD。
```

这类提示词非常像产品经理在验收流程。

它同时做了三件事：

1. 指出当前顺序错了
2. 指出页面信息过载了
3. 指出确认后的下一步应该自动衔接

于是流程从：

```text
对话
-> 可能直接生成 PRD
```

变成：

```text
对话
-> 结束澄清
-> 自动回填
-> 只展示 diff
-> 确认并生成 PRD
```

这不是单点修 bug，而是把一个粗糙功能重塑成了可靠工作流。

### 13.5 第五类：纠错提示词，让系统从“差不多”变成“真的对”

开发过程中，你多次贴出具体错误和异常行为。

比如：

```text
结束澄清之前，还是输出了 PRD，应该在结束澄清用户确认没问题之后。
结束澄清提示回填结构化摘要失败。
```

还有后面贴出的后端 traceback。

这类提示词非常重要，因为它们不是抽象抱怨，而是带着现象、时机和期望行为：

```text
什么时候错了
错成什么样
应该是什么样
```

这直接推动了几个修复：

- 给 `/v2` 增加澄清专用系统 Prompt
- 禁止澄清阶段生成 PRD
- 增强 JSON 提取逻辑
- 增加 JSON 修复 fallback
- 把模型原始输出片段带回错误信息，方便定位

这类提示词制造出来的是系统鲁棒性。

### 13.6 第六类：工作台提示词，让产品从线性流程升级成平台

当 v2 已经能生成 PRD 后，你又提出：

```text
v2 版本也需要能包含 v1 之前的能力，有 PRD 之后能继续选择生成接口文档，以及后面的提示词。
```

然后进一步补充：

```text
v2 版本可以增加一个能力，支持直接进入到某个环节，比如 PRD 生成接口文档的环节，可以自己填 PRD，也就是每一步既可以串联，也可以从中间某步开始。
```

这两句话把 `/v2` 的产品定位彻底改变了。

它不再是：

```text
结构化需求 -> PRD
```

而变成：

```text
结构化需求 -> 澄清 -> PRD -> 接口文档 -> 提示词
```

同时还支持：

```text
从 PRD 开始
从提示词开始
从中间环节继续
```

这类提示词制造出来的是“工作台”概念。

它让页面从一个功能页，变成了可以承载多阶段文档生产的操作台。

### 13.7 第七类：可见性提示词，把隐藏能力做成产品体验

RAG 第一版接好后，其实后端已经能影响接口文档生成了。

但你马上追问：

```text
我现在生成接口文档，页面能体现出来我用了 RAG 技术吗？
```

这个问题非常关键。

因为技术上“用了 RAG”和产品上“用户知道用了 RAG”是两件事。

接着你给出了非常明确的流程提示词：

```text
点击“生成接口文档”
-> 先显示：正在检索接口规范与历史示例...
-> 显示命中结果
   - team-api-guidelines.md / 路径命名
   - team-api-guidelines.md / 响应规范
   - history-copywriting-api.md / 生成文案
-> 用户点“确认使用这些参考资料生成”
-> 再生成接口文档
```

这句话直接把 RAG 从隐藏实现变成了可见体验。

最终系统变成：

```text
检索
-> 展示命中
-> 用户确认
-> 生成
```

这和前面的回填 diff 是同一个产品哲学：

> 只要某个中间信息会影响最终输出，就应该让用户看见，并允许确认。

### 13.8 第八类：文档化提示词，把开发过程沉淀成资产

你多次要求把设计过程整理成 Markdown：

```text
整理成一份看着就很厉害的 markdown 教程文档，大概 10 多篇吧。
```

```text
再在 wiki 建一个目录 v2record，里面用 markdown 文件详细记录一下 v2 的开发过程，遇到的问题，总结与复盘。
```

```text
这个 RAG 的设计，给我整理成 markdown 文档，包括 RAG 整体怎么设计的，为什么用这个简单的设计，具体的分数排序是怎么算的。
```

这类提示词制造出来的是项目的“第二大脑”。

代码解决的是产品能不能跑，文档解决的是后来的人能不能理解它为什么这样跑。

最终项目里形成了两套非常重要的文档：

```text
wiki/skills/     讲设计理念和 skill 方法论
wiki/v2record/   讲 v2 是怎么一步步做出来的
```

这也是这个项目和普通 Demo 最大的区别之一：它不只是实现了功能，还把演进路径、取舍和方法论一起沉淀了下来。

### 13.9 这些提示词共同完成了什么

把这些提示词合在一起看，你其实不是在“给 AI 派活”，而是在持续做产品塑形。

它们分别控制了：

| 提示词类型 | 控制的东西 | 制造出的结果 |
|------------|------------|--------------|
| 目标提示词 | 产品要解决什么问题 | v1 主链路 |
| 判断提示词 | 技术是否值得引入 | skill / RAG 的轻量路线 |
| 边界提示词 | 哪些事情要分开 | `/v2` 独立入口、结构化优先 |
| 流程提示词 | 用户操作顺序 | 回填 diff、确认后生成 |
| 纠错提示词 | 系统哪里不符合预期 | 澄清 Prompt、JSON 修复 |
| 工作台提示词 | 产品形态如何升级 | 可串联、可跳步、多阶段 |
| 可见性提示词 | 隐藏能力如何呈现 | RAG 命中预览 |
| 文档化提示词 | 经验如何沉淀 | skills 文档、v2record |

这就是“你是怎么通过提示词制造出这个产品”的真正过程。

不是靠一条神奇提示词，而是靠一组连续、具体、有判断力的提示词，把一个模糊想法一步步压成可运行系统。

## 14. 最值得复用的提示词范式

如果以后要继续 Vibe Coding 类似项目，可以复用下面这些范式。

### 14.1 产品目标型

```text
我要做一个 [产品类型]，目标是帮助 [目标用户] 解决 [核心问题]。
先做一个能跑通核心链路的版本，不追求大而全。
```

### 14.2 稳定优先型

```text
这里稳定可靠比体验更重要。
宁愿让用户按结构化格式填写，也不要完全依赖模型猜。
前端字段要尽量对应后端 schema。
```

### 14.3 阶段边界型

```text
这个阶段只做 [澄清/回填/预览/确认]，不要直接进入下一阶段。
只有用户确认后，才允许生成最终文档。
```

### 14.4 中间态可见型

```text
这个动作会影响最终结果，所以页面必须展示它的中间结果。
用户确认之后再继续。
```

### 14.5 差异确认型

```text
不要展示所有内容，只展示前后发生变化的 diff。
diff 里要区分新增、修改、删除。
```

### 14.6 可串联也可跳步型

```text
这个流程既要支持从第一步完整走完，也要支持从中间某一步开始。
每一步既可以承接上一步，也可以作为独立入口。
```

### 14.7 轻量先行型

```text
先做一个轻量版本跑通业务价值，不要一开始引入重型基础设施。
但代码边界要预留好，后面可以替换实现。
```

### 14.8 文档沉淀型

```text
把这次设计整理成 Markdown 文档。
不仅记录做了什么，也要记录为什么这么做、遇到了什么问题、以后怎么演进。
```

这些范式，就是这个项目一路走到 v2 的真正“提示词资产”。

## 15. v1 和 v2 的本质区别

如果只看功能，v1 和 v2 都能生成 PRD、接口文档、提示词。

但它们的本质完全不同。

| 维度 | v1 | v2 |
|------|----|----|
| 输入方式 | 表单 + 自然语言对话 | schema 化结构录入 |
| 核心驱动 | 对话历史 | requirements_summary |
| 澄清方式 | AI 自由推进 | 澄清专用阶段 |
| 信息更新 | 留在聊天记录里 | 回填到结构化摘要 |
| 用户确认 | 主要确认最终文档 | 确认中间态 diff / RAG 命中 |
| 流程形态 | 线性向导 | 可跳步工作台 |
| 能力封装 | Prompt 写在代码里 | skill 包 + references |
| 接口文档 | 直接基于 PRD 生成 | 生成前先 RAG 检索规范和历史示例 |

一句话概括：

> v1 是“用 AI 对话生成文档”；v2 是“用 AI 参与一条可见、可控、可确认的文档生产流水线”。

这是这个项目真正的升级。

## 16. 如果重来一次，应该怎么开始

如果重新从 0 开始 Vibe Coding 这个项目，我会建议这样提第一条需求：

```text
我要做一个对话式需求收集工具，帮助用户把模糊的软件想法整理成 Claude Code 能直接使用的 PRD、接口文档和开发提示词。

请先做 v1：
1. 前端有基础表单，收集产品名称、目标用户、核心问题、MVP 功能、平台、是否登录、是否数据库等信息
2. 提交后进入 AI 澄清对话，AI 像产品经理一样继续追问
3. 对话足够后，可以生成 Markdown PRD
4. PRD 之后可以继续生成接口文档
5. PRD + 接口文档之后可以生成 Claude Code 提示词套件
6. 所有生成过程用流式输出
7. 前端用 localStorage 保存当前会话

先保证链路跑通，不要做复杂权限和数据库。
```

等 v1 跑通后，再提 v2：

```text
现在我要做 v2，单独放在 /v2，不影响旧版。

v2 的目标是稳定可靠：
1. 前端改成结构化表单，字段尽量对应 requirements_summary schema
2. MVP 功能用“功能名称｜功能描述｜用户价值”逐行填写
3. 先进入澄清对话，但澄清阶段不能生成 PRD
4. 用户结束澄清后，AI 根据对话回填结构化摘要
5. 回填前后展示 diff，只展示变化项
6. 用户确认后再生成 PRD
7. PRD 后继续支持接口文档和提示词
8. 每一步都支持返回上一步，也支持从 PRD 或提示词阶段中途开始
```

再之后，把 skill 和 RAG 加进去：

```text
把 PRD 生成抽成通用 skill，不强依赖 Codex 或 Claude Code。
skill 应该包含 skill.yaml、instructions.md、field-schema、template、writing-rules 和 examples。
```

```text
生成接口文档前加入 RAG。
知识库先用本地 Markdown，包含团队接口规范和历史接口文档示例。
点击生成接口文档后，先展示命中的 RAG 片段，用户确认后再生成。
```

这就是这次项目演进里最清晰的一条路线。

## 17. 最后一层复盘

这个项目最有价值的地方，不只是它现在能生成 PRD、接口文档和提示词。

更有价值的是，它把一次真实的 Vibe Coding 过程沉淀成了可复用模式：

```text
自然语言表达意图
-> AI 生成第一版
-> 人类用产品判断持续纠偏
-> AI 把判断落成代码
-> 真实问题继续反馈
-> 架构逐渐浮现
-> 文档反过来沉淀方法论
```

这和传统软件开发不是对立关系。它更像是把“产品经理、架构师、工程师、技术写作者”的协作过程压缩到一条连续对话里。

但这里有一个关键前提：

> 人类不能只说“帮我优化一下”，而要持续指出边界、取舍、流程和判断标准。

这个项目能从 v1 长到 v2，不是因为一开始的提示词完美，而是因为每一轮反馈都足够具体。

这就是它最值得被记录下来的地方。

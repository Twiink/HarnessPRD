# 第一版 `/v2`

## 1. 第一版目标

第一版 `/v2` 的目标很克制，只追求把主链路走通：

```text
结构化表单 -> 澄清对话 -> PRD 生成
```

当时并没有立刻把它做成完整工作台，而是先证明以下三件事：

1. 前端可以按 schema 录入
2. 对话可以围绕结构化摘要展开
3. 生成 PRD 时可以基于结构化摘要而不是基于旧会话模式

## 2. 第一版做了什么

### 2.1 独立路由

没有动旧页面，而是通过：

- `/`
- `/v2`

分离新旧入口。

这一步是对的，因为它大大降低了试错成本。

### 2.2 新表单结构

前端引入了更严格的字段约束，例如：

- `MVP 功能`：每行 `功能名称｜功能描述｜用户价值`
- `页面结构`：每行 `页面名｜模块1,模块2｜备注`

这和旧版“先填一个大 textarea 再让模型理解”很不一样。

### 2.3 结构化摘要生成

前端会先把 `StructuredFormData` 转换成 `requirements_summary`，再作为后续流程的主输入。

### 2.4 新 PRD 接口

后端新增了：

`POST /api/conversation/generate-prd-from-summary-stream`

让 PRD 生成可以直接吃结构化摘要。

## 3. 第一版为什么是必要的

因为如果第一步不先把结构化主链路做通，后面所有：

- 回填
- diff
- 跳步
- 多模型兼容

都没有根。

## 4. 第一版的明显不足

虽然第一版能跑，但很快暴露了几个问题：

### 4.1 结构化摘要和澄清对话之间仍然松散

对话补充的信息没有立即回到结构化对象中。

### 4.2 没有 diff

系统即使更新了摘要，用户也看不出来改了什么。

### 4.3 仍然太线性

只能从头走，无法从 PRD 或提示词阶段开始。

### 4.4 缺乏状态恢复

刷新就容易丢上下文。

## 5. 第一版的结论

第一版是成功的，因为它确认了一件关键事实：

> “结构化输入 + skill 驱动生成” 这条方向是能跑通的。

后续所有增强，本质上都是围绕第一版暴露的问题继续迭代。

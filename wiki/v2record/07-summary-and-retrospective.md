# `/v2` 开发总结与复盘

> 这篇是整个 v2 开发记录的收尾。不是说"我们做了什么功能"，而是说"我们学到了什么"——哪些决策是对的，哪些坑最值得记住，以及现在这套系统还缺什么。

---

## 1. 这次开发真正完成了什么

从结果上看，`/v2` 并不只是多了一个页面，而是把整个项目推向了一个新的架构阶段。

它完成了四个关键升级：

| 之前 | 之后 |
|------|------|
| Prompt 驱动页面 | Skill 驱动工作流 |
| 自然语言输入优先 | 结构化输入优先 |
| 会话黑盒（用户不知道 AI 基于什么生成） | 中间态可视化 |
| 线性流程（只能从头走） | 可跳步工作台 |

每一行升级背后都有大量具体的技术工作，但整体方向就是这四条。

---

## 2. 哪些决策是明显正确的

### 2.1 新旧页面分离

没有直接改旧页面，而是单独做 `/v2` 路由。这让整个试验的风险降低了——新版出问题不影响旧版，随时可以回退，随时可以继续试验。

**经验**：在不确定的探索阶段，隔离试验比直接改主路径要稳健得多。

### 2.2 优先稳定性，而非体验

用户一开始就说了：

> "稳定可靠比体验更重要。"

这句话让设计取向非常清晰，也避免了很多"把时间花在让填写更自然"这类方向错误的工作。结果是：系统的可靠性更高，虽然某些地方填写起来稍微麻烦一点，但出错概率大幅降低。

**经验**：在 AI 产品早期，稳定性往往比体验流畅更值得优先投入。

### 2.3 把回填做成显式确认

"对话补充 → 自动更新摘要 → 用户不知道改了什么"这条路当时有人提出过，但最终选择了"回填 → diff 预览 → 用户确认"这套更显式的方案。

这是整个链路里最关键的一个取舍。它让结构化数据成为真正的中心对象，而不是系统内部悄悄更新的黑盒。

**经验**：AI 替你做的修改，必须让你看见。否则用户对 AI 的信任很难建立起来。

### 2.4 Skill 文件外置

把 skill 做成独立目录和文件，而不是把指令和规则写死在代码里。这为后续的"skill 更新""多 skill 扩展""平台迁移"留出了空间。

**经验**：把"知识"和"代码"分开放，长期来看维护成本更低。

---

## 3. 哪些问题最值得记住

### 3.1 模型会天然破坏 JSON

这不是偶发异常，而是必然要考虑的工程事实。

AI 生成的文本是为了让人读懂的，不是为了满足机器解析的严格语法。任何依赖 AI 输出 JSON 的系统，都必须提前设计好容错策略。

**教训**：不要假设 AI 每次都能输出格式完美的 JSON，必须有兜底。

### 3.2 运行时状态比代码本身更容易误导人

"改了文件"不等于"服务在跑新逻辑"。这个坑简单，但很容易在调试过程中浪费大量时间。

**教训**：看报错时，先确认服务是否加载了最新代码。改了代码之后一定要重启服务。

### 3.3 多阶段工作流必须有明确的 Prompt 边界

澄清阶段、生成阶段、确认阶段——这些不同阶段如果共用同一个系统 Prompt，AI 的行为就会不可预测（比如"澄清阶段就提前生成了 PRD"）。

**教训**：每个阶段必须有专属的系统 Prompt，明确告诉 AI"这个阶段能做什么、不能做什么"。

### 3.4 工作台不是"多加几个按钮"

一旦支持跳步、刷新恢复、返回上一步，系统就已经是一个状态管理系统，不再只是页面切换。这带来的工程复杂度要提前认识到。

**教训**："工作台"和"流程页面"是两种不同的系统复杂度。跳步、恢复、回退是三个独立的技术问题，不要低估它们。

---

## 4. 当前 `/v2` 的位置

现在的 `/v2` 可以从三个角度来理解：

- **产品层**：一个支持多阶段、可跳步、中间态可见的高级需求工作台
- **架构层**：skill-first 方案的第一个真实验证
- **工程层**：未来通用 skill runtime 的第一版前端

它既是当下可用的产品，也是未来更大系统的探路前哨。

---

## 5. 还没有完成的地方

`/v2` 已经相当完整，但仍然有明显的后续空间：

- **Skill 注册中心还没做**：现在 skill 是手动维护的文件夹，未来需要一个管理机制
- **Adapter 还没做**：不同 Agent 平台之间的适配层还没有
- **Schema 严格验证还不够**：前端表单的格式约束还比较宽松，应该更严格
- **回填 patch 还不够细粒度**：现在回填是整体替换，未来应该支持更精细的字段级更新
- **自动评估还没上线**：生成结果的质量评估还没有系统化

---

## 6. 这次迭代最值得保留的一句话

如果整个 `/v2` 的开发只能留下一个经验，那就是：

> 不要把"生成文档"当成一次模型调用，而要把它设计成一条**可见、可控、可确认、可恢复**的能力链路。

"可见"：中间状态用户能看到。  
"可控"：每一步用户有决策权。  
"可确认"：关键变更需要用户明确同意。  
"可恢复"：出了问题能回退，刷新不丢失进度。

这是 `/v2` 真正留下来的东西，也是这套系统和"直接调一次 AI 接口"之间最根本的区别。

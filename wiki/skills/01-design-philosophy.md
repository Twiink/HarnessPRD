# 设计理念：为什么要从 Prompt 思维切到 Skill 思维

很多 AI 产品在早期都会经历一个很典型的阶段：

先写一个 Prompt，把用户输入喂进去，效果不错；  
然后继续补 Prompt，再加一些规则，再补一些模板；  
最后 Prompt 越来越长，功能好像也越来越多，但整个系统开始变得难解释、难扩展、难迁移。

这正是 skill-first 思维出现的背景。

它不是在否定 Prompt 的价值，而是在承认一件现实：

> 当一个能力已经涉及输入结构、流程约束、中间态确认、失败恢复和多模型兼容时，它就不再只是 Prompt 问题了。

## 为什么 prompt-first 到后面会吃力

Prompt-first 最吸引人的地方，是它很快。

你几乎可以立刻做出一个“能用”的东西：

- 写一段角色设定
- 写几条输出要求
- 加一个模板
- 让模型直接生成

早期验证想法时，这种方式没有问题。

真正的问题出现在后面。

当你开始要求系统：

- 输入要更稳定
- 输出要更可靠
- 对话补充不能丢
- 用户要知道系统到底改了什么
- 同一套能力最好还能在多个运行时复用

这时你会发现，继续堆 Prompt 并不能真正解决根问题。

因为 Prompt 擅长的是“传达意图”，不擅长的是“定义契约”。

## skill-first 真正强调的是什么

skill-first 的重点不是“把 Prompt 改个名字”，而是把能力拆成几个清晰层次。

先有能力定义，再有模型调用。

先有输入输出契约，再有文案表达。

先有工作流，再决定哪一步交给模型、哪一步交给前后端。

所以在这套设计里，真正重要的不是某一句 Prompt，而是下面这些东西一起成立：

- 输入 schema 是什么
- 输出模板是什么
- 澄清在什么时候发生
- 回填如何回到结构化对象
- 用户如何确认变更
- 失败时如何兜底

一旦这些层次被分开，系统就会变得非常不一样。

## 四个最核心的原则

### 1. `skill-first`

先把能力看成独立模块，再讨论页面如何调用它。

这意味着 PRD 生成不是某个按钮背后的私有逻辑，而是一个可被复用的能力单元。

### 2. `schema-first`

先定义输入结构，再让模型来消费。

这一点非常关键。因为 PRD 质量最先决定于“输入是否清晰”，而不是“模型是否文采好”。

### 3. `workflow-first`

不要把所有事情压成一次模型调用。

很多系统不稳定，不是模型笨，而是因为流程里那些原本应该显式存在的中间步骤被全部吞掉了。

### 4. `model-agnostic`

能力定义尽量独立于具体模型。

否则你会很快发现，今天服务 Claude 的设计，明天换个模型就得重来一半。

## 这套理念为什么特别适合 PRD 场景

PRD 生成表面上看像写作任务，实际上更像“结构化决策整理任务”。

模型真正需要做的不是自由发挥，而是：

- 读懂输入结构
- 识别缺失项
- 通过澄清补足关键字段
- 在模板约束下输出一份稳定文档

这种任务天然就适合：

- schema
- 模板
- 规则外置
- 明确中间态

也就是天然适合 skill-first。

## 为什么说这不是“更重”，反而是“更清楚”

很多人第一次看到 skill-first，会觉得系统变复杂了。

这其实是个错觉。

它不是把事情搞复杂，而是把原本藏在黑盒里的复杂度拿到了台面上。

以前的复杂度藏在：

- 长 Prompt
- 模型自由发挥
- 不透明的状态变化
- 模糊的输入结构

现在这些复杂度被重新组织成：

- skill 包
- schema
- 工作流
- diff
- 确认机制

从工程角度看，这不是负担，而是秩序。

## 一个更准确的理解方式

如果一定要用一句话概括 skill-first，它更像是：

> 把“能力”从模型语言里拔出来，变成系统中一个可以被看见、被约束、被复用的对象。

这也是为什么这套设计一旦成立，后面不止能做 PRD，还能继续长出：

- API 设计
- 提示词生成
- 测试计划
- 技术方案

因为你得到的已经不是一个 Prompt 技巧，而是一种能力建模方式。

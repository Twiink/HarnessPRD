# 设计理念

## 1. 总原则

这套设计遵循 4 个核心原则：

1. `skill-first`
2. `schema-first`
3. `workflow-first`
4. `model-agnostic`

这 4 个原则合在一起，决定了系统不是“一个提示词工程项目”，而是“一个能力工程项目”。

## 2. skill-first

### 2.1 含义

把“PRD 生成”看成一个独立能力，而不是某个页面按钮背后的一段 Prompt。

### 2.2 为什么重要

只有当它被定义成 skill，才会自然引出这些问题：

- 输入是什么
- 输出是什么
- 缺失信息怎么处理
- 失败时怎么兜底
- 多个平台如何复用

如果只是 Prompt，这些问题往往会被隐藏在大段自然语言里。

## 3. schema-first

### 3.1 含义

先定义输入结构，再讨论模型如何消费它。

当前 `prd-generator` skill 的输入 schema 在：

[`skills/prd-generator/references/field-schema.json`](../../skills/prd-generator/references/field-schema.json)

### 3.2 为什么重要

因为 PRD 生成最难的地方不是“写文档”，而是“搞清楚需求到底是什么结构”。

一旦输入结构被定义出来：

- 前端可以做校验
- 对话可以围绕缺失项澄清
- 回填可以回到结构化对象
- 输出文档会明显更稳

## 4. workflow-first

### 4.1 含义

把中间步骤显式化，而不是把所有事情都压到一次模型调用里。

当前推荐工作流是：

```text
结构化输入
-> schema 校验
-> 澄清对话
-> 回填结构化摘要
-> diff 预览
-> 用户确认
-> PRD 生成
-> 接口文档
-> 提示词
```

### 4.2 为什么重要

因为很多错误都发生在中间态：

- 输入不完整
- 用户表达模糊
- 模型补错字段
- 输出 JSON 不合法
- PRD 生成前没有确认新增信息

把中间步骤显式化，系统就更可控。

## 5. model-agnostic

### 5.1 含义

能力定义与具体模型分离。

### 5.2 具体表现

- skill 的结构定义写在文件里，而不是只写在模型 Prompt 里
- schema 是 JSON Schema，而不是模型专属格式
- 参考模板是 Markdown/JSON 文件，而不是写死在某个 SDK 逻辑里
- 前端和后端编排关注的是“流程”，不是某个模型的品牌特性

## 6. 为什么不追求一步到位

这套设计并没有一开始就做：

- 向量检索
- 多 skill 编排引擎
- 自动工具选择
- 复杂执行器

原因很简单：在 PRD 生成场景里，最先需要稳定的是：

- 输入结构
- 澄清流程
- 输出质量
- 失败恢复

这些基础打牢后，再做 skill 运行时平台化才有价值。

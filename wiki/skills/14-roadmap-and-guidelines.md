# 演进路线与实践建议：这套东西接下来应该怎么继续长

到现在为止，这套 skill-first 方案已经过了最难的那个阶段：

不是“有没有想法”，而是“第一条完整链路能不能真的跑起来”。

现在答案已经比较清楚了：

- skill 包能独立存在
- `/v2` 能围绕 schema 工作
- 澄清 -> 回填 -> diff -> PRD 这条线已经成立
- 后续的接口文档和提示词也能继续串上

所以接下来的问题，不再是“要不要做”，而是“往哪里继续做最值”。

## 第一优先级：把一套能力做得更稳

这是最重要的，不要跳过。

很多团队一看到 skill 的形状出来了，就会立刻想去做：

- skill 市场
- skill 自动发现
- 多 skill 编排
- 复杂调度系统

这些当然都很诱人，但当前最值得继续投入的，其实仍然是单项能力稳定性。

比如对 `prd-generator` 来说，马上最值得做的包括：

- 回填后的 schema 严格校验
- 更稳的 JSON 修复策略
- 更细粒度的字段级 patch
- 更系统的自动评估

因为只有把一项能力做扎实，后面的平台化才不至于变成空壳。

## 第二优先级：把技能运行时真正抽出来

现在 skill 包已经有了，但运行时还更多是在项目里“按需消费”。

未来如果想继续往前走，一个很自然的方向就是把 skill runtime 再显式抽出来。

可以想象成这样几层：

- skill package
- skill registry
- skill loader
- skill executor
- skill adapter

今天其实只完成了最前面的两步雏形。

后续只要继续抽，整套系统就会从“项目内技能”逐渐变成“技能平台”。

## 第三优先级：把 adapter 层补出来

这一步会非常关键。

因为现在虽然已经尽量模型无关，但还没有真正把“不同模型或 Agent 平台的消费差异”独立收纳起来。

未来一旦补了 adapter 层，很多东西会立刻更清楚：

- 哪部分属于 skill 核心
- 哪部分属于 Claude 偏好
- 哪部分属于 OpenAI 偏好
- 哪部分属于某个运行时自己的限制

这会让整个系统的边界更清爽。

## 第四优先级：让更多能力也按同样方式长出来

一旦 `prd-generator` 跑通，最自然的下一步不是继续把它做得越来越大，而是看看哪些能力也值得按相同模式抽出来。

例如：

- API 设计 skill
- Prompt 套件生成 skill
- 测试计划 skill
- 技术方案拆解 skill

当越来越多能力按同样模式出现时，你会发现“skill-first”不再只是一个单点实验，而开始像一个真正的架构方向。

## 给未来继续做这套系统的人几个建议

### 1. 先问输入输出，不要先写 Prompt

这是最容易犯的错。

### 2. 先把中间态做可见，再谈自动化

看不见中间态的系统，很难真正稳。

### 3. 前端不要只当外壳

前端在 skill 系统里承担的是：

- 输入稳定化
- 用户确认
- 工作流控制

这不是“UI 层顺便做点表单校验”那么简单。

### 4. 任何结构化回填都要假设 JSON 会失败

不要心存侥幸。

## 最后一句更大的判断

如果用一句话来总结这套东西接下来应该往哪里走，我会这么说：

> 不是继续把“文档生成”做得更花，而是继续把“能力链路”做得更稳、更清楚、更可迁移。

因为真正值钱的，从来不是某一篇 PRD 本身，而是你已经开始拥有一套可以不断复制到别的能力上的方法。

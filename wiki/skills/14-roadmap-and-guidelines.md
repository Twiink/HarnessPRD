# 演进路线与实践建议

## 1. 当前阶段的结论

当前这套系统已经完成了最关键的第一阶段：

- 把 PRD 生成能力独立成 skill
- 把输入结构化
- 把澄清做成中间环节
- 把回填做成显式确认动作
- 把 `/v2` 做成可跳步的工作台

这意味着基础范式已经成立。

## 2. 接下来最值得做的 5 件事

### 2.1 skill 注册中心

把 `skills/` 做成可扫描、可注册、可选择的能力目录。

### 2.2 adapter 层

为不同运行时和模型增加薄适配：

- Claude
- OpenAI
- OpenClaw 风格运行时

### 2.3 严格 schema 校验

回填后的 JSON 不应只“能解析”，还应“满足 schema”。

### 2.4 字段级回填

未来可以从“整对象回填”升级成“字段级 patch”，进一步提高可控性。

### 2.5 自动评估

基于 `examples/` 和固定测试集，自动评估：

- 是否丢字段
- 是否乱编
- 是否出现结构漂移

## 3. 给未来扩展 skill 的建议

### 3.1 一定先定义 schema

不要先写 Prompt，再补 schema。

### 3.2 一定先拆工作流

不要把所有行为压成“一次调用模型”。

### 3.3 一定把参考资料外置

模板、示例、规则不要全写进 Prompt。

### 3.4 一定做中间态可视化

只要有结构化中间态，就应该让人看见。

## 4. 给前端的建议

- 前端不要把自己当“纯壳”
- 前端应该承担输入稳定化职责
- 前端应该承担用户确认职责
- 前端应该让工作流可见、可退、可恢复

## 5. 给后端的建议

- 后端不要只做模型转发
- 后端要承担 skill 文件加载、Prompt 组装、异常修复、错误可观测性

## 6. 给 skill 设计者的建议

- 先问“这个能力的输入输出是什么”
- 再问“这个能力在哪些步骤最容易失败”
- 最后才问“Prompt 怎么写”

这会让 skill 设计从“写提示词”升级成“设计能力系统”。

## 7. 最终目标

这套方案最终不是为了“生成一篇 PRD”，而是为了建立一个可复制的能力模板：

```text
skill package
-> structured input
-> clarification loop
-> structured backfill
-> human approval
-> artifact generation
```

只要这个模板成立，后面不止能做 PRD，还能做：

- API 设计
- 测试计划
- 实施方案
- 代码迁移计划
- 运营 SOP

这才是 skill-first 架构真正厉害的地方。

# OpenClaw 启发：这套设计到底借鉴了什么，又没有借鉴什么

说这套设计“参考了 OpenClaw 风格”，容易让人误会成两件事里的某一种：

一种误会是：  
它已经完全变成了 OpenClaw 那种系统。

另一种误会是：  
只是借了个名字，实际上没什么真正相通的地方。

这两种理解都不太准确。

更准确的说法应该是：

> 这套方案明显借鉴了 OpenClaw 对“通用 skill”的理解方式，但当前实现仍然是 VibeCoding 自己的、面向当前项目现实约束的一版落地。

## 真正被借鉴的是哪部分

最核心的启发，其实不是某个具体格式，而是一种看待能力的方式。

### 1. 能力应该独立存在

不是埋在某个页面里，不是藏在某个 Service 里，不是散在几段 Prompt 里。

而是应该有自己的：

- 目录
- 元信息
- 指令
- 参考资料

也就是今天这个：

```text
skills/prd-generator/
```

### 2. Skill 不只是接口定义，而是知识包

这一点非常像你举的对比例子里说的那样。

Function Calling 更像在定义“接口”；  
Skill 更像在传递“这项能力的知识与做法”。

`prd-generator` 现在就明显不是一个纯函数接口，因为它除了输入输出之外，还包含：

- 写作规则
- 模板
- 示例
- 工作流概念

这已经更像一种能力说明书，而不是一个单纯 API。

### 3. 技能应该可以被多个运行时消费

这是最重要的开放性原则。

如果某个 skill 一旦离开当前产品壳就失效，那它其实还谈不上“技能”，更像“项目内私有逻辑”。

当前这套设计努力在做的，就是让 skill 包本身尽量不绑：

- Codex
- Claude Code
- 某一个网页前端

而是把它做成“谁能读取这些文件，谁就有机会消费这项能力”。

## 当前没有照搬 OpenClaw 的地方

这一点也必须说清楚。

虽然设计方向有相似性，但当前项目并没有把自己硬套成 OpenClaw 的形状。

比如：

### 1. 还没有完整的 skill registry

现在只是项目内一个 `skills/` 目录，不是完整市场或自动发现系统。

### 2. 还没有 runtime adapter 层

还没有专门针对不同 Agent 写：

- `adapters/claude.md`
- `adapters/openclaw.md`
- `adapters/openai.md`

### 3. 还没有“技能自动调度平台”

当前仍然主要是由产品流程决定什么时候调用 `prd-generator`，而不是一个更大的 skill orchestration 层。

## 为什么先做到这一步反而是对的

因为很多项目一上来就想做一个“技能平台”，最后往往会掉进另外一个坑：

平台壳做得很大，但没有一项能力真的被做扎实。

现在这条路反过来：

先把一项能力，也就是 `PRD 生成`，做成真正独立的 skill；  
再围绕它做：

- schema
- 工作台
- 回填
- diff
- 多模型兼容

这会让后面再往平台化走的时候基础更扎实。

## 一个最值得保留的启发

如果要用一句最短的话总结 OpenClaw 给这套设计带来的真正启发，我会写成这样：

> Tool 解决“能做什么”，Skill 解决“在什么场景下，这些能力应该怎么被组织起来”。

当前 `prd-generator` 已经明显站在“Skill”这一层，而不只是一个底层工具接口。

这件事本身，就已经很重要了。

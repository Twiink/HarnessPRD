# 前端结构化录入：表单为什么要主动贴近 Schema

很多 AI 产品在输入这一步的默认思路都是：

让用户尽量自然地说，剩下交给模型理解。

这种方式有它的优点，尤其在早期产品验证时，会显得很轻、很自然、很“AI”。

但一旦你真的想把后面的 PRD、接口文档、提示词做稳，就会很快碰到一个硬问题：

> 模型当然可以理解输入，但它理解出来的结构，未必就是你后续系统真正需要的结构。

这也是为什么 `/v2` 前端在设计时做了一个非常明确的选择：

不是让表单继续停留在“自由表达层”，而是让它尽量贴近后端 schema。

## 为什么这一层不能留给后端兜底

因为如果前端仍然只是把一堆自由文本扔给后端，那么后端 skill 即使存在，也会被迫承担两件完全不同的工作：

1. 先猜用户到底想表达什么结构
2. 再基于这个猜出来的结构生成文档

这样 skill 的稳定性就会被输入的随机性持续拖垮。

所以更合理的分工是：

- 前端负责把输入收敛成稳定结构
- 后端负责基于这个结构去执行 skill

这其实是在把“结构化”这件事前移。

## 当前前端并没有直接让用户写 JSON

这里有个很值得讲清楚的点。

`/v2` 的前端虽然贴近 schema，但它并没有直接让用户手改 JSON。

这是一个很克制、也很正确的决定。

因为如果真让用户直接编辑最终 JSON，会立刻带来几个问题：

- 人类填写成本太高
- 很容易写坏格式
- 不适合做字段级提示

所以当前前端的策略是：

先用一套更适合录入的 `StructuredFormData` 表单结构承接用户输入，  
再通过转换函数把它稳定转成 `requirements_summary`。

你可以把它理解成：

```text
用户友好的录入层
-> 程序可消费的结构层
```

## 这层映射到底是怎么做的

当前主要逻辑在：

[`frontend/src/AppV2.tsx`](../../frontend/src/AppV2.tsx)

核心函数是：

```ts
buildRequirementsSummary(formData)
```

它做的事情其实很“技能系统化”：

- 把多行文本拆成数组
- 把 `MVP 功能` 的每一行拆成对象
- 把页面结构拆成 `{ name, modules, notes }`
- 把认证、数据库、部署等字段归到 `technical_constraints`
- 把安全、性能、可用性归到 `non_functional_requirements`

所以从前端视角看，它不是“提交表单”，而是在构建一个 skill 可消费对象。

## 为什么 `MVP 功能` 和 `页面结构` 要变得更严格

这里其实是一个非常典型的工程取舍。

老做法会更宽松，比如：

- “请写一下 MVP 功能”
- “请大概描述一下页面”

用户当然更容易写，但系统后续就必须继续猜。

`/v2` 现在改成这种约束：

- `功能名称｜功能描述｜用户价值`
- `页面名｜模块1,模块2｜备注`

看起来更“硬”，但它直接换来了两件事：

1. 后端更容易稳定消费
2. 回填之后也能反向映射回表单

这就是为什么用户一开始说“稳定可靠比体验更重要”后，这条路就变得特别合理。

## 为什么还要给用户看 JSON 预览

这是这套前端设计里一个很漂亮的点。

如果前端只做结构化转换，但用户看不到转换结果，那中间层仍然是黑盒。

所以 `/v2` 增加了：

- `requirements_summary` JSON 预览

它的价值非常大：

- 用户第一次能看见“系统到底理解成了什么结构”
- 开发者第一次能直接调试前端映射是否稳定
- skill 的输入第一次真正变成可见对象

这一步对整个 skill-first 方案其实是关键加分项。

## 这一层设计为什么值得

你可以把 `/v2` 的前端理解成一个“结构化输入运行时”，而不只是一个 UI。

它承担的职责已经不再只是采集数据，而是：

- 稳定输入
- 约束格式
- 提前校验
- 显示结构结果
- 为后续回填和 diff 做准备

这也是为什么前端这一层在 skill 设计里其实远比看上去重要。

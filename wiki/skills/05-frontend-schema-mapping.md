# 前端结构化录入与 Schema 映射

## 1. 为什么前端要主动结构化

这套设计里，前端不是“把用户原话原封不动发给后端”，而是承担了一层非常重要的职责：

> 把用户输入稳定地收敛成可进入 skill 契约的结构化摘要。

这样做的原因是：

- 能更早发现格式错误
- 能减少模型猜测输入结构的成本
- 能让回填结果稳定回到表单

## 2. 当前实现位置

主要逻辑在：

[`frontend/src/AppV2.tsx`](../../frontend/src/AppV2.tsx)

## 3. 前端使用的结构

前端表单内部使用的是 `StructuredFormData`，它比最终 schema 更适合直接渲染到输入框：

- 很多字段先用字符串保存
- 多行文本靠换行分隔
- 复杂对象先让用户按约定格式填写

例如：

- `target_users`：每行一个
- `mvp_features`：每行 `功能名称｜功能描述｜用户价值`
- `ui_pages`：每行 `页面名｜模块1,模块2｜备注`

## 4. 为什么前端不直接编辑最终 JSON

因为直接让用户编辑 JSON 虽然最“纯粹”，但会带来明显问题：

- 不利于填写
- 容易写坏格式
- 不利于做字段级校验

所以当前采用的是：

```text
表单态 StructuredFormData
-> 转换函数
-> requirements_summary
```

## 5. 核心转换函数

核心入口是：

```ts
buildRequirementsSummary(formData)
```

它会做这些事情：

- `parseList`：把多行字符串拆成数组
- `parseMvpFeatures`：把 `｜` 分隔的功能行拆成对象
- `parsePages`：把页面定义拆成 `{ name, modules, notes }`
- 把“响应式”“认证”“数据库”等字段挂到 `technical_constraints`
- 把安全/性能/可用性挂到 `non_functional_requirements`

## 6. 为什么这种方式稳定

因为它把“用户输入习惯”和“后端 schema 契约”隔离开了：

- 用户面对的是适合录入的表单
- 后端消费的是稳定的结构化对象

这也是为什么回填时能够再从 `RequirementsSummary` 反向转回表单。

## 7. 当前的校验策略

前端已经做了基础严格校验：

- 必填字段不能为空
- `MVP 功能` 必须符合 `名称｜描述｜用户价值（可选）`
- `页面结构` 如果填写，必须符合 `页面名｜模块列表｜备注（可选）`
- `在范围内` 和 `不在范围内` 不能重复

这让前端在“进入澄清对话”之前，就先把最危险的输入问题拦掉了。

## 8. 这套映射设计的意义

它让整个系统第一次具备了这样的能力：

> 用户不是把“想法”发给模型，而是把“半结构化需求对象”发给 skill。

这是 skill-first 设计真正成立的基础。

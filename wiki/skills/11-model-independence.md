# 模型独立性：这套 Skill 设计为什么不应该绑死在某一个模型上

很多产品在做到一定阶段之后，都会出现一个非常现实的分叉口：

今天这套能力是围绕 Claude 做的，明天如果要接 OpenAI 怎么办？  
后天如果又想接别的 Agent runtime，是不是又要重做一遍？

这个问题如果一开始不想清楚，后面几乎一定会越来越痛。

所以这套设计在很早的时候就做了一个明确选择：

> 输出可以服务 Claude，但能力本身不能只属于 Claude。

## 什么叫“模型独立”

这里说的模型独立，不是说完全不考虑模型差异。  
不同模型当然会有：

- 风格差异
- 稳定性差异
- JSON 严格性差异
- 对长上下文的耐受度差异

所谓模型独立，真正强调的是：

> 核心能力的定义，不应该被某个模型品牌或某个 SDK 格式绑定死。

也就是说，今天就算主要服务 Claude，这个 skill 也不该写成“只有 Claude 才能理解”的样子。

## 当前哪些部分已经做到模型无关

### `skill.yaml`

它定义的是能力契约，不是某个模型的专属调用格式。

### `instructions.md`

它虽然是自然语言，但本质上是技能说明，不依赖某个 SDK 私有协议。

### `field-schema.json`

这是标准 JSON Schema，本身就和模型品牌无关。

### `/v2` 工作台流程

前端的结构化录入、diff、确认、阶段跳转，这些都属于工作流逻辑，不属于任何一个模型。

### `llm_factory`

当前后端已经通过：

[`backend/services/llm_factory.py`](../../backend/services/llm_factory.py)

把 Anthropic 和 OpenAI 做了抽象切换。

这说明模型选择和 skill 定义已经开始被分层处理。

## 当前哪些地方还会受到模型差异影响

说实话，当前系统当然还没有“完全中立”到模型可随便替换而不受影响。

最明显的几个点是：

### 1. Prompt 仍然是自然语言 Prompt

自然语言 Prompt 天生就会受到模型风格影响。

### 2. JSON 输出稳定性不同

有的模型天生更容易严格遵守格式，有的更容易多说几句。

### 3. 文档表达会有风格倾向

哪怕契约一样，不同模型写出来的文档节奏、颗粒度、重复度也会不一样。

所以模型独立从来不是“完全无差异”，而是“差异不会侵入能力定义本身”。

## 为什么这仍然是值得坚持的方向

因为一旦核心能力被独立出来，后续模型切换时你需要改的，通常不再是整套系统，而只是局部：

- `llm_factory`
- 某些 Prompt 细节
- 某些修复策略

真正不会轻易动的，反而是最重要的那部分：

- 输入 schema
- 输出模板
- 工作流
- 中间确认机制

这就说明设计方向是对的。

## 一个很实际的判断标准

你可以用一句很简单的话来判断一个技能体系到底有没有模型独立性：

> 如果明天把底层模型换掉，哪些东西必须重写？

在这套设计里，真正必须重写的部分相对有限；  
而不该重写的那部分，已经被尽量抽成：

- skill 包
- schema
- references
- 工作台逻辑

这就是模型独立性正在发生的证据。

## 为什么这和 OpenClaw 风格会天然走到一起

因为 OpenClaw 一类系统的核心思想，本来就是：

能力应该尽量独立于底层模型与运行时存在。

你当然可以先服务某个模型，但只要你把：

- 输入契约
- 输出契约
- 能力说明
- 参考资料

都抽出来了，后续跨模型迁移的难度就会小很多。

这也是为什么 skill-first 和 model-agnostic 几乎总是一起出现。

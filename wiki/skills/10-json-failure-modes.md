# JSON 故障手册

## 1. 为什么 JSON 回填经常出问题

因为“让模型输出 JSON”远比“让模型输出 Markdown”脆弱。

只要它犯下面任何一种错，解析就会失败：

- 少一个逗号
- 多一个引号
- 输出了代码块围栏
- 在 JSON 前后加了解释
- 把中文说明塞进对象中间
- 粘了两个对象
- 字符串里有未转义引号

## 2. 当前最常见的失败场景

### 2.1 代码块包裹

```text
```json
{ ... }
```
```

### 2.2 解释性前缀

```text
以下是修正后的 JSON：
{ ... }
```

### 2.3 看起来像 JSON，但内部语法错误

例如：

- 少逗号
- 尾逗号
- 字符串没闭合

### 2.4 结构正确但不是对象

例如模型返回数组或多段内容拼接。

## 3. 当前的第一层兜底

后端现在会先调用 `_extract_json_object()`：

- 去掉代码块围栏
- 去掉 `json` 标记
- 尝试直接 `json.loads`
- 再尝试从首个 `{` 到最后一个 `}` 中间切对象

这能覆盖很多“轻度跑偏”的情况。

## 4. 当前的第二层兜底

如果第一层提取失败，会触发一次**JSON 修复调用**：

- 把模型原始输出再喂回模型
- 明确要求“只修复为合法 JSON 对象”

这是对第一轮生成失败的补救，而不是重新理解需求。

## 5. 当前的错误返回策略

如果第二层还失败，接口不再返回裸 500，而是：

- 返回更明确的错误
- 附带原始输出片段
- 附带修复后输出片段

这样下一轮排查就不需要靠猜。

## 6. 为什么仍然会失败

因为模型不是 JSON parser。  
它可以被强约束，但不能被完全假设成语法严格机器。

所以这类回填设计必须接受一个现实：

> “让模型生成 JSON” 必须配合解析、修复、错误回传和人工确认。

## 7. 更稳的未来方案

未来可以继续升级为：

1. 使用严格工具调用 / function calling
2. 用更细粒度字段级回填，而不是一次更新整对象
3. 增加 schema validator
4. 对模型输出做自动清洗与重排

## 8. 设计经验总结

做 skill 系统时，JSON 不是边角问题，而是核心工程问题。  
只要系统中间态要结构化，就必须认真设计：

- 生成约束
- 解析策略
- 修复策略
- 错误可观测性

# JSON 故障手册：为什么“让模型吐 JSON”总是没看起来那么简单

只要系统开始依赖结构化中间态，迟早都会碰到一个问题：

> 模型输出的 JSON 没你想的那么老实。

这件事几乎可以算是所有 skill 系统都会踩的坑。  
因为一旦你不只是要一段自然语言，而是要一段严格可解析、可回填、可继续流转的数据对象，模型的自由表达就会立刻变成风险。

## 最常见的误解：看起来像 JSON，不等于它真是 JSON

很多时候，模型返回的内容在视觉上非常像 JSON：

- 有花括号
- 有键值对
- 字段名也都差不多对

但只要里面存在下面任意一种问题，解析器就会立刻失败：

- 少一个逗号
- 多一个尾逗号
- 字符串里的引号没转义
- 在对象前后加了解释
- 包了 ```json 代码块
- 把两个对象拼在了一起

这也是为什么“肉眼看上去差不多”这件事，在回填链路里几乎没有意义。

## 这类问题为什么在回填场景特别多

因为回填不是纯文档生成，它要求模型做的是一件更别扭的事情：

> 读懂一份已有结构化对象，再结合澄清对话，重新输出一个更新后的结构化对象。

这件事天然比“写 Markdown”更脆弱。

Markdown 就算多写几句、少写一段，通常也还能看。  
JSON 不行，哪怕只错一个字符，整段就不能用。

## 当前最容易出现的几类故障

### 1. 代码块包裹

模型很喜欢这样输出：

```text
```json
{ ... }
```
```

对人没影响，对解析器却是直接报错。

### 2. 解释性前缀

比如：

```text
以下是修正后的 JSON：
{ ... }
```

这在人类语境里很自然，但在接口语境里就是脏数据。

### 3. 看起来是对象，内部语法却坏了

这类最烦。

因为它说明模型大体理解了任务，但输出时还是没做到严格格式化。  
最典型的报错就是：

```text
Expecting ',' delimiter
```

### 4. 不是单个对象

有时模型会输出：

- 一个对象加一段说明
- 两个对象拼接
- 一个数组而不是对象

这些都会让下游失去稳定性。

## 当前是怎么兜底的

这套系统现在已经做了多层兜底。

### 第一层：直接解析

如果模型很配合，直接 `json.loads` 就结束。

### 第二层：尝试提取对象

如果有围栏、前缀、尾部说明，就先清洗，再从首个 `{` 到最后一个 `}` 截对象。

### 第三层：再次让模型修 JSON

如果提取后还是不合法，就再发一次模型请求，但这次任务非常单纯：

> 不重新理解需求，只把现有输出修成合法 JSON 对象。

这一步的意义不是提高智能，而是把模型当成一个“格式修复器”。

### 第四层：错误信息可观测

如果连修复轮都失败，就不再只抛一个冷冰冰的 500，而是尽量把：

- 原始输出片段
- 修复后输出片段

带回来，方便继续定位。

## 为什么这套策略比“强行要求模型只输出 JSON”更现实

因为任何做过这类系统的人最后都会承认一个事实：

> 你当然应该要求模型只输出 JSON，但你不能指望它永远真的做到。

这不是模型不够强，而是自然语言模型本质上仍然偏向“表达”，不是偏向“语法绝对正确”。

所以真正稳的系统不会停留在“我已经在 Prompt 里强调了”，而会继续补：

- 清洗
- 提取
- 修复
- 错误回传

这才是工程态度。

## 一个很实用的经验

只要你要让模型参与中间态数据流，就不要把 JSON 问题当边角料。

它不是偶发问题，而是这类系统的常驻主线问题。

你今天做的是 PRD 回填，明天做接口 patch、配置同步、任务编排，都会重新碰到它。

所以越早认真设计 JSON 失败路径，后面的 skill 系统就越不容易失控。

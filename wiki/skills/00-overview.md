# 总览：这套 Skills 设计到底解决了什么问题

如果只从产品表面看，VibeCoding 的事情并不复杂：用户说需求，AI 帮他整理，然后生成 PRD、接口文档和提示词。

问题是，只要你真的去做，就会很快发现这件事远不是“一段 Prompt + 一个按钮”那么简单。

真正困难的地方通常不在“生成文档”，而在这几件事：

- 用户输入天然是乱的、散的、层次不稳定的
- 对话里补充的信息很容易只停留在聊天记录里，回不到结构化对象
- 模型一旦自由发挥，输出就会漂
- 今天你也许想服务 Claude，明天可能又想接 OpenAI，后天还想接别的 Agent 运行时

所以这套新方案的重点从一开始就不是“把 Prompt 写得更长”，而是换一个问题定义：

> 我们要做的不是“一次调用模型生成 PRD”，而是“把 PRD 生成做成一项可以复用、可以迁移、可以验证的 skill 能力”。

这就是 `wiki/skills/` 整组文档的出发点。

## 为什么旧思路不够了

旧思路更像这样：

```text
用户输入 -> 会话历史 -> 模型生成 PRD
```

这种方式不是不能用，早期验证产品想法时甚至很高效。但它有一个很明显的问题：几乎所有关键东西都混在一起了。

- 输入没有稳定结构
- 澄清没有独立阶段
- 对话补充没有回填
- PRD 生成没有清晰的中间检查点
- 文档质量高度依赖模型当时的发挥状态

换句话说，这条链路跑起来很顺，但可控性并不高。

## 新方案到底变了什么

新方案不是把原链路推倒重来，而是把中间那些原本隐形的步骤显式化。

现在更接近这样：

```text
结构化录入
-> schema 校验
-> 澄清对话
-> 结构化回填
-> diff 预览
-> 用户确认
-> PRD 生成
-> 接口文档
-> 提示词
```

这条链路一旦建立起来，你会立刻得到几样旧方案很难同时拥有的东西：

- 输入更稳
- 中间态可见
- 用户能确认系统到底改了什么
- 文档生成前有明确边界
- 能力开始具备跨平台复用的可能

## 这套方案为什么叫 skill-first

因为这里真正被抽象出来的，不再是“某条 Prompt”，而是一项能力本身。

以 `prd-generator` 为例，它不只是几句给模型的自然语言，而是一整个能力包：

- 有自己的 `skill.yaml`
- 有自己的 `instructions.md`
- 有自己的 schema
- 有自己的模板
- 有自己的示例输入输出

这意味着系统对它的理解，不再停留在“这是一个生成 PRD 的接口”，而是：

> 这是一个独立能力，它有输入契约、有输出契约、有执行规则，也有失败边界。

一旦这样理解，很多后面的设计就都顺了。

## 为什么前端也必须跟着变

skill-first 的一个常见误区是：好像只要后端把 skill 做出来就行。

其实完全不是。

因为如果前端还停留在“把一堆自由文本发给模型”的阶段，那后端 skill 再漂亮，也只是被迫替前端兜底。

所以 `/v2` 工作台做的第一件大事，就是把前端也拉进这个体系里：

- 表单要贴近 schema
- 输入要提前做校验
- 用户要能看见自己最终提交的是哪个结构化对象
- 对话回填之后要能直观看到 diff

你可以把它理解成：前端不再只是界面，而是 skill 运行时的一部分。

## 为什么这套设计天然会走向平台无关

一旦能力被拆成：

- `skill.yaml`
- `instructions.md`
- `references/`
- schema
- 工作流

它就不再天然依赖某一个模型品牌。

今天它当然可以很好地服务 Claude Code，因为当前输出目标本来就对 Claude 很友好；但从结构上看，它也完全可以被：

- OpenAI 模型
- 其他 Agent
- 未来自己的 skill runtime

继续消费。

这就是为什么这套设计会明显带有 OpenClaw 风格的影子，但又不必直接绑定 OpenClaw 本身。

## 一句话总结

这套 Skills 设计真正解决的，不是“怎么让 AI 更会写文档”，而是：

> 怎么把“AI 生成文档”这件事，从一次不透明的 Prompt 调用，升级成一条可见、可控、可确认、可迁移的能力链路。

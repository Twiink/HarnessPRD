# 澄清对话：为什么不能一开始就生成 PRD

很多人对这套流程最直觉的疑问是：

既然前端都已经结构化录入了，为什么还要多一段澄清对话？  
为什么不直接生成 PRD？

这个问题非常关键，因为它正好打在 skill-first 方案最核心的地方。

答案其实很简单：

**结构化输入解决的是“输入有骨架”，不是“输入已经足够清楚”。**

## 结构化并不等于充分

把用户输入收成 schema，当然已经比自由文本稳定很多了。  
但它仍然经常会留下几类典型问题：

### 1. 字段填了，但意思不够明确

比如用户写：

- “需要登录”
- “支持管理后台”
- “要有历史记录”

这些都不是错，但远远不够生成高质量 PRD。

### 2. 字段合法，但粒度不对

比如 `MVP 功能` 写成：

- 用户系统
- 内容系统
- 数据系统

听起来像填了，其实太粗。

### 3. 字段之间有冲突

比如：

- 说不需要数据库
- 又要求保存历史记录

这种冲突如果不在中间阶段被识别，后面的文档就一定会别扭。

## 所以澄清对话不是附属功能，而是结构化输入的补完层

这段对话真正的任务不是“聊天”，也不是“继续收集更多自然语言”，而是：

> 围绕当前结构化摘要里最影响后续产出的缺失项、歧义项和冲突项，做最小必要确认。

你可以把它理解成：

- 结构化录入负责搭骨架
- 澄清对话负责补关节

没有这一步，后面的 PRD 其实还是会被迫依赖模型猜测。

## 为什么 `/v2` 必须给澄清对话单独 Prompt

这里踩过一个非常典型的坑。

最开始如果直接复用旧版通用对话 Prompt，模型很容易在“信息差不多够了”的时候直接开始：

- 大段总结
- 输出结构化内容
- 甚至提前写 PRD

这在旧流程里可能不算坏事，但在 `/v2` 里会直接破坏顺序。

因为 `/v2` 需要的是：

```text
先澄清
再回填
再 diff
再确认
最后才生成 PRD
```

所以后来专门加了 `CLARIFICATION_SYSTEM_PROMPT`，明确限制：

- 只做澄清
- 不生成 PRD
- 不输出完整文档
- 信息足够时只提示“可以结束澄清”

这一层限制非常关键，它让“流程边界”从前端按钮层延伸到了模型行为层。

## 为什么澄清之后必须接回填

澄清如果只是停留在聊天记录里，它的价值会被削弱一大半。

因为这意味着：

- 用户补充的信息只是“说过”
- 不是“被结构化系统记住了”

而 skill-first 方案最重视的，恰恰是中间态的稳定性。

所以正确闭环一定是：

```text
结构化摘要
-> 澄清对话
-> 回填结构化摘要
-> diff 预览
-> 用户确认
-> PRD
```

只有这样，澄清才真正参与了能力链路，而不只是增加了一段会话。

## 一句话说透这段对话的意义

如果把 `/v2` 理解成一条 skill 驱动流水线，那么澄清阶段做的事情其实是：

> 在文档生成之前，先把“看起来合法的输入”推进到“足够可靠的输入”。

这一步很不起眼，但它几乎决定了后面所有产物的质量上限。

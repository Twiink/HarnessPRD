# 澄清对话闭环

## 1. 为什么不能一开始就生成 PRD

如果直接用结构化摘要生成 PRD，通常会遇到 3 个问题：

1. 缺字段  
用户没有填到位，直接生成会出现大量 `待确认`

2. 模糊字段  
例如“需要登录”并不等于“需要什么角色体系”

3. 错字段  
用户表单里写法看似合法，但真实意图并没有说清楚

所以在 skill-first 方案里，澄清不是可选项，而是质量控制的一部分。

## 2. 当前对话目标

当前 `/v2` 的澄清对话目标不是“聊天”，而是：

> 围绕结构化摘要里还不清楚、还不稳定、还影响后续文档质量的字段，做小步确认。

## 3. 当前的专用澄清 Prompt

当前澄清阶段已经不用旧的通用 `SYSTEM_PROMPT`，而是用了专门的：

`CLARIFICATION_SYSTEM_PROMPT`

位置：

[`backend/services/prompts.py`](../../backend/services/prompts.py)

它显式限制了：

- 只做澄清
- 不生成 PRD
- 不输出完整文档
- 信息足够时提示“可以结束澄清”

## 4. 为什么这个限制很重要

如果还沿用老 prompt，模型常会在信息足够时直接开始：

- 生成 PRD
- 输出大段总结
- 提前进入文档写作

这会破坏 `/v2` 的工作流秩序。

## 5. 当前澄清的操作方式

结构化表单提交后，前端会先构建一个 `conversation seed`，包含：

- 产品名称
- 核心目标
- 目标用户
- 平台
- MVP 功能
- 页面结构

然后明确告诉模型：

> 请先指出最需要澄清的 3 个问题，再逐步和我确认。

## 6. 为什么澄清对话必须可回填

如果澄清只是聊天，不回到结构化摘要里，它的价值会大打折扣：

- 无法稳定进入 PRD 生成
- 用户也不知道补充的信息到底被系统记住了没有
- 下一步生成仍然可能基于旧摘要

所以澄清 -> 回填 是必须成对出现的。

## 7. 当前闭环

当前闭环已经是：

```text
结构化摘要
-> 澄清对话
-> 回填摘要
-> diff 预览
-> 用户确认
-> PRD 生成
```

这个闭环的意义在于：

- 用户补充的信息不会只存在于自然语言里
- 系统不会悄悄修改结构化摘要
- 生成 PRD 之前有一次明确确认

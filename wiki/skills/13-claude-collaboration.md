# 当前与 Claude 的协作方式

## 1. 为什么还要单独讲 Claude

因为这个项目一开始就有一个很强的目标：

> 输出可以被 Claude Code 这类 AI 编程工具直接消费的 PRD、接口文档和提示词。

所以即使 skill 要平台无关，当前与 Claude 的协作方式仍然非常重要。

## 2. 当前哪些地方明显考虑了 Claude

### 2.1 PRD 生成目标

在现有文案里，一直强调：

- Claude Code 可直接用于 AI 辅助开发
- 文档要工程可执行
- 结构清晰

### 2.2 提示词套件设计

系统最终生成的提示词，本身就是面向 Claude Code 场景设计的。

### 2.3 文档结构倾向

例如：

- MVP 功能表格
- 范围内/范围外
- 技术规格表格

这些都很适合 Claude 这种需要快速建立上下文的 Agent。

## 3. 但为什么不能只围绕 Claude 设计

因为如果全部逻辑都围绕 Claude 写死：

- 换模型时成本高
- 换运行时成本高
- skill 无法复用
- 文档与能力会被某个平台“吞掉”

所以现在的策略是：

- 核心能力平台无关
- 当前输出仍然照顾 Claude 的消费习惯

## 4. 当前实际协作边界

可以把当前协作理解成三层：

### 4.1 Skill 层

不依赖 Claude。

### 4.2 文档层

文档结构明显偏向适合 Claude Code 直接消费。

### 4.3 提示词层

提示词当前明确考虑 Claude Code 场景。

## 5. 这是一种好的过渡状态

因为它避免了两个极端：

### 极端一：完全平台私有

所有设计都绑在 Claude 上。

### 极端二：完全平台中性

结果文档太抽象，反而不好用于真实开发工具。

当前方案的平衡点是：

- skill 定义尽量通用
- 输出内容尽量实用

## 6. 未来怎么做得更成熟

未来可以把“面向 Claude 的优化”单独放到 adapter 或 profile 中，例如：

- `profiles/claude-code.md`
- `profiles/openai-codex.md`

这样就能把：

- 通用 skill 核心
- 平台消费偏好

做得更干净地分离。

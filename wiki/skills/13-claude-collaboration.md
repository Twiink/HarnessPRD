# 当前与 Claude 的协作：为什么这套设计一边面向 Claude，一边又不能只面向 Claude

如果完全不提 Claude，这套设计会显得有点假。  
因为 VibeCoding 一开始就有一个非常明确的现实目标：

> 生成出来的 PRD、接口文档和提示词，要足够适合 Claude Code 这种 AI 编程工具继续消费。

所以在讨论 skill-first 的时候，一定要承认一个事实：

今天这套系统确实是在和 Claude 协作，而且协作得还挺深。

问题只是，它不能因此变成一套**只为 Claude 存在**的系统。

## 当前哪些地方明显在照顾 Claude

这件事其实非常明显，甚至不需要特意隐藏。

### 1. PRD 的风格就是面向 AI 工程消费的

现在的 PRD 结构强调：

- 清晰章节
- 表格化 MVP
- 范围内 / 范围外
- 技术规格收敛

这类文档不只是方便人看，更方便 Claude 这类模型快速建立上下文。

### 2. 提示词套件本来就有 Claude Code 场景

系统最终生成的那一组 Prompt，本身就是在认真服务 Claude Code 这类使用场景。

### 3. 整体文档风格偏“可执行”

这类文档不是写给品牌宣传页的，也不是写给抽象战略会的，而是写给：

- 工程师
- AI 编程助手
- 后续自动化流程

这和 Claude 的消费方式天然是契合的。

## 那为什么还要强调平台无关

因为如果你把所有逻辑都和 Claude 写死，后面一定会碰到这些问题：

- 换模型时整个系统牵一发动全身
- skill 文件没法迁移
- 运行时层和能力层纠缠在一起
- 你会越来越难分清楚哪些是“能力定义”，哪些只是“Claude 偏好”

这会把系统做窄。

## 当前其实已经形成了一个很自然的分层

现在最合理的理解方式不是“这是一套 Claude 系统”，而是把它拆成三层。

### 第一层：Skill 核心

包括：

- `skill.yaml`
- `instructions.md`
- schema
- references

这层尽量平台无关。

### 第二层：工作流与运行时

包括：

- `/v2` 工作台
- 回填
- diff
- 阶段控制

这层也尽量平台无关。

### 第三层：当前主要消费对象

这里的消费对象之一，就是 Claude Code。

也就是说：

- skill 本身不属于 Claude
- 但当前输出显然很照顾 Claude 的使用习惯

这是一种很健康的状态。

## 为什么这种状态其实比“完全中立”更好

如果你强行追求绝对中立，有时反而会做出一种“谁都能用，但谁用起来都不够顺”的结果。

而当前这套设计更实际：

- 核心能力尽量通用
- 当前落地结果尽量好用

所以它既没有被 Claude 锁死，也没有为了抽象而牺牲今天的产品价值。

## 一个很自然的未来方向

等到 skill 体系更成熟，后续完全可以把“面向不同消费方的偏好”单独抽成 profile 或 adapter。

比如：

- `profiles/claude-code.md`
- `profiles/openai-codex.md`

这样就能把：

- 技能核心
- 运行时逻辑
- 平台消费偏好

进一步拆开。

但在今天这个阶段，先把“能服务 Claude，又不被 Claude 绑死”做到，其实已经是一个非常务实也非常对的平衡点。

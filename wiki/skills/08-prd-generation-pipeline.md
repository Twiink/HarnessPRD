# PRD 生成流水线：结构化摘要、对话、模板是怎么组合起来的

如果只看接口名字，PRD 生成好像只是一次请求：

`generate-prd-from-summary-stream`

但真正的事情其实没那么简单。

从系统角度看，它更像一条由多个层次叠起来的流水线，而不是“把输入交给模型就完了”。

## 先把这个过程想象成几层叠加

PRD 最终能不能稳，取决于下面这几层能不能一起工作：

```text
结构化摘要
+ 澄清对话补充
+ skill 执行规则
+ PRD 模板
+ 写作约束
= 最终 PRD
```

这也是为什么这套设计比传统 prompt-only 方案明显更重，但也明显更可靠。

## 第一层：结构化摘要是骨架

整个生成流程最重要的输入不是会话历史，而是 `requirements_summary`。

这是一个非常关键的转变。

传统做法里，模型面对的通常是一整段聊天记录，它需要自己从中抽出：

- 产品名
- 目标用户
- MVP
- 技术约束
- 非功能需求

这一步非常耗费模型的“自由理解能力”，也很容易漂。

而现在，前端已经先把这些内容收成对象了。  
模型面对的不是一团自然语言，而是一份有骨架的输入。

## 第二层：澄清对话是修正和补充层

虽然结构化摘要是主输入，但它不是唯一输入。

系统在生成 PRD 时，还会把澄清对话一起喂进去，目的是让模型知道：

> 哪些信息后来被补充清楚了，哪些地方已经有了比原摘要更明确的说法。

这个设计非常像“主数据 + 补充上下文”的关系。

也就是说：

- 结构化摘要负责稳定
- 对话负责纠偏和补充

这样既不会让对话重新变成主导输入，也不会浪费掉澄清过程中已经确认下来的细节。

## 第三层：Skill 参考文件负责给生成加边界

这是 skill-first 方案里特别重要的一层。

生成前，后端会从 `skills/prd-generator/` 读取：

- `instructions.md`
- `references/prd-template.md`
- `references/writing-rules.md`

这三样东西分别在控制不同的风险：

### 模板控制结构漂移

模型不应该随便发明章节。

### 写作规则控制内容质量

比如：

- 少空话
- 少重复
- MVP 用表格
- 缺失信息写 `待确认`

### 指令控制整体执行方式

它让模型明白自己此刻不是在自由创作，而是在执行一个 skill。

## 第四层：后端 Prompt 组装不是简单拼字符串

在实现上，这一步在：

[`backend/services/document_service.py`](../../backend/services/document_service.py)

里通过 `_build_prd_from_summary_prompt()` 完成。

从代码角度看它当然是“在拼 Prompt”，但从设计角度看，它做的事情其实更像：

> 把 skill 契约、输入对象和参考规则压缩成一次模型可消费的执行上下文。

这和单纯的“写一大段 Prompt”其实完全不是一个层次。

## 为什么这条流水线比旧方案稳

旧方案更像：

```text
会话历史 -> PRD
```

新方案更像：

```text
结构化输入
-> 补充上下文
-> 契约约束
-> 模板渲染
```

当你这样拆开看，就会发现新方案的稳定性其实来自两个地方：

1. 输入先被收敛
2. 输出再被约束

这两头一起夹住，中间模型的发挥空间自然就没那么容易失控。

## 为什么 PRD 生成一定要放在 diff 确认之后

这里还有一个经常被忽略的点。

既然对话会回填摘要，那生成 PRD 之前就必须先让用户确认这些回填结果。

否则用户会面临一种很糟糕的体验：

- 系统默默改了摘要
- 然后直接按这份修改后的摘要生成文档

这会让人失去对系统的信任。

所以现在的顺序必须是：

```text
结束澄清
-> 回填
-> diff 预览
-> 用户确认
-> PRD
```

这个顺序看起来多了一步，但其实是在给后续所有文档质量兜底。

## 这一条流水线真正厉害的地方

它不是把模型“用得更猛”，而是把模型放到了一个更合适的位置。

模型不再负责：

- 从混乱输入里硬猜结构
- 临场决定整份文档骨架
- 默默修改用户数据

它更像是在一套已经铺好的轨道上，做最后那一步高质量表达。

这也是为什么这条 PRD 生成流水线，看起来流程更多了，结果反而更稳。

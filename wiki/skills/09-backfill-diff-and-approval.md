# 回填、Diff 与确认机制

## 1. 为什么一定要回填

澄清对话的价值不在“问了什么”，而在：

> 问完之后，结构化摘要究竟变成了什么。

如果没有回填：

- 补充信息只留在聊天记录里
- 结构化输入与最终文档之间仍然存在断层
- 下一次继续生成时，系统很难稳定复用这些确认结果

## 2. 当前回填的输入

回填接口当前接收：

- `requirements_summary`
- `conversation_messages`

接口：

`POST /api/conversation/sync-summary-from-conversation`

## 3. 当前回填的目标

模型的任务不是重写文档，而是：

> 根据澄清对话，对现有结构化摘要做必要的、保守的更新。

这意味着它应该：

- 覆盖更明确的信息
- 保留未确认信息
- 维持原字段结构
- 不随便新增字段

## 4. 为什么要做 diff 预览

因为回填是一个高风险动作：

- 用户未必意识到系统会改哪些字段
- 模型可能误解一段对话
- 某个字段可能被改得过头

所以当前设计里，回填之后不会直接应用，而是先展示 diff。

## 5. 当前 diff 机制

前端通过 `collectSummaryDiff()` 对：

- 回填前摘要
- 回填后摘要

做字段级比较。

当前 diff 具备这些能力：

- 只展示有变化的字段
- 支持嵌套路径，如 `technical_constraints.auth`
- 标记变化类型：
  - 新增
  - 修改
  - 删除

## 6. 为什么确认后直接生成 PRD

以前“应用到表单”是个中间动作，但会让链路拖长。

当前改成：

```text
结束澄清
-> 回填
-> diff 预览
-> 确认并生成 PRD
```

这样更符合真实心理模型：

- 用户不是为了“修改表单”
- 用户是为了“确认这些变更后继续走流程”

## 7. 为什么仍然保留回表单能力

虽然确认后会直接生成 PRD，但系统仍然会把回填后的摘要同步回表单状态。

这意味着用户后续：

- 仍能返回表单
- 继续查看结构化 JSON
- 重新编辑输入

## 8. 这套机制的价值

它把原本不可见的中间态，变成了：

- 可见
- 可审
- 可拒绝
- 可继续流转

这正是 skill-first 方案区别于单次 prompt 方案的关键。

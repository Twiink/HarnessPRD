# 目录解析与文件解析：这套 Skill 到底是怎么被系统找到并读进去的

很多时候，大家会把注意力都放在 skill 内容上，容易忽略一个看起来很“工程细节”的问题：

> 系统到底怎么知道去哪里找这套 skill？

这个问题一点都不边缘。  
因为 skill 是否真正独立，看的不只是它有没有自己的目录，还要看运行时是否能把它当成一个稳定资产来定位和加载。

## 先看当前的目录约定

现在项目里的技能包放在：

```text
skills/
  prd-generator/
```

然后在后端：

[`backend/services/document_service.py`](../../backend/services/document_service.py)

里，通过 `_load_skill_artifact()` 读取 skill 文件。

当前的查找方式其实非常直接，就是从服务文件所在位置向上回到项目根目录，再进入：

```text
skills/prd-generator/
```

然后按传入路径继续往下找。

## 这种方式为什么看起来简单，但其实已经够用了

它当然不是一个完整的 skill registry，也没有做自动发现、多版本协商、动态装载之类更高级的事情。

但它已经满足了当前阶段最关键的目标：

1. skill 文件不再散落在代码里
2. 后端确实是在“读 skill 文件”，而不是读硬编码字符串
3. skill 目录具备明确边界

这三件事一成立，很多后续演进才有基础。

## 当前到底读取了哪些文件

### 生成 PRD 时

会重点读取：

- `references/prd-template.md`
- `references/writing-rules.md`
- `instructions.md`

你可以把它理解成三层：

- 模板：告诉模型最后长什么样
- 规则：告诉模型写的时候别犯什么错
- 指令：告诉模型这个 skill 到底怎么执行

### 做摘要回填时

会读取：

- `references/field-schema.json`

这一步很关键，因为回填不是在重写文档，而是在尝试维护结构化对象。

## 文件解析本身为什么故意做得很朴素

现在的解析方式本质上就是：

- Markdown 按 UTF-8 文本读取
- JSON 要么当字符串喂给 Prompt，要么直接由代码解析

这种做法看起来不“高级”，但恰恰很适合当前阶段。

因为它有几个很实际的优点：

- 稳
- 好调试
- 不依赖额外 runtime
- 不绑某个生态

如果现在一上来就做复杂 skill loader，反而很容易把问题复杂化。

## 这套目录解析还有哪些明显边界

说实话，当前方案距离一个真正通用的 skill 运行时还有不小距离。

最明显的边界是：

### 1. skill 名称还是写死的

当前就是读 `prd-generator`，不是扫描注册表。

### 2. 没有 skill 自动发现

它不会自动去理解 `skills/` 下还有哪些能力包。

### 3. 没有版本概念

如果未来 `prd-generator` 出了 `0.2.0`、`1.0.0`，现在这套逻辑还不会处理版本选择。

## 但为什么这一步仍然很重要

因为“先让一个 skill 真正以文件形式被消费”，本身就是巨大的进步。

很多项目嘴上说自己有技能系统，实际上能力仍然分散在：

- 页面逻辑里
- Service 代码里
- Prompt 字符串里

那种状态离“可迁移的能力包”还很远。

而当前这种目录解析虽然朴素，却已经明确了一件事：

> Skill 是项目里的一级资产，不是某段业务逻辑的附属品。

这就是后面能继续做注册中心、扫描器、adapter 的前提。

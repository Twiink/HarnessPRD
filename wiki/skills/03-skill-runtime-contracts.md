# 运行时契约：Skill 真正被系统消费时，靠的不是灵感，而是 Contract

很多人第一次接触 skill 设计，会把注意力放在“给模型写了什么说明”。  
但真正决定一个 skill 能不能稳定运行的，往往不是说明本身，而是它有没有明确的运行时契约。

说得更直白一点：

> 如果系统根本不知道这项能力接受什么、输出什么、哪些地方不能乱来，那它就不是 skill，只是一个风格化 Prompt。

## 什么叫运行时契约

在这里，运行时契约指的是：

- 输入格式是什么
- 输出格式是什么
- 默认缺失值怎么表达
- 哪些规则必须遵守
- 整个过程大概应该怎么走

这些信息在当前 `prd-generator` 里主要写在：

[`skills/prd-generator/skill.yaml`](../../skills/prd-generator/skill.yaml)

## 输入契约：系统到底期待什么

先看输入。

当前 `prd-generator` 不是说“用户给我一段话就行”，而是明确要求：

- 输入格式是 `json`
- 主 schema 来自 `references/field-schema.json`
- 至少需要有：
  - `product_name`
  - `product_goal`
  - `target_users`
  - `platform`
  - `mvp_features`

这一步的意义很大。

因为它把“能不能进入技能执行”这件事，从主观判断变成了相对明确的条件判断。

换句话说，系统不是在猜“这段输入够不够”，而是在问：

> 这份输入是否满足当前 skill 的最低可消费结构？

## 输出契约：结果不是随便写篇 Markdown

从表面看，输出是 Markdown。  
但严格一点说，它其实不是普通自由文本，而是一个模板化文档产物。

为什么这么说？

因为输出同时受到这些东西约束：

- 文档必须是 Markdown
- 模板必须遵守 `prd-template.md`
- 风格必须简洁、工程可执行、低冗余
- MVP 必须以表格呈现

这时候输出就已经不是“写一篇 PRD”，而更像：

> 把一个结构化对象渲染成一份指定骨架的文档。

这类输出一旦被定义清楚，后面的接口文档生成、提示词生成都会轻松很多。

## 约束契约：系统允许什么，不允许什么

约束这部分很容易被低估。

因为很多时候，一个 skill 不稳定，不是因为模型不够聪明，而是因为边界说得不够硬。

当前 `skill.yaml` 里有几条特别关键的约束：

- 不要编造业务事实
- MVP 优先表格化
- 技术规格要区分“已确认”和“建议”
- 保持固定章节结构

你会发现，这些约束其实是在控制两个风险：

1. 模型过度发挥  
2. 文档结构漂移

只要这两件事不被控制，skill 的输出就很难稳定。

## 工作流契约：中间步骤不是可有可无

`workflow` 这一段经常会被人一眼扫过去，但它其实是 skill 设计里很高级的一部分。

它告诉你：

```yaml
validate_input
normalize_requirements
deduplicate_content
map_to_template
render_prd
```

这意味着 skill 的内部逻辑，并不被理解成“拿输入直接找模型出结果”，而是被理解成一条有明显阶段感的管线。

哪怕今天这些步骤还没有全部拆成独立代码模块，它们也已经作为契约存在了。

这很重要，因为未来你想继续增强时，会天然知道该往哪里下手：

- 想做更强校验，就加强 `validate_input`
- 想减少重复，就加强 `deduplicate_content`
- 想让模板更稳，就加强 `map_to_template`

## 为什么这套契约对多运行时特别重要

一旦输入、输出、约束、工作流都被写成明确 contract，运行时就开始具备一种很强的可替换性。

今天这个 skill 可以这样被消费：

- 前端结构化录入后交给后端
- 后端加载 skill 文件并组装 Prompt

明天它也可以这样被消费：

- 另一个 Agent runtime 读取 `skill.yaml`
- 按自己的方式加载 schema 和模板
- 再用自己的模型执行

注意，这里真正跨平台复用的不是 Prompt，而是 contract。

这也是 skill-first 比 prompt-first 更像工程系统的地方。

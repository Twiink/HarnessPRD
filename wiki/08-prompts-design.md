# Prompt 设计说明

## 概述

VibeCoding 有 5 个核心 Prompt，全部定义在 `backend/services/prompts.py`。它们共同构成产品的核心智能层。

---

## 1. SYSTEM_PROMPT — 对话角色设定

**作用：** 定义 AI 在需求收集对话中的角色和行为方式。

**设计思路：**
- 角色定位为"资深产品经理"而非"助手"，强调专业性和主动性
- 明确要求"双向对话"而非单向追问，让对话更自然
- 限定每次聚焦 1-2 个关键点，避免信息轰炸用户
- 提供 10 个基础问题框架，但不要求逐一问，只识别缺失的关键信息
- "像产品伙伴一样提出建议"——主动帮用户想到没想到的问题

**关键段落：**
```
你的工作方式：
1. 通过**双向对话**深入了解产品需求——不是单向追问，而是真正的讨论
2. 仔细分析用户提供的信息，识别不清晰、有歧义或缺失的关键点
3. 像产品伙伴一样提出建议，帮助用户想清楚他们可能没考虑到的问题
4. 每次回复聚焦 1-2 个最重要的点，不要一次问太多
5. 适时总结已确认的内容，推动对话向前
6. 当信息足够完整时，主动提议生成 PRD
```

**10 个基础问题框架（不直接问，而是用于识别信息缺口）：**
- 产品名称与核心价值
- 目标用户与使用场景
- MVP 核心功能（3-5 个）
- v2 功能规划
- 页面数量与设计风格
- 平台类型（网页/小程序）
- 是否需要用户登录
- 是否需要数据库

## 2. PRD_GENERATION_PROMPT — PRD 生成模板

**作用：** 将完整对话历史转化为标准化 PRD 文档。

**设计思路：**
- 提供明确的 Markdown 结构模板，减少 AI 自由发挥的空间
- 6 个章节覆盖开发所需的全部信息
- 强调"Claude Code 可直接用于 AI 辅助开发"——文档面向 AI 工具消费
- 表格格式（功能需求、技术规格）让结构更清晰

**文档结构：**
```
## 1. 产品概述     — 名称、核心问题（一句话）、目标用户、平台
## 2. 功能需求     — MVP 功能表格 + v2 规划列表
## 3. 页面设计     — 页面结构清单 + 视觉风格
## 4. 技术规格     — 平台/认证/存储/技术栈建议表格
## 5. 非功能需求   — 性能/安全/可用性要求
## 6. 项目范围     — 在范围内 / 不在范围内（本期）
```

**本地模板增强：**
如果 `core/prd_template.md` 存在，`_build_prd_prompt()` 会在 PRD_GENERATION_PROMPT 后追加：
```
请参考以下格式模板（仅作格式参考，内容以对话为准）：
[模板内容]
```
这样可以在不修改代码的情况下，通过修改模板文件来调整 PRD 格式。

## 3. API_DOCS_GENERATION_PROMPT — 接口文档设计

**作用：** 根据 PRD 和对话历史，设计完整的 RESTful API 接口文档。

**设计思路：**
- "核心接口 vs 边缘接口"的分类是关键设计，帮助开发者区分优先级
- 每个接口包含 Method、Path、参数表格、响应 JSON 示例，格式统一
- 明确要求遵循 RESTful 规范，减少不规范设计
- 用二级标题区分两类接口，便于快速定位

**核心 vs 边缘的区分：**
- **核心接口**：产品 MVP 必须实现，直接支持核心用户价值（如用户登录、数据 CRUD）
- **边缘接口**：辅助功能，可后期添加（如配置管理、统计报表、管理后台）

**接口格式模板：**
```markdown
### 1. [接口名称]
- **方法**：POST
- **路径**：/api/...
- **功能**：...

**请求参数**
| 参数名 | 类型 | 必填 | 说明 |
...

**响应示例**
```json
{ ... }
```
```

## 4. PROMPTS_GENERATION_PROMPT — AI 提示词套件

**作用：** 生成可直接给 Claude Code 使用的 5 类提示词。

**设计思路：**
- "直接可用，复制粘贴给 Claude Code 即可"是核心约束，每个提示词必须自包含
- 5 类提示词覆盖开发全流程：上下文建立 → 功能实现 → 接口实现 → 前端实现 → 代码审查
- 功能开发提示词数量与 PRD 中 MVP 功能数量一致（1:1 对应）
- 提示词使用中文，与项目整体语言保持一致

**5 类提示词设计意图：**

| 类别 | 在开发流程中的使用时机 |
|------|---------------------|
| 项目总览提示词 | 新开会话时，第一个发给 Claude Code 建立背景 |
| 功能开发提示词 | 每实现一个功能模块时单独使用 |
| 接口实现提示词 | 后端开发阶段，对照接口文档实现 |
| 前端开发提示词 | 前端开发阶段，包含设计风格要求 |
| 代码审查提示词 | 功能实现完成后，质量检查 |

**温度设置：** `temperature=0.5`，比文档生成（0.3）稍高，允许更有创意的提示词表达。

## 5. OPTIMIZE_DOCUMENT_PROMPT_TEMPLATE — 文档优化模板

**作用：** 根据用户指令，优化已有文档内容。

**设计思路：**
- 模板字符串，包含 4 个变量：`{doc_type_label}`、`{instruction}`、`{current_content}`、`{context_section}`
- 明确要求"直接输出文档全文"，不添加"以下是优化后的文档"等前缀（避免前端需要做文本清理）
- "只修改用户指令涉及的部分，其余内容保持不变"——精确修改，不引入不必要的变化
- `context_section` 是可选的，当有其他文档时可以作为参考上下文（如优化 PRD 时参考接口文档）

**变量说明：**
```python
OPTIMIZE_DOCUMENT_PROMPT_TEMPLATE.format(
    doc_type_label="产品需求文档（PRD）",     # 文档类型中文名称
    instruction="把技术栈改成 Vue + FastAPI",  # 用户的优化指令
    current_content="# PRD: ...\n...",         # 当前完整文档
    context_section="**参考上下文**：\n...\n\n"  # 其他文档（可选）
)
```

## Prompt 维护建议

### 修改 Prompt 时注意
1. 修改只需编辑 `backend/services/prompts.py`，无需改其他文件
2. PRD 格式变更优先考虑修改 `core/prd_template.md`，无需触碰代码
3. 温度参数在 Service 层调用 `get_llm()` 时指定，不在 Prompt 里控制
4. 中文 Prompt 使用 `ensure_ascii=False` 序列化，前端正常显示中文

### 添加新 Prompt
1. 在 `prompts.py` 添加新常量
2. 在 `document_service.py` 添加使用它的方法
3. 如果是模板字符串（含变量），在 Service 层做 `.format()` 替换

### 测试 Prompt 效果
最快的测试方式：直接在 `/docs` Swagger UI 中调用对应接口，观察输出效果。

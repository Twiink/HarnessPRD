# PRD 生成规范

当任务是将结构化需求摘要转为稳定的 Markdown PRD 时，使用本 skill。

## 输入约定

- 读取符合 `references/field-schema.json` 的 JSON 输入。
- 以输入内容为唯一事实来源。
- 重要字段缺失时写「待确认」，不要猜测。

## 输出约定

- 仅输出 Markdown。
- 章节顺序与标题遵循 `references/prd-template.md`。
- 行文简洁、面向工程落地、结构清晰。
- 避免空话、重复表述和装饰性语言。

## 工作流程

### 1. 校验输入

- 确认必填字段存在且非空。
- 将数组、布尔值、短枚举转为可读中文。
- 忽略无实现价值的未知字段。

### 2. 归一化需求

- 合并语义重复的表述。
- 区分已确认事实与建议性内容。
- 将冗长功能描述拆为原子功能项，全部已确认功能纳入统一功能表。
- 将细节归入以下分组：
  - 产品概述
  - 产品功能
  - 页面与交互设计
  - 技术约束
  - 非功能需求
  - 范围边界

### 3. 渲染各 PRD 章节

#### 1. 产品概述

- 填写产品名称、核心问题、目标用户、平台。
- 核心问题用一句话概括。

#### 2. 功能需求

- 产品功能渲染为表格，列包括：
  - 功能名称
  - 功能描述
  - 用户价值
- 每行粒度应足够支撑后续 API 或任务拆分。

#### 3. 页面设计

- 仅描述实现所需的页面、主要模块与关键交互。
- 视觉风格说明保持简短，除非设计语言直接影响实现。

#### 4. 技术规格

- 用词上区分已确认的技术约束与建议性实现选择。
- 示例：
  - 已确认：「无需用户认证」
  - 建议性：「前端可采用 React 实现」

#### 5. 非功能需求

- 仅保留可执行的约束，如性能、安全、可用性、兼容性与限流等。

#### 6. 项目范围

- 确保「在范围内」与「不在范围内」不重叠。
- 优先写具体交付物，避免空泛表述。

## 写作规则

- 默认使用短段落、列表与表格。
- 除非为清晰起见，不要在多个章节重复同一事实。
- 不要把 UI 装饰性描述写成大段散文。
- 不要编造后端、数据模型或 API 细节，除非输入中已明确提供。
- 输入暗示某实现选择但未确认时，标注为建议性内容。
- 字段未知且重要时，写「待确认」。

## 终检

- PRD 完整，产品、设计、研发可直接使用。
- 产品功能以表格呈现，而非长段落。
- 文档比原始输入更短、更清晰，同时保留关键决策。
- 各章节无明显冗余。
